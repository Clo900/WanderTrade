# hex-map-lab —— 六边形 2.5D 跑商地图实验页

这是《地图系统重构方案》的**阶段 0+1 垂直切片**，一个独立的纯网页实验：用 Three.js 渲染手绘蜡笔沙盘风的六边形 2.5D 地图，复用原项目已有的 13 座城市与 21 条道路拓扑。

当前实验版采用**统一平面微缩沙盘**：平原完全平、丘陵只做格内微起伏，山体则由簇级连续高度场生成并作为独立几何叠加在地表上。连续山格可以形成多主峰、鞍部、冲沟、岩台、山谷与不对称孤峰；相邻山格以共享的世界坐标高度场衔接，非山格、水体与河流不会被自动填平。

河流在共享角点构成的顶点图上沿格边寻路，并以同一条权威中心线同时驱动河面、地表河槽与山体切口。策划可用稀疏覆写指定 `mountainGorge`、`mountainPass`、`waterfall`、`blocked` 或 `dryValley` 等水路语义；峡谷与隘口已有真实侵蚀，且**山体网格本身会消费这个切口**（否则山壳会把整条穿山河重新盖住 —— 历史实测 171 个河道横断面里 169 个被岩石压住，见下文与方案 §15.21）；瀑布、干谷和阻断的专属视觉仍在后续范围。道路过水与跨河是桥、穿山是隧道；另有蜡笔连续描边、五档道路（泥路 → 石子路 → 夯土车辙 → 石板 → 铁轨）、生态植被、村落房屋、贴地云影与飞鸟、**日夜 / 季节 / 天气**三轴环境系统，以及两名玩家「服务器权威状态 + 客户端插值」的移动链路。

## 独立性声明

本目录是独立产物，**不读写、不修改原项目的任何文件**。与项目的关系只有一处：`src/data/world-snapshot.js` 是 `map/world-map.json` 的一份只读快照（13 城 / 21 路 / viewBox 850×520 / worldSchema 972 / terrainSeed 20260812）。之所以内联成快照而不是运行时读取，是因为本页要支持双击 `file://` 打开，而浏览器禁止跨目录 fetch。

方案文档见 [地图系统重构方案（实验版）.md](./地图系统重构方案（实验版）.md)。

## 运行

双击 `index.html` 即可，无需构建、无需联网（Three.js 已放在 `vendor/`）。

如果浏览器对本地脚本有限制，也可以起一个静态服务：

```powershell
python -m http.server 8099
# 然后访问 http://127.0.0.1:8099/
```

操作方式：左键拖拽旋转视角，右键 / 中键 / Shift+左键平移，滚轮缩放，点击地块或城市查看详情并高亮。右侧面板可以切换正射 / 低透视相机，以及描边、道路、里程标签、植被、村落、城市、玩家、**山体**、**河流**、**泉眼 / 小湖**、**云影（贴地）**、**云雾（高空）**、飞鸟、网格线共十四个图层的显隐；另有「山脉重掷」卡片（`重掷山脉` / `还原默认`，只换山脉分布，供策划对比不同效果，面板上会显示当前山脉种子号）、环境卡片（时段 / 季节 / 天气 / 自动轮播），「道路一览」卡片把五档道路各画一张顶视预览用于对照等级差异。**FPS 与网格统计的悬浮条固定在左上角**。

## 改参数就能改世界

世界的生成与外观集中在唯一的参数文件 `src/config/world-config.js`，策划改这一个文件即可，不需要动逻辑与渲染代码：

| 段 | 作用 |
| --- | --- |
| `terrain.landform*` | 地貌份额（水 / 低地 / 丘陵）、岛屿衰减、噪声采样尺度、类别平滑遍数 |
| `terrain.landuse*` | 用途份额（草地 / 农田 / 森林 / 花田）与其噪声通道 |
| `terrain.relief` | **山脉通道**：山脉份额 `ridgeShare`、噪声尺度（11 格）、城市距离衰减（`cityFadeStart/End`，2 → 7 格）、孤立山点软化遍数 |
| `terrain.relief.mountains` | **山体形状**：峰高包络 `peakHeight` / `ampScale`、孤峰比例 `loneScale`、簇级峰高增长 `peakHeightGrow`、脊带半宽与蜿蜒 `beltHalfWidth` / `beltWander` / `beltWidthJitter`、峰谷调制 `summitScale` / `summitFloor`、脊网 `crestStretch` / `crestSharp`、放射脊 `spurAmp`、岩台 `baseLevel`、轮廓收脚 `taperInner` / `taperOuter` / `outlineWobble`、**可见厚度下限 `footMin`**（v2.6，见「山体」一节）、山谷 `valley`、演示块 `demoMassif` |
| `terrain.relief.demoMassif` | 演示用的 4×5 手工山块（默认贴地图左下角，`col / row / w / h`）；优先级高于比例生成，但不计入目标份额 |
| `height` | 世界基准高度相关参数：岛屿衰减 `islandFalloff`、旧 `visualPeak`（保留兼容，已不参与地表高度） |
| `river` | **河道**：统一半宽 `width`、岸色带倍数 `wetScale / bankScale / floodScale`、避让倍数 `propsClearanceScale`、浅切槽 `channel.depth / widen`、支流参数、**穿山侵蚀 `gorge.depth/widen` 与 `pass.depth/widen`（`depth` = 核心开通度：1 表示整条水带完全开通）、覆写模式的路径偏好 `routeBias`** |
| `environment` / `weather` / `season` / `dayNight` | 环境系统：默认时段 / 季节 / 天气、天气预设（晴 / 多云 / 雨 / 雾）、季节预设、日夜轮转周期 `dayNight.cycleSeconds` |
| `palette` | 全部配色：地形、水面、树种、花、作物、岩石、房屋、城市、五档道路、**蜡笔描边参数**、**顶点色交融权重**、天空、底座 |
| `ecology` | 每种地形搭配的物种、密度、每格株数、成簇半径、道路避让距离、生长度影响 |
| `village` | 每城房屋数量、分布半径、尺度、成簇概率 |
| `road` | 五档道路的里数阈值、宽度、**路面材质与构件**（`surface` / `rail` / `curb` / `ruts` / `scatter` / `irregularEdge`）、桥与栈桥余量、**隧道洞口尺寸**、**磨损速率（默认 0＝不演示）** |
| `props` | 道具状况衰减速率、修缮增幅、破败色（默认 0＝不演示） |
| `ambience` | 云雾数量/高度/速度/透明度、**贴地云影**（层数/透明度/漂移速度/纹理重复/覆盖范围/网格步长/抬升高度/贴图边长）、飞鸟数量/半径/速度 |
| `lighting` | 半球光、环境光、方向光、补光、阴影、雾 |
| `resources` | 各地形的资源产出（药草 / 谷物 / 橡木 / 染料 / 石材 / 海鱼） |

地形份额是按**排名分位**切分的：先把所有格子的噪声值排序，再按目标比例分配类型。这样做的好处是实际占比与配置几乎一致，不会因为噪声分布不均匀而跑偏。HUD 的「地图状态与生成比例」面板会同时显示目标比例与实际格数，方便校对。

山脉走的是**另一条通道**：带符号的大尺度噪声（`terrain.relief.scale = 11` 格）× 城市距离权重。挑选范围是「非水 **且** 离城 ≥ `cityFadeStart`（2 格）」的格子，按噪声值排序后取最高的 `ridgeShare`（0.42）那一批。噪声尺度放大到 11 格之后波峰拉成长脊，山脉因此连成脉而不是一堆孤立小山包。单格山**不被清理**：它是合法的孤峰，由 `loneScale` 控制峰高；旧版的「孤立山点软化」会把单格山抹掉，已连同参数一起删除。

山格之间的连接是**六邻接**（仅角接触不算同一山系），山簇 ID 由 seed 与排序后的 tile key 集合哈希得到，因此在策划改动其中一格之后，其余格仍属于同一山系。山体的实际形状由簇级高度场统一给出：脊带、主峰与次峰、鞍部、冲沟、岩台、山谷、孤峰对不对称性都来自这一处，渲染层只做采样与上色。

这条通道的种子是可换的（`world.reliefSeed`，见下文「山脉重掷」）：换了它，山格分布与山体形态一起变，而地貌 / 用途两条通道不动。注意同一个通道值有两个消费者 —— 山格排名与丘陵 dome 高度（`hillAmp`），所以代码里把它读成两个数组（`ridgeVal` / `relVal`），只有一个跟着山脉种子走。

**平原与丘陵不再共用高度场**：平原高度恒为 0（完全平），丘陵只在**格内**做一个 dome（幅度 `hillAmp`、半径 0.76 格，到格边回落到 0），所以相邻地块之间不会出现台阶。地表高度只有一个查询入口 `world.heightAt(x, z)`，河流的浅切槽也叠加在里面（见下文「河流」）。

## 编辑器覆写与重建

世界生成、策划覆写与运行时状态彼此分离。覆写以稳定地块键组成稀疏数据，保存后以相同种子、配置与覆写重建会得到相同结果。当前支持的结构如下：

```js
{
  tiles: {
    "q,r": {
      terrain: "ridge",
      mountain: {
        style: "twinPeak",
        heightScale: 1.25,
        landmark: false,
        valley: "auto"
      },
      waterway: {
        mode: "mountainPass"
      }
    }
  }
}
```

`src/world/world-rebuild.js` 是纯逻辑事务：它依次构建世界、稳定山簇 ID、山体场、河流、道路、动态地块状态与派生规则，不触碰 DOM、Three.js、相机或 HUD。实验页启动和后续覆写都应走同一入口，避免两条构建链逐渐分叉。

页面加载后可从编辑器或调试环境调用：

```js
window.__hexLab.rebuild({ terrainOverrides: nextOverrides });
```

除显式地块键，覆写还支持**按地形批量命中的规则**（`match` 支持 `terrain` / `landform`）：

```js
{
  rules: [
    { match: { terrain: 'ridge' }, set: { waterway: { mode: 'mountainGorge' } } }
  ]
}
```

规则存在的理由是：山格是**生成结果**，「把所有山格设成峡谷」如果只能逐格列举 key，就必须「先生成一遍拿到山格、再回头覆写」跑两遍构建。优先级是**规则 < 显式 key**，即规则是默认值、显式覆写是最终值；规则也会计入覆写 revision，否则改规则不会让山体场与河网的缓存失效。

默认地图上有一条演示规则 `river.demoWaterway`（`{ enabled: true, mode: 'mountainPass', target: 'ridge' }`），它走的就是上面这条管道，用来直接看到「河从山口穿过」；`enabled: false` 即回到完全自然的河网。

## 山脉重掷（策划对比用）

山脉通道的种子独立于世界种子：`world.reliefSeed` 默认等于 `seed + terrain.relief.seedOffset`，传别的值就只换山脉。之所以能把种子拆开，是因为同一条脊状噪声通道被两个消费者读 —— 丘陵 dome 高度（`hillAmp`）与山格排名；拆开后 `hillAmp` 仍读世界种子，所以重掷山脉**不会顺带改掉丘陵起伏**。

页面上是右侧的「山脉重掷」卡片（`重掷山脉` / `还原默认`），面板显示当前种子号、山格数、山簇数，日志里也会写一条。种子来自**确定性序列**（计数器 × 大质数），不使用 `Math.random()` —— 看到喜欢的分布时把种子号记下来即可复现。

```js
window.__hexLab.rerollMountains();      // 下一颗山脉种子
window.__hexLab.rerollMountains(12345); // 指定种子（复现某一次结果）
window.__hexLab.resetMountains();       // 回到默认分布
```

重掷会走一次完整的 `app.rebuild()`：山格分布与山体形态改变，依赖山格的河流与道路随之重算，而水 / 草 / 田 / 林 / 花的占比与逐格分布保持不变（实测非山格的 `terrain / landform / height / hillAmp` 零漂移）。山格总数只会在演示块（`relief.demoMassif`，20 格）的范围内浮动：排名部分的格数是固定的，手工演示块是「谁还不是山就改成山」，它与排名结果的重叠格数会随种子变化。

应用级重建会释放旧图层的 GPU 资源，替换 terrain、mountains、rivers、springs 等表现层，并重建深度预通道、山体 LOD、Picker 与旅行模拟。它会保留图层显隐、环境状态、相机控制器和仍有效的选中地块；旅行中的玩家路径目前不会迁移，正式运行时需要在道路覆写后补充安全迁移规则。若后续编辑器允许替换 seed、地图尺寸或完整快照，也应在这个接口扩展参数与相机范围迁移。

```
  main.js                 装配入口与主循环
```

命名约定：每个模块是一个 IIFE，只向全局挂一个 `HexLab` 命名空间，不在全局散落变量，也不使用 ES Module。这与原项目「经典脚本 + 顶层共享」的组织方式一致，好处是无需构建、`file://` 可直接运行。

## 视觉风格

对齐手绘蜡笔插画风（参考《筑梦颂》与手绘平涂地图）：

- **统一平面 + 格内微起伏**：全部地块坐在**同一个基准平面**上（`surfaceY` / `cornerY` 恒为 0），地块之间没有台阶。平原格心高度恒为 0（完全平）；丘陵只在**格内**做一个 dome（到格边回落到 0），所以相邻地块之间不会出现台阶。山脉**不再抬升地表**，而是叠加在地表之上的独立模型（见下文「山体」）。实测丘陵只把格心抬起 3.83 单位，旧参数 `height.visualPeak`（1.9 × 格半径 ≈ 41.8）已不参与地表高度，仅作兼容字段保留。地表高度只有一个查询入口 `world.heightAt(x, z)`，河流浅切槽也叠加在里面。
- **真正的无缝**：同一个物理顶点在相邻地块里是**不同的顶点副本**，若颜色与法线各算一份，平地就会沿六边形边界露出色阶与明暗缝。因此顶点色与法线都按「世界位置 + 该处地块集合」统一计算，共享顶点上的颜色/法线数值完全一致（实测最大差 0）。这条是「不要分明的六边形」最重要的实现细节。
- **不同地形互相交融**：角点顶点的颜色取「压在该角上的 3 格」等权平均，于是色带在地块交界处整圈过渡；地块中心再按 `palette.blendWeights.center` 朝 6 邻平均色渗透，过渡因此从「只有一圈角点渐变」变成「格心就开始互相渗透」。注意**角点必须等权**：给自身更大权重、或把外圈并进来，三格就会各算一份，实测色差立刻回到 0.07~0.12，六边形色阶重现。
- **水陆基色族隔离（v2.5）**：上面那条「等权平均」对**水 / 陆**必须例外。压在同角上的 3 格里只要有 1 格是水，陆地那一份就被掺进 1/3 的水色（`palette.terrain.water = 0x8cbac8`，偏青蓝），格心还会再按 `cb/6` 掺一点 —— 肉眼就是「**贴着水的陆地基本色变成了蓝的**」。而「一片纯水该是什么颜色」本该由**画面深度**单独决定，不该反过来去染陆地。现在按**族**过滤：`sameFamily(t) = (t.terrain === 'water') === isWater`，角点只收同族邻居等权、格心只按同族邻居均分。过滤依据是**成员自己的属性**、与「谁在问」无关，所以同族地块之间仍然完全一致（无缝这条硬约束不破）；陆地网格与水网格本来就是两套几何、不共享顶点，岸线因此是一条真实的分界。实测 804 个水陆交界角、逐点与「纯陆地三格平均」对拍，**最大偏差 0**（对照组：把水格一起等权混进去，颜色差 ≥ 0.01 的角占 804/804，最大 0.354 —— 证明这条断言不是空转）。
- **「沿岸度 → foam」染色已删除（v2.6）**：族隔离只管住了「角点混色」，地表层里还留着**第二条**染色路径 —— 按「该格有几个水邻居」给陆地顶点掺 `water.foam`（`SHORE_LIGHTEN 0.16`）。它就是「陆地基本色发蓝」的直接来源，且违反「水色只能由画面深度表达」这条原则。现已连 `tile.shore` 字段、常量、累加器与 HUD 的「沿岸度」一行一起删除，并加了一条「死字段不得复现」的断言（实测 0 格仍带该字段）。⚠ 查这类问题时不要只查混色公式，要问「**还有没有第二条染色路径**」。
- **蜡笔描边（按结构/用途分级）**：只有**跨结构类**的边才画墨线 —— 陆|水、陆|岩、岩|水、城|其他 收边；草|林、草|田、草|花 之间不描边，改由「混色 + 边界过渡装饰簇」咬合（分级表在 `palette.outlineClass`）。早先的规则是「任一侧地形标记为 outlined 就画」，于是农田与花田的每条边都有墨线，整张图被切成一格一格。一条边只画**一条连续笔触**：沿边取一维平滑噪声，宽度、横向游走、浓淡都在**相邻段共享的站点**上取值，因此中心线连续、不会错开成两条断线；再叠一张「边缘毛糙 + 颗粒 + 孔洞」的笔触贴图，因此不是等宽 CAD 线（`breakRate` 保留为「断笔」选项，默认 0＝一笔到底）。
- **暖调高饱和配色**：橄榄绿草地、赭黄条纹农田、紫红花田、灰褐岩壁、砖红/紫顶小屋、橙红秋树、淡青水面、柔和天空渐变。
- **成片而非碎格**：噪声采样尺度放大到 5~9 格，再做两遍类别多数投票，区域因此连成整片；所有地表贴图都按可平铺方式生成（周期噪声 + 笔画环绕补画），不会在大尺度上留下网格接缝。
- **生态植被**：绿冠阔叶 / 秋色阔叶 / 针叶 / 灌木 / 花丛 / 作物 / 岩石七类，森林成簇、农田按行（行距由贴图周期推导，两者不会错位）、全部避开路面。
- **贴地云影（v1.6 改为贴合地形）**：以前整片「云雾」压在地表之上会让画面雾蒙蒙，于是默认关掉云雾、改用云影。但 v1.5 的云影是**比地图大 2.7 倍、悬在峰顶之上的水平面片**（`y = maxRise + 0.6`），压低到贴地视角时它会横贯整个画面、盖住树与屋，纹理被极度拉伸后排成一排排细线（用户反馈的「很多粘连的线」）。现在改成**贴合地形的网格**（逐顶点 `heightAt + lift`，约 90×64 段），贴图提到 512 并开各向异性过滤；两个环境层默认都不开，需要时在 HUD 里各自挑选。详见下文「v1.6」。
- **扁带的横向贴地**：路面 / 车辙 / 路缘 / 钢轨 / 蜡笔边线 / 枕木本质都是「沿折线铺的扁带」，过去三列顶点**共用采样点那一个高度**，只有中心线跟着地形走；8.8 单位宽的御道横跨陡坡时必然一边浮起、一边插进地形，掠射视角下就是悬空的细线。现在 `Ribbon.pushBand` / `pushCrossBar` 支持 `ground + maxDrop`：左右两列（枕木是四个角）各自落到地形上，并钳制在中心线 ±`road.conformDrop` 内；桥面 / 栈桥面 / 洞内路面传 `null` 保持原高度，不会被摊到谷底。
- **沙盘感**：地图坐在一块底座上，保留方向光与阴影（用户要求保持立体感，后续还要做日夜与季节）。

## 山体（微缩沙盘）

地表网格每格只有「格心 + 中环 + 6 个共享角点」13 个顶点 —— 这是「地块之间没有台阶」的前提，也因此**无论把山抬多高，形状永远是缓丘**。所以山体是**叠加在地表之上的独立几何**。

**形状只有一个真源：`world/mountain-field.js`。** 渲染层（`render/mountain-layer.js`）只做三件事：采样、建网格、上色 —— 它里面没有任何「每格的形状」概念。

```
H(x, z) = 包络 × 轮廓掩码 × ( 岩台 + (1 − 岩台) × 脊带 × 峰高 × 脊网 )
```

### v2 为什么换掉「椭球穹丘」（2026-09-18）

v1.9 的写法是 `dome = 1 − ru² − rv²`（整簇一个椭球穹丘）+ 脊状噪声**向下雕刻**。实拍反馈「山脉太平了、没有起伏」，量化之后根因有三条：

| 实测指标 | v1.9（椭球） | v2（窄脊带） | 参考图 |
| --- | --- | --- | --- |
| 体量比（峰高 / 半高半径） | **0.14** | 2.51 | ≈ 1.0 |
| 脊状噪声对造型的贡献 | **±13%**（`1 − 0.5×(1 − rg)` 只在 0.67~0.93 之间飘） | 主要项 | — |
| 单格孤峰明暗图 | 一圈同心环（光滑圆包） | 6~9 条放射脊 / 冲沟 | 放射沟 |
| 最大山簇尺寸 / 峰高 | 34.8 × 18.2 格 / 1.30 格 | 14.7 × 5.3 格 / 1.43 格 | 2~4 格宽窄带 |

- **椭球的几何方向就是错的**：`1 − ru² − rv²` 是「倒扣碗」（顶平、根陡），山的横剖面必须是**凹形**（顶陡、根宽）。所以换成 `belt = (1 − nd)^flankExp`，`flankExp 1.45 > 1` 才有裙摆。
- **它只在几何中心有一个极大值**，脊状噪声又只能做减法（`shape ≤ dome`）⇒ 每簇最多一个峰，永远长不出「峰—鞍—峰」。
- **噪声的实测值域不是满量程**：`ridgedPerlin2` 的 min/p05/中位/p95 = 0.11 / 0.34 / 0.62 / 0.87。直接当系数用只剩 ±13% 起伏；v2 用 `crestSharp 3.0` 把它拉到有效量程（中位压到 ~0.24、保住脊顶 1.0）。

### v2 的形状（逐项）

- **脊带**：山体是一条沿簇主轴延伸、横向**蜿蜒**（`beltWander`）的窄带，半宽 `beltHalfWidth: 1.15` 格（≈2.3 格宽，正好落在「单格地块也能单独撑起一座山」的量级）。半宽沿走向抖动 `beltWidthJitter`，两端收口 `beltEndTaper`。主轴由簇内格心 PCA 给出（单格簇退化为 +X，确定性）。
- **峰高沿走向调制**（`summitScale 2.2` / `summitFloor 0.32`）：这是「峰—鞍—峰」的来源，也是参考图里「基安蒂山脉」那种连绵脉的关键。实测最大簇：脊上 5 个局部极大、最深鞍部 2% 峰高。
- **脊网**（`ridgedPerlin2` + `crestStretch 2.4` 沿走向拉伸）：`|n| → 0` 的等值线是**曲线**，天然没有格点偏好；它是「脊线与冲沟落在哪」的判据。
- **放射脊 / 冲沟**：把「到脊线的横向距离」按噪声调制（`spurAmp 0.46`）⇒ 等值线成**星形**，脊与沟沿坡面放射。单格 / 短簇用**角向**取样 —— 在噪声空间里 `perlin(cosθ·k, sinθ·k)` 天然以 2π 为周期，所以不需要另写一个周期噪声函数。实测最高孤峰：放射脊 17 条、环向起伏 63%。
- **低岩台**（`baseLevel 0.20`）：整簇的底盘，保证山格本身是一块起伏的岩石高地（而不是悬空的脊带），同时又足够低 —— 实测最大簇格心场值 31%~82% 峰高、**峰:底 = 3.23**（v1.9 的椭球把整簇抬到 63% 峰高，这就是「平台感」的来源）。
- **轮廓掩码**以「到簇边界折线的**有符号**距离」收脚：内侧 `taperInner: 0.45` 格开始降、外侧 `taperOuter: 0.30` 格归零，再叠一层低频噪声抖动（`outlineWobble: 0.22` × `outlineWobbleScale: 1.6`）。**外侧 > 0 就是「允许山脚漫出簇边界」** —— 接触线因此是一条噪声曲线，而不是格边折线。实测 282 / 282 条簇边界边外侧仍是山体。
- **逐簇归一化**：`body = 脊带 × 峰高 × 脊网` 是三个各自 ≤1 的噪声相乘，极大值不落在同一点 ⇒ 裸场峰顶只有包络的 0.6~0.8（v1.9 文档里那句「实测峰值只到包络的约 0.74」就是这么来的，雪线因此吊在够不着的地方）。v2 在编译时量一次实测峰顶、把整簇场缩放回去，于是 **`peakHeight` 就是「这座山有多高」**，与任何噪声参数解耦（实测 18 簇：maxField 恒等于 `amp`）。

### 山脉的分布（一起收窄成窄带）

「起伏通道」的噪声从 `fbm2` 换成了 `ridgedPerlin2`（`src/world/hex-world.js`）。原因是实测出来的：

- 山格 = 「起伏通道的高分位集合」，所以它的**形状**完全由这条通道的极大值长什么样决定；
- `fbm2` 的极大值是**团块** —— 只调 `ridgeShare`（0.10 → 0.42）平均簇宽都从 3.6 涨到 6.1 格，长宽比一直在 1.3~2.0，**永远收不出窄带**；
- `ridged` 把 `|n| → 0` 的等值线翻成极大值，那是**曲线** —— 取 top 22% 得到的就是蜿蜒窄脊带。

实测（`ridgeShare 0.22` / `scale 11`）：山脉占陆地 **16.8%**（v1.9 是 32.2%）、18 簇、平均簇宽 2.9 格、最长 14.7 格，6 片孤峰。连带影响：河源 7 条、隧道 7 格、桥 14 格，都在。

### 演示用的大片山脉（`relief.demoMassif`）

给策划看「一大片山脉长什么样」用的**手工块**：偏移坐标（odd-r）一块 4×5，默认贴地图左下角
（`col −11, row 5`，世界中心约 (−351, 231)，离城 4 格）。它放在「按排名切分」之后 ⇒ 手工优先于
比例生成 —— `ridgeShare` 不保证任何具体位置，而「左下角要有一大片」只能显式指定。

- 只跳过**地图边界水格**（`border`，海岛轮廓外圈），块内普通水格改成山格 ⇒ 块内永远是一整片、
  **连成 1 簇**（实测 20 格全成山、1 簇，其中 18 格是新改建的，含 1 格沿海水格 → 做出「山体探进海里」
  的样子，正是参考图里那种海岸山体）。
- 它**不计入**目标份额，也在「生成的山脉分布是窄带」这条断言里被剔除 —— 否则那条断言会退化成
  「演示块有多大」的间接度量。
- 配套两条形状规则（对**生成出来的**山脉同样生效）：
  · `beltWidthGrow 0.85`：`hw = max(beltHalfWidth·hexSize, 0.85 × extV)`。脊带随簇宽增长，否则
    20 格的大块会读成「一条薄脊 + 一大片岩台」。单格簇 extV ≈ 1 格 ⇒ 增长项打不过下界，
    **单格山形态完全不变**。
  · `peakHeightGrow 0.32`：`amp ×= 1 + 0.32 × clamp((簇格数 − 5) / 12, 0, 1)`。簇越大峰越高 ——
    否则「10 格宽、1.3 格高」还是个缓丘（实测体量比 0.79）。只对 **≥ 6 格**的簇生效。
- 实测：演示簇 22 格 / 峰高 **1.66 格** / 脊带半宽 **4.21 格**（下界 1.15）/ heightGrow 1.32。

### 山谷：山脊对面的一条沟（`mountains.valley`）

参考图里很常见的构造：一条脊线旁边跟着一条同向的沟。做法是在**脊带局部坐标**里，沿一条与脊线
平行的中心线挖高斯槽（谷底 = 当地高度 × (1 − 谷深)）：

- **单格与连续地块都可能出现**，是否出现由「簇号 + 种子」的哈希决定（`rate 0.55`）⇒ 确定性、可复现
  （实测 9 / 17 簇带谷：单格 2 + 连续 7）；
  ⚠ 判定必须是**三态**：`'on'` / `'off'` 是策划的显式决定，`'auto'` 与缺省是「没指定」、要交回 `rate` 判定。
  曾经把 `plan.valley === 'off' ? false : (plan.valley === 'on')` 的结果当三态用 —— `'auto'` 也算出 `false`，
  与「显式关闭」不可区分，`rate` 分支永远走不到，于是**默认世界 17 簇一个谷都没有**。
  另一条：`stableHash` 必须是**数字**（`Rng.hashInt` 内部是 `x | 0`，传字符串会被压成 0，
  所有簇共用一个哈希 ⇒ `rate` 退化成「全有或全无」）。
- 单格簇的脊线退化成一个点（`endCore = 0`），所以另给谷一个朝向 `valleyAz`（也由哈希给出）⇒
  **单格地块的山脉 / 山峰可以是不对称的**（「与山脊相对的山谷」）；
- ⚠ 刻在**合成后的高度**上而不是只刻脊带：只刻脊带时谷在坡脚几乎看不见，实拍读不出「沟」；
- 验收必须用 **A/B 对拍**（关掉 `rate` 再编译一次、在**同一坐标**上比）：单点采样分不出「谷」与
  「脊线自身的蜿蜒」—— 实测无谷的簇两侧就能差 2.04 倍。实测带谷簇的谷心线被压低 **30%+（最强 51%）**，
  而**镜像侧只差 6%**（全部来自归一化系数的微差）。

以下三条是**设计红线**，换实现也要守住：

- **红线①：高度只有一个来源，且只依赖 (x, z)**。同一世界坐标只有一个值 ⇒ 相邻格、跨格、跨簇一律同高，裂缝在机制上不可能出现。实测：3210 个采样点场值恒 ≥ 0、低于地表 0 个；**0 个重复位置顶点**。
- **红线②：山脚不低于地表**（表面高度一律走 `MountainField.surfaceAt` = `max(地表, 场按水流侵蚀权重插值回地表)`）。否则丘陵微起伏与河床浅切槽会让地形从山脚里穿出来，落地墙还会变成朝上的反墙。⚠ 这里**不能**写成 `max(场, 地表)`：那是「山壳盖住一切」，会把穿山河段已经开好的切口重新盖回去（见下文「河流」与方案 §15.21）。实测各 LOD 级表面超差 0、墙脚超差 0、悬空自由边 0、退化面 0。
- **红线③：壳体只落在轮廓线上**。「场值归零的那条等值线」就是山脚接触线，沿线立竖直墙落到地表。因此**自由边只剩贴地的墙底边，空中没有任何敞开的边** —— 这就是「表面闭合」的全部含义。实测各级翻面 0、索引越界 0、悬空自由边 0。

拓扑与建网格：

- **共享三角格网格器**：整簇按 `step = hexSize / detail` 铺一张网格、逐点取样场，相邻格**复用同一批格点**，所以格子感从结构上消失。同一簇内按位置焊接（1/512 单位量化）。表面三角按 `ny ≥ 0` 定向（高度场不会悬垂，判据只有这一条）；只有竖直落地墙用「背离格心」的判据。
- **孤峰（单格成山体）**：6 邻无山的山格标记 `isLone`，峰高乘 `loneScale: 0.85`（实测孤峰最高 26.87 vs 最大簇 31.38 单位）。旧版那条「孤立山点软化」循环已删除，现在实测 63 格里 6 片孤峰。
- **顶点色**（`palette.mountain` + `rockBands`）：岩带按归一化高度 `y / refH` 做两段 smoothstep 混合（带抖动）；**冲沟压暗** `creviceShade` 用采样网格的**凹凸**判定（某点比 4 邻平均低就是沟）—— 不重算任何噪声，天然跟着形状改动走；再叠**雪带** —— 雪线 = `refH × snowRatio`（0.66），沿主轴拉伸的噪声让雪成为**顺坡的条带（残雪）**而不是一圈整齐的环，`snowFade` 控制渐变宽度。最后**山脚往「脚下地块的地表色」过渡**（`footBlend`）。实测 19 / 63 格在雪线以上、最细一级近雪色顶点 1633 个。
  ⚠ `refH` 取**本簇实测最高峰**（归一化之后它恒等于 `amp`），所以每条山脉都有自己的雪顶。
- **山体占位**由 `MountainLayer.occupancy(world)` 统一对外提供：植被、房屋都问它一次，才不会有杉树从山体里穿出来；山格只长岩石，且按 `occ.thickness(x, z) < ridgeScreeClearance` 落在**山脚之外**。实测落在山体格内的道具 0 个。
- **不做轮廓线**：山体不加墨线描边（按用户决定），剪影靠分带顶点色的块面感 —— 山体是独立网格、不与地表共享顶点，加描边一定会在地表上多出一圈闭合线。
- **场只编译一次**：`plan()`（渲染）、`occupancy()`（植被 / 村落各一次）原本各自编译一遍场 —— 实测同一份世界被编译 **4 次**、白花约 76ms。现在 `MountainField.compile` 按 world 用 WeakMap 记忆化；**就地改配置数值时要显式调 `clearCache()`**。

## 山体 LOD（按缩放切采样密度）

高度场是 `(x, z)` 的**纯函数**，所以「同一片山体用不同间距采样」得到的一定是同一个地形的不同精度版本 —— 这是 LOD 能做得这么轻的根本原因。

- **块 = 山簇**。相邻簇即使级别不同也不会裂：簇边界处场值恰好归零、落地墙把边界压到地面，接缝处两者都在地面上 ⇒ **结构上没有 T 型缝**，不需要缝合带 / 裙边。
- **判据用屏幕像素密度，不是裸距离**：`detail ≥ hexSize / (targetPxPerStep × 每像素世界单位)`。本项目有正交 / 透视两种相机（正交是默认档，它没有距离衰减），拿裸距离做判据在正交下是错的。
- **滞回阈值取相邻两级的几何平均**（对数中点）`√(当前 × 邻级)`：变细要求需求超过 `√(dc×df)×(1+h)`，变粗要求低于 `√(dc×dk)÷(1+h)`。⚠ 早期写法拿「当前级自己的 detail × (1+h)」当阈值，它落在自然切换点的**错误一侧**，等于滞回完全不生效（实测两个方向都会跳）。
- 相机静止时整个 `update` 直接短路；最短重算间隔 `updateInterval 0.12s`。
- 级别表 `lod.details: [12, 8, 5, 3]`（细 → 粗，步长 1.83 / 2.75 / 4.40 / 7.33 单位）。`lod.enabled: false` 时锁在 `details[0]`（最细一级）。

实测（本图 17 簇，含演示块）：

| 级别 | 步长 | 三角形 | 块数 |
| --- | --- | --- | --- |
| 12 | 1.83 | 93224 | 17 |
| 8 | 2.75 | 43190 | 17 |
| 5 | 4.40 | 17968 | 17 |
| 3 | 7.33 | 7388 | 17 |

- **性能**：四级全部预建（一次性 637ms），内存约 10MB；默认视角（正交、距离 1250）判据算出需求 ≈ 3，实际渲染 **17968 / 93224 = 19.3%** 的三角形。
- **它省的是 GPU 顶点处理，不是建造耗时**：要预建所有级别，建造时间是各级之和（几何级数，粗级几乎不要钱）。当前地图规模下这不是瓶颈（分层耗时见下），**真正有收益的场合是编辑器产出的大地图**（几千个山格时总面数上 50 万、阴影通道也变重）。所以默认开、可一键关。
- 已知边界：块粒度是「一个山簇」，所以一条超长山脉内部无法混级。若编辑器将来产出超长单簇，再按 ~6 格分段 + 一圈裙边处理（方案 §15.17）。

分层建造耗时（软件渲染 / Swiftshader，535 格）：地形 384ms / **山体 1248ms** / 河流 11 / 描边 10 / 道路 37 / 植被 31 / 村落 12 / 城市 10。

## 水面与「画面深度过渡」

河 / 湖 / 海现在是**同一套水**：一个水平面（`water.level = 0`）+ 一张被切下去的水下地表。两者含义完全不同，必须分开建：

- **水下地表（bed）**：水格的地表由 `world.heightAt` 给出，是两项相乘 ——
  · **敞水深度场（v2.6 改成连续离岸距离）**：`depthShallow 0.016` → `depthDeep 0.09`，跨 `depthRamp 2.5` 个**格心间距**过渡；自变量是**到最近陆地格六边形的连续距离**（不是「离岸多少格」这个整数）。为什么必须连续：水深驱动下面的画面深度过渡，而旧写法按整数格距分级 ⇒ **全图只有 3 个水深档位**（0.352 / 1.003 / 1.654），相邻水格最多差 40% 的过渡量，过渡把它们原样放大成**一块块硬边多边形**（用户截图里的色块）。现在在格心处与旧公式**逐值相同**（ring-k 的比值仍是 (k−1)/2.5），但点与点之间连续：实测「到最近陆地格距离 × 岸坡因子」的暴力对拍 1292 点**最大误差 2.2e-16**，同一离岸档位内水深极差 0.297（旧版 0），共享边跨格差 0.0010。
    梯度用 smoothstep 收放（`u²(3−2u)`）：在「贴岸浅滩 → 斜坡」与「斜坡 → 深水」两处斜率都归零，于是**深度的一阶导也连续**，水面上不会留下一条条等深线。平台（深度不变）只允许出现在贴岸那一圈（离岸 ≤ 内切圆半径）—— 实测 18012 个采样点里 1642 段平台**全部**贴岸。
  · **岸坡因子**：0 在岸线上、`shoreRamp 0.7` 格内升到 1；只在**临陆的格边**上量距离。实测：水/水共享边 0 处非零，岸线处为 0（唯一例外是 **5 处河口**，那里被河的浅切槽切下去 2.20 —— 本来就该凹）。
  · ⚠ **地图外按开阔水域算**（v2.6）：旧版把「取不到邻格」也算成岸线，于是海底在沙盘边缘抬回水面 —— 外缘一圈水莫名变浅发亮、水与海底还共面。实测外缘 182 个格边采样点高度**全部 < 0**（最高 −0.40；修前 182 个全为 0）。
  · ⚠ **海底不加格内微起伏**（v2.6）：`innerRelief × maxRise` 实测 1.25 单位，而水深只有 0.35 ~ 1.48 —— 旧版给水下地表也加这层起伏，**272 / 948 个中环顶点被抬到水面之上**（最高 +0.997），海底在整片水面上穿出一圈圈硬边格子斑块，深度过渡也读到一堆逐格噪声。现在这层起伏**只给陆地**，海底形状交给连续距离场（实测水下地表 2054 个顶点最高 y = 0，高于水面的 0 个）。
  ⚠ 更早的「每格一个碗」写法（v1.9 之前）：碗底的 0 落在该格**全部六个角点**上，连深海中央也是 0 ⇒ 整片海变成一格一个洼的六边形凹凸纹。角点只有一种情况该是 0：这个角点**真的踩在岸线上**（三格里有陆地）。
- **水面**：一个严格水平面（实测 2054 个顶点全部落在 `y = 0`），高度只由 `config.water.level` 决定，与地形完全解耦。**水面顶点色是一个常数**（v2.6 起纯水只用基色：实测 2054 个顶点里除河口湿岸 8 个外**全等**；旧版把 ±30% 的大尺度手绘斑驳也铺在水上，读成「水面深浅不匀的斑」）—— 深浅只由下面的深度过渡给出。
- **画面深度过渡（`render/water-depth.js`）**：水面网格本身是平面，它凭什么读出「水有多深」？靠一张**半分辨率的深度预通道**（只画地表 + 山体，水面自己不在里面 —— 否则「地表深度」恒等于水面深度、差值为 0），水面材质在片元里比较「本片元深度」与「该像素处地表深度」：

  ```
  fragViewZ = vpViewZ(gl_FragCoord.z)          // 窗口深度 → 视空间 z（相机前方为负）
  bedViewZ  = vpViewZ(深度图在该像素的值)
  dz = (fragViewZ − bedViewZ) × 1/|视线方向 y|
  t  = smoothstep(clamp(dz / depthFade, 0, 1))
  颜色压深 = mix(原色, 原色 × depthTint, t)      不透明度 = mix(depthAlphaMin, 1, t)
  ```

  差 ≈ 0（岸边、水线）⇒ 水面几乎透明、透出水下地表，岸线自然收边；差 ≥ `depthFade` ⇒ 不透明并压深，读作深水。**「水」与「地」之间因此不再是硬边，而是一段由真实几何深度驱动的过渡**，河 / 湖 / 海 / 泉共用同一套（河面与河中泓两个材质也一起注入）。
  · ⚠ **两边都必须在视空间相减**（v2.5 修正）：窗口深度是非线性的，「每 1 单位窗口深度差 = 多少竖直水深」**逐像素**不同（取决于该像素到相机的距离）。旧实现用一个「相机到水面平面的中心距离」算出全局系数 `uDepthPerUnit`，于是偏离视线中心的像素会被判成更浅、相机高度 / 俯角一变整片水就变深变浅。现在两边都用 `near/far` + 正交标志还原成 viewZ 再相减（`vpViewZ` 与 three 的 `orthographicDepthToViewZ / perspectiveDepthToViewZ` 同一套约定，直接写在注入片段里以免依赖该材质是否 `#include <packing>`），乘 `1/|cos|` 折回竖直水深。**同一个世界点在任何视角下得到同一个 t** —— 实测同一水面像素跨 6 组位姿（正交 / 透视 × 俯角 × 视距）的色差从量级 100+ 降到 **0.4 / 0.6 / 0.7**（关雾后）。
  · 相机有俯角时，沿视线量到的深度差要除 `|cos|` 才能折回竖直水深，`uInvViewCos = 1/|视线方向 y|` 是**唯一**的视角相关量（它只随俯角变，不随视距 / 像素位置变，实测 1.533 / 1.533 / 1.911 / 1.533 …）。
  · ⚠ **不要再加第二个视角相关项**（v2.6 试过并删除）：曾经按 Fresnel 直觉加过一条「视线越平、水面越不透明」（`t = max(t, gate(|视线方向 y|))`，区间 `[0.08, 0.35]`）。写完时曲线、端点、6 条断言全绿，但**同姿态、固定像素集的 A/B** 显示它对画面的真实影响只有 **0.04%**（默认整图视角）~ **7%**（最平视角）—— 因为它的生效区间（`|视线.y| < 0.35`）整个落在 `t` **已经饱和**的区间（`viewCos < 0.42`）里：`dz = 水深 / viewCos²`，最浅水深 0.35 单位，`viewCos < 0.42` 时 `dz` 就已超过 `depthFade`，`t` 恒为 1，`max` 抬不动它。代码已全部删除，`water-depth.js` 与 `config.water.depthFade` 两处都留了「不要再加这一类项」的注释与量化理由（详见方案 §15.24）。
  · ⚠ **不要让 `t` 在屏幕上分块**（v2.6 修，详见方案 §15.24）：深度纹理在 WebGL 里**只支持 NEAREST 采样**，而预通道是**半分辨率** ⇒ 水面片元在屏幕上**每 2×2 像素**采到同一个 texel，`t`（进而深浅与不透明度）一块一块地阶跃。远看就是一条**水平、固定在屏幕位置、平移场景不动**的「分界线」（即用户截图里那条：逐行亮度实测奇数行 ≈ 118 / 偶数行 ≈ 170）。扫 `depthResolution` 0.5 / 0.75 / 1.0 ⇒ 行奇偶差 **35.94 / 10.51 / 0.42**，与深度图的 texel 格严格同步。修法是在水面片元里**手动双线性**：取相邻 4 个 texel、各自用 `vpViewZ` 还原到**视空间**再加权（窗口深度非线性，不能先插值深度值本身），背景 texel（`depth = 1`）权重置零后重新归一化，四个都无效时回退最近邻；`config.water.depthFilter` 留了 `'nearest'` 作对照档。实测行奇偶差 **35.94 → 0.21**，切回 `nearest` 的对照组 **18.05**。⚠ 采样步长必须用**深度图自己的**尺寸（`1/640 × 1/400`），不能拿「主画面 → UV」的 `uDepthTexel`（1/1280）顶替 —— 半分辨率下两者差一倍，会把双线性权重算错。
  · UV 换算要用**绘制缓冲尺寸**（`gl_FragCoord` 的单位是它，不是 CSS 像素），并且本模块比 `sceneKit.resize()` 先创建，所以尺寸**每帧自检**（否则会拿到 canvas 默认的 300×150，建出一张 150×75 的深度图）。
  · 深度贴图用 24 位（`UnsignedInt`）：16 位在 `far ≈ 4000` 时每级 ≈ 0.06 单位，而过渡区间只有 2 单位，会看出台阶。
  · **实测对拍**（俯视相机、射线竖直 ⇒ 深度图读到的就是该水格的水下地表）：最深的水格真实水深 1.482 / 量到 1.46~1.52；浅滩 0.352 / 量到 0.28~0.36（半分辨率 + 手动双线性采样，逐次有 ±0.06 抖动）；深浅在同一套尺度下被区分开。⚠ 通道读的是**渲染网格**的水下地表，所以「把海底形状做对」比「把公式写对」更重要 —— 下一条正是踩在这里。
- **顺带删掉了一处重复逻辑**：顶点色里原来还有一条「浅水带」（按 `distToLand / 3.2` 把水面朝 `water.shallow / water.foam` 提亮）。它看上去也在做「近岸浅、远处深」，但**必然是一格一格的** —— 同一个水格上，格心顶点的权重是「本格 + 6 邻」、角点顶点是「压在角上的 3 格」，两套权重算出的 `distToLand` 平均值不同，每个六边形内部都会有一圈色阶，实拍就是水面上的**蜂窝纹**。水深现在由几何唯一给出，这条就删了。

## 河源水体（泉眼 / 小湖）

河流原本是一条**和别处同宽的水带凭空开始**。v2.5 在河源处补上了「源头」：`world/river-builder.js` 在河源顶点附近选一格刻一个**碗**（由 `world.heightAt` 叠加 `tile.springRefs`），全图统一水位的水面覆盖上去，于是河源变成一个泉眼或小湖。

- **凭什么在数据层就能成立**：水面是**水平的**、水位与海 / 河是同一个值，所以湖口不会有台阶；碗只**往下切**（`h = min(h, -depth)`），「水面永远在最上层」这条不变量自动成立。
- **三条硬约束**（都来自已有不变量）：① 碗心从河源顶点朝「最开阔的那一格」的格心退 `pullback`（不落在顶点上，也不伸进山壳）；② 半径保证够不到**相邻的共享角点**（实测裕量 0.21 格），否则同一物理角点会算出两个高度 ⇒ 裂缝 —— 而且**共角的三格都要记这份下切**；③ 避开山格（会被山壳盖住）与水格（那里已经有水），共角三格都不可用就不放，计入 `springSkipped`。默认世界实测：**5 处水体（3 湖 / 2 泉）+ 1 处跳过 = 6 条河**，全部有交代。
- **碗与水片是两个尺度**（config 的 `basin` 与各形态的 `water`）：碗半径由**地表网格的分辨率**下限决定，不是美术喜好 —— 每格只有 13 个顶点（格心 + 中环 + 六角点），碗太小就一个顶点都压不到，网格解析不出盆地。实测碗半径 0.32 格时水面片外圈被地表**顶穿 33/45 条竖直射线**（解析式 `heightAt` 在那时是对的，所以只有「打到网格上」才看得见）；调到 0.72 格 × 水片比例 0.62/0.46 后**顶穿 0 条**，只有 2 条落在线上的山脚（容差内）。
- **岸线不是正圆**：`SpringLayer.shoreRadius` 用两个整周期谐波把半径扰动 ±10%（首尾闭合），否则一个正圆贴在地表网格上读起来像「画上去的圆盘」。实测每片 40 个方位的外圈半径比 0.900~1.096。
- **涟漪**：水面片是极坐标圆盘（`SEG = 40`、`RINGS = 4`），UV 的 `v` 轴 = 归一化半径，于是滚动 `offset.y` 就是一串向外扩散的涟漪，不需要写着色器。贴图 `Textures.rippleTexture` 在 `v` 上取整周期（回绕不留缝）、方位向加相位抖动（免得读成靶心），幅度刻意压到 ±13/255 ≈ 5%（第一版 7 圈 ±13% 在泉眼上就是个同心圆靶心）。水面材质进深度过渡的注入列表 ⇒ 深浅与海 / 河同一套规则。
- **「融合地块」的那一圈**：水面边缘往外 `wetBand × 碗半径` 内把地表朝 `river.bedTint` 靠拢（水面边缘最湿），再叠一点 `water.foam`；碗内的碎石与湿生灌木由 `props-layer` 撒在水片外圈（半径从 `waterRadius` 起算），道具与**道路**都按 `springAt()` 避让 —— 穿过水面的路段抬成桥面（否则路会跟着 `heightAt` 沉到水面以下，视觉上就是「路扎进湖里」）。
- ⚠ **两个渲染层的坑**（都留了回归断言）：① 一个几何里装多片圆盘时，索引必须带上每片的**起始顶点号**，漏掉就会把第 2 片之后的所有三角形接到第 1 片的顶点上（实测竖直射线只有第 1 片打得中）；② 判「水面上有没有别的面」要用**线段**到碗心的距离（道路采样步长约 7 单位，与水面片直径同量级，只看采样点会漏判）。

## 河流（权威中心线、水平水面与穿山切口）

参考图里的河是**地块与地块之间的边界**：地块落在河的哪一侧、哪个聚落临河，都有玩法含义；穿格心的河会把地块从中间切开，地块语义就没了。所以河流严格走六边形的棱（`world/river-builder.js`）：

- **顶点图上的寻路**：把所有地块的 6 个角点按位置去重建成**顶点表**，沿棱把顶点连成图 —— 于是「走一条棱」恰好就是「跨过一条格边」，从根上避免河斜切进格内（旧版是「tile 路径 + 取中点」，一旦方向映射写错就会取到镜像的那条边，出现 3.279 格的斜向直线段）。河源取「融雪线以上最高的角点」里彼此相隔足够远的几个，实测 5 条主河全部从山地 / 丘陵出发。
- **势能场保证必定入海**：先算「每个顶点到海面在图上要走几步」（BFS），再叠一层噪声；每步只能走到势能更低的邻点，而**噪声权重 `meander = 0.45 < 1`**，所以每一步势能都严格下降 —— 既不会绕圈，也不会停在田中央（旧版靠有限次「翻坎」逃洼地，是概率性的）。实测 5 条主河的去向是 入海 ×4 + 汇流 ×1。河会**绕开城市格**（否则水带会被城市广场模型整片盖住）。
- **汇流 = 撞上别人的顶点**：下一步落到别的河已经走过的顶点即为汇流，本河并入、下游共享同一水道，不需要第二套渲染规则。
- **水面严格水平，且与海面同一个水位**：整张图只有一个水位 `config.water.level = 0`（= 基准平面 = 与陆地齐平），河 / 湖 / 海共用。旧版把水位钉在「这条棱自身的岸高」上，水面会跟着地形爬坡；中间一版又给河单独取 `格距 × 0.005`（0.110），结果**河口比海面高 0.11 —— 河入海处有一个台阶**。现在两者同源，台阶不存在。
- **统一河宽**：整条河同宽、所有河同宽、支流与干流同宽。`river.width = 0.16`（× 格距）即半宽 3.52 单位；实测全线 3.52 ~ 3.52 单位（**1.000×**），首尾差 0.000000。参考《文明 6》：河道宽度基本恒定，不做「河源细、河口粗」的锥形收放（旧版由 `prog` 与汇流通量 `flowT` 叠出 3.1×，再叠上支流与干流的差异，全图到过 **5.1×**，就是「河宽很丑陋」的直接成因）。
- **浅切槽**：水面要看得见，就必须让河线附近的地表低于水面。`channelOffset(x, z)` 把临河格的顶点按「到河线距离」下切 `channel.depth × (1 − r²)`（`r = d /（半宽 × channel.widen）`），槽在水带之外回落到 0，所以**切槽不侵入格心**（实测临河平原格心最大高度 0.000000）。地表高度只有一个入口 `world.heightAt`，切槽叠在里面，因此共享角点天然一致、相邻地块不会裂缝；下切处还加了一个 `ceiling = waterY − 0.02` 的钳制，保证水面永远是最上层可见面。
  实测：**209 个临河角点**被切到水面之下、**134 条临河边中段**同样低于水面（角点只覆盖格边两端，中段由中环顶点承载）、横剖面 102/102 在河线处低于水面、98/98 在半宽处仍在水下、39/39 在槽外回到基准平面。
  ⚠ 判据必须是「**本格临河 或 本格是临河格的邻居**」（`riverNear`）：格边角点由三个格共享，只按本格判定会在角点上漏切，河面拐角会被顶出一条薄墙。
  ⚠ 采样点要从**角点朝格心**退 6%（≈1.3 单位）：退多了会走出槽（退 6% 时离格边还有 1.1 单位，而槽半宽 4.4 单位）；方向也不能反 —— 从格心往角点退 6% 是退到离角点 20.7 单位的地方，早就出槽了。
- ⚠ **为什么不做「岸唇」**：曾把剖面做成「满深 → 回升越过水面 → 岸唇回落」，想让水带的几何边缘被岸埋住。实测只有约 **27%** 的水带边缘能达到水面之上 —— 地表网格在格边附近**只有角点顶点**，一格以外的地形全靠线性插值，**抬到水面之上的岸唇没有顶点去承载**，渲染出来依旧是水带边缘浮在地表上。因此回退成「几何只负责让水下陷，两岸交给颜色」（河床混色 + 湿岸带）。这条约束写在 `channelOffset` 的注释里，避免以后重试一遍。
- **岸色带全部按水带半宽缩放**：`wetScale / bankScale / floodScale` 是「水带半宽的额外倍数」，不是绝对半径。实测湿岸 1.58 / 河床 3.87 / 漫滩 7.74 单位（半宽 3.52），三层按「湿岸 ⊂ 河床 ⊂ 漫滩」层层收束。旧版写死绝对半径（6.6 / 10.1 / 17.6 单位）不随水宽缩放，窄段就成了「一条细线套一圈 11.5 倍半宽的巨大深色晕」、宽段几乎没有岸 —— 这是「河宽很丑陋」的另一半成因。植被与房屋的避让距离同理（`propsClearanceScale`）。
- **支流**：从内湖 / 内海湖岸出发（候选 39 处，实测生成 3 条），走同一套势能场，撞进已有水道即并入；**每生成一条就把它并进网络**，所以水系自然长成树枝状。支流起点彼此拉开（最近 1.73 格），不会并排出发；支流也会重进最近河段索引，因此同样有湿岸、避让与切槽。
- 渲染上复用 `render/ribbon.js` 的扁带：水面 + 中泓深色带 + 岸线暗边（`render/river-layer.js`）。`river.renderSmoothing` 只做表现层的圆润化，不影响逻辑上的格边路径；水纹与海面共用同一张贴图与同一 UV 周期，滚动 `offset.x` 就是顺流向流动。
- **穿山河段共用中心线**：`nearestSegment(x, z)` 是河流的空间查询入口。`world.heightAt()` 的河槽、`RiverLayer` 的河面与 `MountainField.surfaceAt()` 的山壳侵蚀都以该中心线采样，避免出现“水在一条线、峡谷在另一个地块中心”的双重几何。河流 revision 同时编码采样坐标、宽度和模式，任一项变化都会让山体场缓存失效。
- **山体网格必须消费这个切口**：数据层的侵蚀做好不等于看得见 —— 建网格时若用 `max(裸场, 地表)`，山壳会把切口重新盖回去。现在网格走 `MountainField.surfaceFrom`（与 `surfaceAt` **同一条混合公式**，只是接受本簇裸场以免每点做 25 次邻域查询：实测 `surfaceAt` 慢 7.7×、山体层会从 ~1.0s 涨到 ~2.8s）。存活单元判据也换成「**相对地表的厚度 > eps**」：侵蚀到贴地处厚度为 0，若仍发三角形就会与地表网格共面闪面，那块地交给地表与水带。实测修前 171 个河道横断面里 **169 个被岩石完全压住**、修后 **0 个**。
- **策划水路模式**：`mountainGorge` 与 `waterfall` 采用窄缝切口，`mountainPass` 采用宽豁口切口；`blocked` 会过滤该河段，`dryValley` 当前主要影响路径偏好。无论模式为何，河流仍只在势能下降且可通向入海或汇流终点的候选中选择，覆写不能制造逆流或无出口的河道。
- **侵蚀剖面的形状同样有语义**：`depth` 是「山壳退回地表的**比例**」，而混合是凸组合 —— 残余的 `(1 − depth) × 山壳` 只要高于水面，水带边缘就被压住；旧写法 `depth × (1 − t²)` 还从河心向外单调下降，即使 `depth = 1`，水带边缘也只剩 `1 − 1/widen²`。所以剖面改成「**水带宽度内恒为核心开通度、带外二次收束**」：`depth = 1` 就是整条水带完全开通；`< 1` 只能当「抬高河床的浅滩」实验。实测 `pass.depth` 0.72 → 86 个断面被压住、0.85 → 63 个、≥ 0.95 → 0 个，默认因此取 1.00（与 `gorge` 的区别只剩 `widen`）。

## 过渡带与格内次生特征

「不同地形之间怎么过渡」「单个地块里怎么不呆板」这两件事都放在 `render/props-layer.js` 里做，而不是另起一层 —— 它们与主植被共用同一套物种桶、同一套避让规则（道路 / 河流 / 山体）与同一套实例网格：

- **边界过渡装饰簇**：两种地形相接的边上按 `ecology.transitionRate` 撒一小簇「中间物种」（表在 `TRANSITION_SPECIES`：草|林撒灌木+阔叶+秋色，草|田撒灌木+作物，陆|岩撒碎石+灌木，陆|水撒岸边石…）。簇是往格边**两侧**甩的，压在同一条线上会像一条摆出来的队列。
- **格内次生特征**：每格按 `ecology.featureRate` 出现一处小景物 —— 水洼（只在平地上，`world.heightAt` 探一次坡度）、草丛、碎石堆（只在岩石类地块，否则满地灰石块像工地）、花簇/作物。同一地块因此是「有主景、有零碎」，而不是一块均匀的板。
- 地表的**格内微高差**（`height.innerRelief`）与中环细分是这一层的前提：中环顶点严格落在格内、不与邻居共享，才可以自由加起伏而不会破坏共享角点的一致性。
- 河滩混色：地表顶点色在河线附近朝 `palette.river.bedTint` 靠拢，并按河宽解析出的**三圈影响场**分层叠加 —— 漫滩（最宽，权重 0.42×）、河床（中等，0.78×）、湿岸（最窄，另叠一点 `water.foam` 提亮），最后整体略微压暗。`TerrainLayer` 里按世界位置计算，因此共享顶点算出来天然一致。只靠一条蓝色水带读不出「这是一条河」，水面必须配上湿岸。

## 五档道路

档位由「里数 + 端点城市梯度」推导（`config.road.grades`），表现由 `render/road-style.js` 统一给出配方，3D 与 HUD 的「道路一览」预览共用同一份配方与同一张贴图：

| 档位 | 里数 | 路面材质 | 构件 |
| --- | --- | --- | --- |
| 御道（铁轨） | ≥ 45 | 道砟 | 枕木 + 双钢轨（钢轨微凸带高光） |
| 官道 | ≥ 30 | 石板 | 两侧路缘石（抬起） |
| 商道 | ≥ 18 | 夯土 | 双条车辙暗线 |
| 乡道 | ≥ 8 | 碎石 | 沿路散石（实例化小石） |
| 小径 | < 8 | 泥土 | 毛边（路幅边缘抖出缺口） |

只靠宽度是不够的：默认视角下最宽与最窄只差两三个像素，等级根本看不出来，所以真正的等级信号是「材质 + 构件」。

跨地形时：跨水与跨河都抬平为**桥**（护栏 + 桥墩）；离岸 ≥ `road.trestleDeepWater`（默认 3 格）的**开阔**水面改用**栈桥**（窄桥面 + 高细密墩）；穿山脊的路段定为**隧道**，洞内路面不铺正常路面，而是压暗（`floorShade`）并略微下沉（`floorDrop`），两端各放一座**洞口**：卡在路上的六棱柱岩体（颜色由山脉配色派生，因此看起来是山的一部分）+ 两根门柱与门楣 + 深色洞口（两层暗面做出纵深）+ 门槛石阶。洞口半径跟着**路幅**走（`holePad`），否则最宽的御道会从洞口两侧溢出来。

跨河判定不能只看「采样点是否落在河道里」：道路采样步长约 7.04 单位，与收窄后的河宽同量级，完全可能出现两个采样点**跨在河两侧、而没有一个落在河里** —— 那样就判不出桥，路面会直接扎进 2.20 深的河槽。所以判据是「采样点落在河道内（带符号距离 < 0）**或**相邻两点的符号翻转」。实测 18 个陆上跨河桥采样点、异常 0；最低桥面 3.41，高于水面 0.11。

## v1.6：贴地视角下的「粘连细线」定位与修法

策划反馈「当前出现很多粘连的线」，现象是：贴地视角下有多条细长、淡灰、大致平行的半透明带横穿地图，压在树冠与屋顶之上。定位过程与结论：

1. **先排除坏几何**：遍历全场景，无 NaN、无异常长边；`bridge-piers 8.38` / `trestle-piers 13.46` 的实例缩放是「桥面高 − 地面高」（单位就是世界单位），桥跨水面 8 单位、栈桥跨峡谷 13 单位，合理 —— 不是被拉长。
2. **再逐层隔离**（同一贴地视角：仰角 16.7°、距离约 300，星陨城北）：
   - 只关「云影（贴地）」→ **长条全部消失**，画面饱和度恢复；
   - 只关「道路」→ 长条仍在。**主因是云影面片**。
3. **几何上的必然性**：地形最高 41.8，云影面片挂在 `y = maxRise + 0.6 = 42.4`，共 3 层（相差 0.35）；面片 2781×2326（比地图大 2.7 倍），一张 256 的贴图重复 7 次 → 1 个 texel ≈ 1.5×1.9 世界单位。贴地视角纵向压缩 `sin(16.7°) ≈ 0.29`，texel 行被压成间距 ≈2 世界单位的密排细线（用户截图上量到 13px @ 150px/格 = 1.9 单位，吻合）；`depthWrite:false` + `renderOrder 18` 且面片高于一切，所以它盖在树/屋/山之上。
4. **首修**：云影改为**贴合地形的网格**（`conformGeometry`：逐顶点 `heightAt + lift`，步长 `0.6 × hexSize`，覆盖 `1.12 × viewBox`）；3 层并为 1 层；贴图 512；开各向异性过滤（`sceneKit.maxAnisotropy()` 下发）；两个环境层**默认都关**。修后云影相对地形的偏移是常数 `1.100`（抽 253 点，min = max），即真正贴地。
5. **顺带发现的同类问题**：扁带只按中心线走高度，横坡上会浮边。修法见上文「扁带的横向贴地」，对照实测（同一场景两次构建道路层，只差 `conformDrop`）：

   | 左右两列离地偏差 | 修复前（三列共高） | 修复后（贴合地形） |
   | --- | --- | --- |
   | 中位数 | 0.85 单位 | **0.00 单位** |
   | 平均 | 1.77 单位 | 1.00 单位 |
   | > 1 单位的比例 | 26.4% | **11.0%**（＝桥 / 栈桥 / 洞内段的桥面，本该离地） |

6. 修完复测：贴地视角下开/关云影的画面**逐行纵向梯度曲线几乎重合**（中位数 4.92 vs 4.88，尖峰落在同样的行），说明细线不再由云影产生；剩下的横向条带是道路本身（御道 8.8 单位宽的路面在掠射角下本来就是一条带），属于设计内的观感。
7. **追加修复：山体峰顶扇面的索引错误**（策划随后反馈「山脉顶部和底部出问题，且各处山脉之间都会连接起来」）。`mountain-layer.js` 缝合三层环时，第三组的 `inner` 是**峰顶这一个顶点**，6 个扇区必须共用它，但代码写的是 `inner + k`：

   ```js
   const i0 = inner + k;            // ✗ k = 1..5 时读到的是「下一座山的基环」
   const i0 = toApex ? inner : inner + k;   // ✓
   ```

   每座山按 19 个顶点顺序排列（峰顶是第 19 个），所以 `apexIdx + 1..5` 正好落在**下一座山的基环**上 —— 每个峰因此朝四周射出又长又细的白刺，山脉之间被连成一片；最后一排山还会直接越出顶点缓冲区，拉出巨大的白片。问题正好出现在「顶部」（被错接的峰顶）与「底部」（被牵连进来的邻山基环），与反馈完全吻合。这个 bug 是 v1.5 写三段式山体时引入的，当时的断言只量了「顶点数与位置」，没量「索引拓扑」，所以漏了；现已补上两条：**三角形不许跨山**（三个顶点的 `floor(i / 每片顶点数)` 必须相同）、**索引不许越界**。（上面这组数字是 v1.6 的实测：0 / 1650。v1.7 把山体改成多环收口之后，每片从 19 顶点 / 30 三角形变为 **25 顶点 / 42 三角形**，这两条断言跟着升级，实测跨单元 0 / 4956、越界 0。）

## v1.7：统一平面微缩沙盘与河道重建

这一版把地形从「连续高度场」换成**统一平面**，并重做河流。改动最大的一处其实是**删掉一整套机制**：

- **所有地块共享同一个基准平面**：`tile.surfaceY` 与 `tile.cornerY` 恒为 0（实测 535 格全部为 0）。旧版那套「按通道给目标高度 → 拉普拉斯平滑 → 按 `reliefKeep` 回填山脉与峡谷 → 角点取三格平均 → 归一化到 `visualPeak`」的高度场整体移除，于是「相邻地块之间不能有台阶」这条约束**从算法上就不再需要维护** —— 大家本来就在同一个平面上。
- **地表只剩两种格内形态**：平原格心恒为 0（完全平，实测非平格心 0 个）；丘陵只在格内做一个 dome（半径 0.76 格、到格边回落到 0），实测 73 格丘陵、最高把格心抬起 3.83 单位，角点未归零数 0（相邻地块依旧无缝）。
- **峡谷与隘口体系整体移除，并且清干净了**：canyon 目标与实际都是 0.0%；逻辑 / 渲染测试里「连续高度场无缝性、隘口分布、跨峡谷栈桥、视觉峰值 41.8」这一批断言被换成「统一平面 / 格内微起伏 / 浅切槽 / 统一河宽」。上一版留下的一批**死配置与死分支**（`terrain.relief` 的 `pass*` 与 `canyonShare` / `minClusterSize`、`height.levels` / `reliefKeep` / `smoothPasses` / `selfWeight`、`palette.terrain.canyon`、`palette.outlineClass.canyon`、`ecology.cover.canyon`、`resources.canyon`、`props-layer` 的 `canyon|*` 过渡物种、`terrain-layer` 的 `CLASS_OF.canyon`、`mountain-layer` 的 `passDip*`）这一轮**已经全部删除**：没有任何代码会写 `tile.pass` / `tile.canyon`，留着只会变成静默失效的残留判据（同一个坑在 v1.3 改地形模型时踩过一次）。
- **山脉改为独立模型层**，不再由地表抬升表达；并重写了山体几何（局部取向主轴 + 共享格边高度 + 多峰剖面 + 残雪），见上文「山体（微缩沙盘）」。
- **河流重建**（顶点图沿格边寻路 + 水平水面 + 统一河宽 + 浅切槽 + 树状支流 + 跨河桥符号翻转判定），并修掉了根因 `Hex.edgeCorners` 的方向映射错误 —— 见上文「河流」。
- **环境系统（新增）**：`render/environment-state.js` 是唯一环境状态源（时段 / 季节 / 天气 / 自动轮播），`render/environment-palette.js` 负责「基础色板 × 当前环境 → 各层最终配色」。地表、植被、水面、天空、光照读的是同一份解析结果，所以切一次环境会整图一起变（实测主色 `#fff4dd` → `#bdb4b9`）。HUD 的环境卡片给出 4 档时段 / 4 档季节 / 4 档天气，外加一个自动轮播开关。

⚠ 一条容易重犯的坑：山体几何的判据必须是**含侵蚀**的共享公式（`field.surfaceFrom`），且按**本簇**的场判（块之间靠包络外溢重叠，跨簇处全局场取的是邻簇的更大值，实测差可达 8.5 单位）。原判据写的是 `max(field.fieldAt, heightAt)` —— 拿网格自己用的公式验网格，是自证，所以山壳埋住整条河时它照样绿（详见方案 §15.21）。

⚠ 三条踩过的坑（详见方案 §15.22）：**判据要打到产物为止**（解析式 `heightAt` 说碗没问题，但地表网格每格只有 13 个顶点，碗太小就解析不出来 —— 只有竖直射线打到网格上才看得见 33/45 条被顶穿）；**`gl.readPixels` 的 y 从下往上**（上一版探针漏了翻转，读到纵向镜像的像素，量出来的「水面极差 132」是假的）；**一个几何装多片圆盘时索引要带每片的起始顶点号**（漏掉只有第 1 片打得中）。

**水体显示（v2.6）**是「水面上奇怪的色块」的一次收尾，三件事都是**「数据的粒度 / 边界假设」错了**，而每一件都只有把画面当判据才看得见（详见方案 §15.23）：

- **水深只有 3 个档位**：`depthRatio = (distToLand − 1) / depthRamp` 里的 `distToLand` 是**整数格距** ⇒ 全图只有 0.352 / 1.003 / 1.654 三档，相邻水格最多差 40% 的过渡量；画面深度过渡把这三档原样放大成一块块**硬边多边形**。现在改成「到最近陆地格六边形的**连续**距离」场：格心处与旧值逐值相同，点与点之间连续（暴力对拍 1292 点误差 2.2e-16），同一档位内水深极差 0.297（旧版 **0**），相邻水格 Δt>0.2 的比例从 40% → 16%。
- **地图外被当成陆地**：海底在沙盘边缘抬回水面（外缘 182 个格边采样点高度**全为 0**）⇒ 外缘一圈水莫名变浅发亮、水与海底共面。现在地图外按**开阔水域**算，182 个采样点全部 < 0（最高 −0.40）。
- **海底被加了格内微起伏**：`innerRelief × maxRise ≈ 1.25` 单位 > 水深 0.35~1.48 ⇒ **272 / 948 个中环顶点被抬到水面之上**（最高 +0.997），海底在整片水面上穿出一圈圈硬边格子斑块 —— 这才是截图里那些「板块」的**主体**（把水下地表隐藏起来，色块立刻消失）。现在这层微起伏**只给陆地**。
- 顺带**纯水只用基色**（水面顶点色实测 2054 个顶点除河口湿岸 8 个外**全等**；旧版顶点色的亮度极差 30.4%、相邻水格 25%，全部来自那条大尺度手绘斑驳 `patch`）—— 深浅只由深度过渡给出，符合「纯水应该是画面深度呈现的效果」。

这条链上最值得记住的是：**「深度过渡」读的是渲染网格里的海底形状，不是 `heightAt` 的解析值** —— 公式对、断言绿，仍然可以在画面上穿出一圈圈斑块。所以新增的断言都直接读**网格顶点**：水下地表 2054 个顶点最高 y = 0（不得高于水面）、水面顶点色是常数、以及逻辑侧那份「深度 = 连续离岸距离函数」的暴力对拍。

**山体与水的交界（v2.6 第二段）**收的是用户截图里另外三处，其中两处同源（详见方案 §15.24）：

- **山体在邻格上铺了一圈「贴地薄壳」**：网格器按「簇包围盒 + 外扩」铺规则网格，而场在包围盒边缘很平 ⇒ 厚度只是趋近 0 的浮点噪声；旧存活判据「厚度 > `GROUND_EPS = 0.02`」把它们全部留下，于是每座山外面有一圈**贴地薄壳**按 `max(场, 地表)` 盖住邻格的草地 / 农田、却用着岩壁贴图 —— 远看就是「**每座山外面一块更暗的方形面片，山格正在正中间**」（方形来自网格器自身的规则边界）。实测 **269 / 454 个非山格心被盖住**、最厚 4.88 单位、72.8% 薄于 0.5 单位。现在按一条原则收掉：**看不见的山体就当它不存在** —— 地表低于水面、或相对地表厚度 < `footMin`（0.03 格 ≈ 0.66 单位）的采样点，表面一律取地表 ⇒ 实测 **0 / 454**；山体三角面 113402 → **72694**、落地墙 5174 → **0**（表面在轮廓线上就等于地表，墙顶与墙脚焊成同一个索引、三角形自动退化），而「山脚越过簇边界 282 / 282」与「外溢 ≤ 0.42 格」**保持不变**（没有为了让斑块消失把山脚收回去）。
- **`max(场, 地表)` 把山体抬到水面之上**：水格的「地表」是**负的水下河床**，取 max 之后临海的簇在海面上铺出一块块**方格石板**（实测水格上 181 / 3950 个采样点高于水面、最高 8.46 单位）。修法与上一条同一行判据，只是多一个条件（`g < 水位`）—— 只钳到水面**之下**也不行，浅水里留的一层岩石皮在水面半透明下照样看得见。实测 **0 / 158**。水位不在这里重抄 `size × water.level`，统一问 `Rivers.waterLevel(size)`。
- **一个被实测证伪的提案**：曾经按 Fresnel 直觉加过「水面掠射趋不透明」项（`t = max(t, gate)`，区间 `[0.08, 0.35]`）。写完后曲线单调、端点正确、6 条断言全绿，但**同姿态、固定像素集的 A/B** 显示它对画面的真实影响只有 **0.04%**（默认视角）~ **7%**（最平视角）：判据的生效区间（`|视线.y| < 0.35`）整个落在深度过渡**已经饱和**的区间（`viewCos < 0.42`）里，`max` 抬不动 `t`。已全部删除，两处注释写明理由 —— **新增视觉项必须先做同姿态 A/B，「代码执行了」不等于「画面变了」**。
- **一条「屏幕锁定」的水平分界线**（用户最初记为症状③；「**分界线在场景中间、水平、平移场景不动**」这句话直接把它钉在**屏幕空间**）：先逐个排除世界空间的候选（阴影 / 河床贴图 / 镜面高光 —— 改 `roughness 1 / metalness 0` 只让均值 145.2 → 146.9；把**水下地表网格**整个藏掉，条纹**仍在**，所以它不是上面那三个海底问题）。真正定位它的是**扫分辨率参数**：`depthResolution` 取 0.5 / 0.75 / 1.0 ⇒ 行奇偶差 **35.94 / 10.51 / 0.42**，条纹强度与深度图的 texel 格严格同步。根因是 WebGL 的**深度纹理只支持 NEAREST 采样** + 预通道半分辨率 ⇒ `t` 按 2×2 屏幕像素分块。修法是水面片元里**手动双线性**（4 个 texel 各自还原到视空间再加权、背景权重置零后归一化、无效回退最近邻），实测 **35.94 → 0.21**，切回 `'nearest'` 的对照组 **18.05**。教训：**「离散中间量被下游连续算子放大成台阶」这次放大在屏幕分辨率上** —— 用低分辨率纹理（尤其深度纹理）驱动逐像素量之前，先问它能不能插值。

⚠ 顺带修掉一个隐性坑：`water-depth.js` 的 `applyUniforms()` 原本只在 `create()` 时读过一次配置，**运行期改 `Config.water` 完全无效**（与「策划改完立刻可见」的目标冲突）。现在 `update()` 每帧重读。这也是上面那次 A/B 一度得出「门开＝门关」错误结论的根因 —— **对照组如果「什么也没改变」，先怀疑对照自己有没有生效**。

山脉相关的断言跑在 **`WorldRebuild` 路径**（= 页面实际路径）上：早期它们跑在裸的 `HL.World.build()` 上，而 `MountainSystem` 只在 `WorldRebuild` 里装配，于是「地图有没有山谷」这类判定验的是一条应用从不使用的分支 —— 那条分支带谷、应用那条一个谷都没有，测试却是绿的。另有三条防静默失效的断言：**带谷簇数必须既不是 0、也不等于簇总数**（概率门控最典型的坏法不是报错，而是分支永远走不到）、**规则型覆写只命中匹配的地形分类且计入 revision**，以及**换山脉种子后非山格逐格零漂移**（「只重掷山脉」的判据本身）。

## 已知边界

未实现的部分：网络层（无 WebSocket、无快照与增量同步）、格子事件与资源再生、交易与经济逻辑在 3D 地图上的接入、视锥剔除、真实美术资产、触屏与移动端适配。环境系统（日夜 / 季节 / 天气 + 自动轮播）与山体 LOD 已实现。磨损与生长有完整实现但按需求未启用演示。这些属于方案的阶段 2 及以后，详见方案文档 §11 与 §14。

热重建相关仍留在后续范围的有：旅行中玩家的位置 / 目的地 / 动画时间尚未迁移（当前重建会让玩家回到模拟初始状态）；`waterfall` 的垂直落差视觉与 `dryValley` 的干涸河床材质、生态规则尚未实现，两者目前只参与侵蚀与路径偏好；`blocked` 缺少专项回归断言；山体风格 `twinPeak` / `massif` / `ridge` / `valleyPeak` / `landmark` 已有计划层，但彼此的峰群几何差异仍可继续拉开。

地形侧另有两处是**明确留出、不是 bug**：`gorge` 现在只能把山壳切到「地表」（`depth` 是比例），做不出**河床低于平原的真正地下峡谷** —— 要做需要同时改 `heightAt` 的河道剖面与山壳切口，会动到「地表高度只有一个来源」这条红线，单独一轮再议；最粗一级 LOD（步长 7.33 单位 > 水带宽度 7.04）在俯视缩小时会把豁口采样成一两个顶点、山口变窄成一条缝，默认视角用的是 5 级（步长 4.40）不受影响。

**上一版挂着的几项，这一轮已经修掉（保留记录，避免重犯）：**

- **穿山兼容做好了却看不见（v2.4）**：数据层（`river.mountainErosion` / `MountainField.surfaceAt`）从 v2.2 起就能把山壳沿权威中心线切回地表，但**渲染网格**仍写着自己的老公式 `max(裸场, 地表)`，把切口重新盖了回去 —— 171 个河道横断面里 169 个被岩石压住，页面上就是「河钻进山就没了」。修法：网格改走共享的 `surfaceFrom`、存活单元判据改成「相对地表的厚度」（厚度≈0 处不发三角形，避免与地表共面闪面）、侵蚀剖面改成「水带内恒为核心开通度」（`pass.depth` 0.72 → 1.00）。**它能藏住的真正原因是两条断言盲区**：几何红线拿网格自己的公式验网格（自证），而射线可见性断言又把唯一可能盖住水的山体排除了。教训：查「特性有没有生效」要把链路走到产物为止，判据必须来自与实现不同的来源（详见方案 §15.21）。

- **雪线没跟上平面化**：旧写法是绝对阈值「高程 ≥ `maxRise` × 0.62」，而 `maxRise = 41.8` 已不代表任何真实地表，实测 53 座峰一个雪顶都没有。现在雪线按**该片自身峰高**取（`snowY = baseY + apexH × snowRatio`），再叠方向性噪声做成顺坡条带，实测 121 片全部有雪顶、`snowY / apexY = 0.80`。
- **山脉占比的分母不一致**：目标按「全部非边界格 447」算，实际挑选范围却是「非水 **且** 离城 ≥ 2 格」的可用集合，于是目标 34.4% 与实测 26.4% 天然对不上。现在 `targetByTerrain.ridge` 与挑选范围**同分母**（`ridgeShare × 可用格 / 非边界格`），实测 27.2% → 27.1%，断言通过。教训：份额目标的分母必须与实际挑选集合一致，否则调 `ridgeShare` 永远调不齐。

另外几处是刻意的取舍，不是遗漏：

- **顶点色的交融权重只能调格心**：角点顶点被 3 格共享，同一物理点在相邻地块上必须算出完全相同的颜色，任何「自身权重更大」或「把外圈并进来」的写法都会让三格各算一份（历史实测色差 0.07~0.12），六边形色阶重现。所以角点固定等权，可调项只有 `blendWeights.center`。
- **河道的「岸」只能用颜色表达，不能靠几何**：地表每格只有「格心 + 中环 + 6 个共享角点」13 个顶点，格边附近只有角点顶点，抬到水面之上的「岸唇」没有顶点承载（实测只有约 27% 的水带边缘能达到水面之上）。所以几何只负责把水下陷，两岸交给河床混色与湿岸带。要真正做出几何意义上的岸，必须提高地表网格在格边附近的细分。
- **岩石贴图用平面 UV**：山体与岩壁地表按世界 XZ 贴图，陡壁上的层理会顺着坡面拉伸。要做到严格的等比例需要三平面映射（triplanar），本期先用「少量层理 + 稀疏裂纹」把它压到可接受的程度。
- **洞口岩体是「加法」而非布尔切除**：低多边形风格下不做布尔运算，洞口用「卡在路上的六棱柱岩体 + 门框 + 两层暗面」拼出来。它读起来是「路从岩体里穿过去」，但岩体本身不会真的切削地表网格。
- **御道的细构件不做远景简化**：v1.6 已让扁带横向贴地（`ground + maxDrop`），但御道自身仍是 道砟面 + 双钢轨 + 枕木 + 两条边线 共 4~6 条带；掠射角下它们仍会读成一组平行的细线，只是不再悬空。若还需要更「干净」，下一步是按距离把细构件合并（远景只留路面 + 两条边线），本轮未做。
- **山体不加墨线描边（按需求决定）**：山体是独立网格、不与地表共享顶点，给它描边一定会在山脚的地表上多出**一圈闭合线**（旧版用「全部描边」的写法试过，山脚像被框住）。所以剪影只靠 `flatShading` 的块面感 + 分带顶点色，不加轮廓线。
- **山体格内只长碎石坡，不长植被**：山体的格内被几何占住，树从里面穿出来会很难看；山格因此只长岩石，并强制落在 `ecology.ridgeScree` 区间。⚠ 判据必须跟着山体的形状走：`MountainLayer.occupancy` 给出的 `thickness(x, z)` 就是「这一点上山的厚度」，用 `thickness < ridgeScreeClearance` 判，山脚坡面上就不会再冒出埋进坡里的岩石。<br>历史：旧版按「离格心距离」布置、并把内径与山体的中环半径对齐；改成「簇边界收脚」之后两者不再同源，碎石会整块埋进坡面 —— 这正是「判据的坐标系必须与被判对象的坐标系一致」的又一处。
