# 六边形 2.5D 多人跑商地图系统重构方案（实验版）

版本 v1.7（实验版）　|　日期 2026-09-17　|　依据原稿：《地图系统重构》v1.0

摘要：不换引擎，继续纯网页。前端只引入 Three.js 承担 2.5D 渲染，其余保持零第三方依赖；后端沿用 Node.js 做服务器权威模拟；地图从「城市节点 + 道路图」升级为「六边形地块 + 道路叠加」，并复用现有 13 城 / 21 条道路的拓扑与经济里程。v1.2 把参数集中、按份额比例生成、静态地形与动态状态分离这三件事定了下来。v1.3 补齐三件表现层的事：**起伏地形**（山脉与峡谷走独立通道，道路穿山成隧道、跨峡谷成栈桥）；**蜡笔质感**（描边改为手绘笔触，并让共享顶点的颜色与法线完全一致，彻底消除六边形色阶）；**五档道路的结构化差异**（路面材质 + 构件，而非只靠宽度），并把这份配方抽成 3D 与 HUD 预览共用的单一来源。v1.4 继续推四件观感与可信度的事：**起伏放大成脉**（视觉峰值从 20 提升到 42 单位，噪声尺度放大到 11 格并把小于 3 格的孤立簇清掉）；**隧道终于能被看见**（放弃「靠概率凑」的走廊加成，改为在商路上**显式点名隘口**，洞口重做成卡在路上的岩体 + 门框 + 洞内暗色路面）；**蜡笔笔触连续化**（同一条边只画一条线，修掉「一条边出现两条不接续线段」）；**贴地云影替代云雾**（云雾整片压在地表会让画面发雾，改为两层独立开关）。v1.5 沿「微缩沙盘」方向推三件事：**山体成为独立几何**（基部取该格共享角点、两圈收窄成尖顶、雪线分带）；**河流沿格边最陡下降并真挖河谷**；**地形之间靠「按结构分级描边 + 边界过渡装饰簇 + 格内次生特征」交融**。v1.6 修的是**贴地视角下的「粘连细线」**：云影从「悬在峰顶之上的大面片」改为贴合地形的网格并默认关闭；`Ribbon` 扁带新增 `ground + maxDrop`，让路面 / 车辙 / 路缘 / 钢轨 / 边线 / 枕木横向落到地形上（桥与栈桥保持离地）。v1.7 是一次**减法 + 重建**：地形从「连续高度场」改成**统一平面微缩沙盘**（全部地块共享基准平面，平原完全平、丘陵只做格内微起伏），**峡谷与隘口体系整体移除**，山脉彻底交给独立模型层；河流据此重建为**顶点图沿格边寻路 + 势能场保证入海 + 水平水面 + 统一河宽 + 浅切槽 + 树状支流**，并修掉了让河流「直来直去」的 `Hex.edgeCorners` 方向映射错误；同时补上**日夜 / 季节 / 天气三轴环境系统**。同一轮还**重写了山体几何**：把「单格成山体、连续格成山脉」从调参问题还原成**连接问题** —— 基部取 12 个共享点、主轴逐格锁定六边形邻居方向、主脊端点定义在共享格边中点上并取两侧峰高的平均，于是连续格的缺口恒为 0；再补上多峰剖面、逐峰高低差、顺坡残雪与孤峰规则（诊断过程与教训见 §15.11）。本文件与同目录的 `index.html` 实验页配套，两者都是独立产物，不修改原项目任何文件。

## 1. 目标与范围

把现有的 SVG 路网地图，改造成可承载多人同世界跑商的六边形 2.5D 地图。具体包含五项：

**六边形网格地图。** 地块以轴向坐标 (q, r) 管理，替代现在「城市是唯一坐标点、道路是城市之间的连线」的表达方式。城市、道路、事件、资源都落到格子上。

**2.5D 微缩景观表现。** 参考《筑梦颂》(Dorfromantik)：正交或低透视相机、地块有厚度、方向光加阴影、树木用面片表现体积。视觉目标是「摆在桌面上的一盘地形」，而不是俯视平面图。

**路网叠加在地块之上。** 道路不替换地块本身，只作为覆盖层绘制；遇到树林绕开、遇到水域架桥、遇到高山穿隧道。

**格子事件与生态。** 事件、资源、生态状态挂在单个格子上，玩家经过时由服务器判定是否触发。

**联网多人。** 服务器权威，多玩家在同一世界移动、触发事件、交易，并共享生态状态。

范围之外：美术资产生产、支付与运营后台、移动端原生包装。

## 3. 技术栈

| 层 | 采用 | 原稿多出部分 | 说明 |
| --- | --- | --- | --- |
| 前端 3D | Three.js r147（本地 vendor，UMD） | — | 经典脚本，无需构建 |
| 前端组织 | 经典 `<script>` + IIFE 命名空间 `HexLab` | Vite / ES Module | 与项目「不引入 ES Module」约束一致 |
| UI | HTML + CSS 叠加在画布上 | — | 沿用项目习惯 |
| 后端 | Node.js 内置模块 | — | 项目现状 |
| 网络 | WebSocket（零依赖自研最小帧层）；过渡期 REST/SSE | Colyseus | 见 §7.7 论证 |
| 缓存/消息 | 暂不引入 | Redis Pub/Sub | 单进程内不需要；分片后再评估 |
| 持久化 | 沿用 JSON 文件存储 | PostgreSQL / MongoDB | 项目明确不使用数据库 |
| 部署 | 静态资源 + Node 单进程 | CDN + Redis + DB | 与项目部署方式一致 |

Colyseus、Redis、PostgreSQL / MongoDB 都不是错误选择，它们能解决分片广播、跨进程状态、大世界持久化的问题。但引入它们意味着项目从「零依赖单进程」变成「多组件分布式」，运维成本与故障面同步上升。当前 50~100 人 / 房间的目标用单进程内存态加 JSON 落盘可以覆盖，因此把它们排在分片需求真实出现之后。

## 4. 架构分层

### 4.1 客户端

```
输入层 → 网络层 → 本地状态缓存 → 插值/预测 → Three.js 渲染
```

客户端只负责输入、渲染、动画、插值、UI，不直接修改权威状态。实验页把这条链拆成了可见的模块，目录结构即分层结构：

| 层 | 目录 | 职责 |
| --- | --- | --- |
| 参数 | `src/config/` | 世界生成的唯一参数源：地形比例、高度、配色、生态、村落、道路、氛围、光照 |
| 基础能力 | `src/core/` | 六边形坐标数学、确定性随机与噪声、事件总线 |
| 静态数据 | `src/data/` | 项目地图快照（只读） |
| 世界模型 | `src/world/` | 地块生成、道路样条与分级、城市图寻路、动态状态（纯逻辑，不碰 DOM） |
| 表现 | `src/render/` | 场景装配与各图层，只读世界模型与状态 |
| 交互 | `src/interaction/` | 相机装配、射线拾取，只发意图 |
| 权威状态 | `src/simulation/` | 旅行模拟，扮演服务器那一侧 |
| 装配 | `src/app/` | 主循环接线、HTML 面板 |

依赖方向单向向下，没有环形引用。表现层不写数据，交互层不写数据，模拟层不读渲染对象。

### 4.2 服务端

```
WebSocket 网关 → 世界/房间实例 → 权威模拟
  ├─ 移动与到达
  ├─ 格子事件触发
  ├─ 交易与经济
  ├─ 生态 tick
  └─ 持久化与广播
```

所有关键结果由服务器计算并广播。项目现有的 `/api/tradeBatch`、`/api/warehouse`、星陨城结算已经是这个模式，格子事件与移动需要补上。

### 4.3 共享层

六边形坐标工具、城市图 A*、事件条件与奖励表、价格与旅行耗时公式、地图 schema 版本。这一层要能在浏览器与 Node 双端复用，项目已有先例：`starfall-core.js` 就是双端共享的确定性核心，共享层可以沿用它「同一份代码、两端加载」的做法，避免出现「客户端一份、服务端逐位复刻一份」的双份代码。

## 5. 数据模型

### 5.1 世界静态数据

沿用项目的版本与种子字段名，客户端凭 `worldSchema` 校验版本、凭 `terrainSeed` 重建地形：

```json
{
  "worldSchema": 972,
  "terrainSeed": 20260812,
  "viewBox": { "width": 850, "height": 520 },
  "hexes": [
    {
      "q": 0,
      "r": 0,
      "terrain": "forest",
      "height": 1,
      "roadIds": [],
      "cityId": null,
      "bridgeVia": null,
      "tunnelVia": null,
      "resource": { "key": "oak", "amount": 9 }
    }
  ]
}
```

与项目现有 `map/world-map.json` 的关系：`cities` 与 `roads` 两组数据原样复用（坐标、名称、`tier`、`goods`、`travelDistance`、`economicDistance` 都不变），新增的是 `hexes` 数组——它是「由城市与道路拓扑投影出来的地块层」，属于可重建的派生数据，不进人工维护源。

有一点必须写清楚：项目的「里数」是玩法逻辑权重，和地块间距没有比例关系。实验页实测中，绿田村到溪木村的里数是 2，六边形距离恰好也是 2 格；但橡木镇到铁砧堡是 15 里，格子距离只有 4 格。里数只用于经济与旅行耗时计算，格距只决定视觉与格间寻路，两者不互相换算。

### 5.2 玩家状态

```
playerId
position:      { q, r }              当前所在格
location:      cityId                 当前所在城市（跨城移动时才有意义）
traveling:     { from, to, path, startedAt, arrivalTime, distance }
inventory / gold / vehicle
sessionId
```

`traveling` 的字段与项目现行 `startTravel` 写入的结构保持一致，这样迁移时客户端的蓝点与进度条逻辑可以复用。

### 5.3 动态世界状态

地块资源量与恢复时间、公共事件状态与冷却、道路与建筑变化、生态（季节、天气、植被生长）。

静态地图可由种子重建，动态状态必须服务器持久化并同步。项目现有的 JSON 落盘加 `sv` 单调版本号机制可以直接承载这一层。

### 5.4 参数模块化与按比例生成

地块的所有生成参数集中在 `src/config/world-config.js`。v1.2 时分十段加两段预留（`dayNight` / `season`）；v1.7 起两段预留已兑现为环境系统，因此是**十四段全部启用**：`terrain` / `height` / `palette` / `ecology` / `village` / `road` / `props` / `river` / `resources` / `ambience` / `lighting` / `dayNight` / `season` / `weather`。策划改这一个文件就能调整世界的构成与外观，不需要动逻辑与渲染代码。

地形相关的参数分三组，对应 §6.2 的三条通道：`terrain.landform*`（水 / 低地 / 丘陵）、`terrain.landuse*`（草 / 田 / 林 / 花）、`terrain.relief`（山脉）。⚠ `terrain.relief` 段里与「峡谷 / 隘口 / 走廊加成 / 最小簇规模」相关的参数（`canyonShare` / `corridorBoost` / `pass*` / `minClusterSize`）在 v1.7 之后已**不再被任何代码读取**，属于待清理的死参数 —— 具体清单见 §14「刻意取舍」。

地形的「份额」与「阈值」是两种做法，本方案选择前者：

- **阈值切分**（早期实现）：在噪声值域上设几个分界点。问题是 fbm 的取值并不均匀分布，实际占比会明显偏离目标——实测曾出现草地 19.9% 对目标 29.9%、农田 25.5% 对目标 15.0% 的偏差。
- **排名分位切分**（现行）：先把所有格子的噪声值排序，再按目标份额依次分配类型。因为分位是均匀分布的，实际占比与配置几乎一致，实测各地形偏差都在 3% 个百分点以内。

同一套机制还解决了两件事：一是**岛屿衰减**（离地图中心越远越倾向成水）作用于排名而非阈值，因此不会破坏目标比例；二是**类别多数投票**（连做两遍邻域投票）可以吃掉单格孤立色块，让区域连成整片——这一步是「不要分明的六边形」的前提，否则交界处会一格一格交替，描边就会把每个六边形都框出来。

`road` 段里的 `wearPerHour` 与 `props` 段里的 `conditionDecayPerHour` 默认都是 0，也就是本期不做磨损演示；改成非 0 即自动开始推演，渲染层不需要改动。

## 6. 渲染与视觉方案

### 6.1 相机与光照

正交相机为主，低透视可调。实验页同时维护两台相机，由同一套装配状态（目标点、方位角、极角、距离）驱动，切换只换生效相机，因此两种模式下的取景与操作手感一致。

光照为方向光加半球环境光，配 PCF 柔和阴影；另加一盏反方向补光压暗面，避免背光面纯黑。微缩景观感用雾效代替浅景深，比后处理方案更省。

### 6.2 六边形地块与起伏（v1.7：统一平面）

地形由**三条互不干扰的噪声通道**决定，这是「份额可精确控制」与「特殊地形能长成片」能同时成立的前提：

1. **地貌通道** → 水 / 低地 / 丘陵；
2. **用途通道** → 草地 / 农田 / 森林 / 花田，只作用于非水域；
3. **山脉通道**（带符号，v1.3 新增）→ 只用于判山脉。

山脉通道要乘一个**城市距离权重**（`cityFadeStart = 2` 之内权重 0，到 `cityFadeEnd = 7` 才完全放开），城市与商路密集区保持平缓。挑选范围是「非水 **且** 离城 ≥ `cityFadeStart`」的格，按噪声值排序后取最高的 `ridgeShare`（0.42）那一批。噪声尺度 `scale = 11` 格是「山脉」而不是「小土包」的关键：尺度只有 7 格时同一座山只有三五个格子，远看是一堆孤立小山；放大到 11 格以后波峰拉成长脊，山体连成脉。切完之后再做两遍**孤立山点软化**（6 邻一个山脉都没有的格子还原成普通土地），实测最小的山脉簇是 7 格 —— 正好是「一格 + 它一圈邻居」的六边形包，零散小包被清干净。

⚠ 三处与 v1.3~v1.6 不同，读旧版本时要注意：**峡谷已整体移除**（canyon 的目标与实际都是 0）；**隘口体系已整体移除** —— 「纯噪声凑不出关隘」这个矛盾随峡谷一起消失，那套「显式点名隘口 + 走廊加成」的机制不复存在（其参数与分支还留在代码里，属待清理）；**「最小簇清理」不再是按 `minClusterSize` 整簇 BFS 洪泛**，而是上面那两遍孤立点软化，`minClusterSize` 已不被读取。

**v1.7 最大的变化是地形剖面**：全部地块现在共享**同一个基准平面**，旧版那套连续高度场整体删除：

| | v1.6 及以前 | v1.7 起 |
| --- | --- | --- |
| 高度来源 | 按通道给每格目标高度 → 拉普拉斯平滑 → 按 `reliefKeep` 回填山脉与峡谷 → 角点取「共享该角的 3 格平均」→ 归一化到 `height.visualPeak`（41.8 单位） | 全部为 0。「相邻地块之间没有台阶」这条约束**从算法上不再需要维护** |
| 平原 | 低缓但有起伏（`levels.lowland 0.18`） | **完全平**（格心恒为 0） |
| 丘陵 | 参与高度场，与邻居一起被平滑 | 只在**格内**做一个 dome（幅度 `hillAmp`、半径 0.76 格、到格边回落到 0），因此相邻地块之间不会出现台阶 |
| 山脉 | 由高度场抬升表达，被平滑削成缓丘 | 完全交给独立模型层，见 §6.7 |
| 峡谷 / 隘口 | 带符号噪声的波谷 + 点名隘口 | 已移除 |

实测：535 格 `surfaceY` / `cornerY` 全部为 0；平原格心非平数 0；丘陵 73 格、最高把格心抬起 3.83 单位、角点未归零 0。地表高度只有一个查询入口 `world.heightAt(x, z)` —— 河流的浅切槽（§6.7）与山体基环（§6.7）都从它取值，因此「河从山脚切过去时山脚跟着凹下去」这类问题自动成立，不需要额外对齐。

`height.visualPeak`（1.9 × 格半径 ≈ 41.8）仍留在配置里，但**已不代表任何真实地表高度**，现在只剩状态层的路面高度上限断言（`y < maxRise × 1.25`，宽松到几乎无意义的界）引用它。⚠ 山体的雪线曾经按它取值，导致「53 座峰零雪顶」；v1.7 已改成按每片自身峰高取（§6.7），**不要再把新的高度判据挂到这个值上**。

共享角点只是几何无缝，**视觉无缝还需要三件额外的事**，前两件在 v1.3 定型、v1.7 依然成立：

- **共享顶点的颜色必须一致**。同一个物理角点在相邻地块里是不同的顶点副本，如果颜色按「当前正在写哪个地块」计算，草与林、陆与水之间就会沿六边形边界露出硬色阶；正确做法是基色、辅助色、沿岸度都先在「该顶点的地块集合」里取平均，邻居地块算出来必然与自身相同。
- **共享顶点的法线必须一致**。只做单格 `computeVertexNormals`，同一角点在相邻地块上会拿到不同法线，空地也会出现明暗缝；做法是把每个扇形三角形的面积加权法线按物理位置累加，同位置的所有副本共用一条法线。
- **高度也必须是与「谁在问」无关的函数**（v1.7 补充说明）。这条是前两条在高度维度上的推广：河道的浅切槽与水面高度、山体基部都要经 `world.heightAt` 求值，而它只依赖世界坐标，所以共享角点拿到的切槽深度天然相同。反之，如果切槽改成「把深度写进 `tile.cornerY`」这种按格存值的方式，就会立刻重现共享顶点不一致的老问题 —— v1.5 的「挖河谷」正是这种写法（当时靠「必须在道路与地表网格之前调用」的顺序约束兜住），v1.7 改成了 `channelOffset(x, z)` 纯函数。

**地形交融**沿用 v1.4 的结论：角点顶点取「压在该角上的 3 格」等权平均，地块中心再按 `blendWeights.center`（默认 0.32）朝 6 邻平均色渗透，过渡因此从「只有一圈角点渐变」变成「格心就开始互相渗透」。这里有一个反直觉的硬约束：**角点只能等权**。v1.4 一开始试过「自身权重 1.0 / 邻居 0.85」并把邻居的邻居也并进来（两圈），本意是让色带渗得更宽，结果是相邻地块各算一份集合与权重，同一物理顶点的色差立刻从 0 涨到 0.07~0.12（陆 / 岩 / 水三组全部失败），六边形色阶重现。原因是三格的两圈并不相同（每个格的邻域都包含对方没有的格子）。因此角点固定等权，可调项只剩「格心渗透量」——它是唯一不影响共享顶点的位置。

实测：相邻地块共享角点的最大误差 0.00e+0；渲染侧抽样 240 组共享顶点，颜色与法线的最大差均为 0.0e+0。这两个 0 是「不要分明的六边形」最硬的验收指标，见 §15。

另有两个细节必须处理：

- **水面必须绝对平坦**。规则是：只要角点上有任何一个地块是水，该角点就取水面高度，因此湖面与河面都是平的，不会因为「水参与角点平均」而在每个水格边缘抬出一条亮边。v1.7 之后陆地本身也在 0 平面上，水面只需取 `hexSize × 0.005` 这个略高于基准平面的固定水位（见 §6.7 的浅切槽）。
- **顶面三角形绕序**。角点按角度递增排列时，若按 (中心, 角k, 角k+1) 组三角形，法线会朝下成为背面，顶面被剔除的同时射线也打不中。必须写成 (中心, 角k+1, 角k)。这个坑在实验页里真实踩到过，见 §15。

地表贴图统一按**可平铺**方式生成（周期噪声 + 笔画跨边界环绕补画）。贴图在世界里按约 2.2 格的周期重复，若噪声不周期，平铺后会在随机位置留下网格状接缝，看起来像一片一片的补丁——这也是「格子感」的来源之一，见 §15。

地块厚度只保留在网格最外缘（一圈水面裙边）与整张地图的沙盘底座上，不再给每个格子做侧壁。

关于 InstancedMesh 的取舍：原稿要求地块用 InstancedMesh 批量渲染，但「逐顶点共享角点插值」与「同一份实例几何」在技术上互斥。实验页把同一种材质的地块合并成一个 BufferGeometry（陆地／农田／花田／岩壁／水面共五组），先保证连续曲面成立；生产环境可以退化为「基准块走 InstancedMesh + 顶面走合并几何」。树木、房屋、城市地标、岩石都走 InstancedMesh。

### 6.3 树木与建筑

树木用十字交叉面片（两片互相垂直的矩形）加程序化画布贴图，单次 draw call 实例化绘制。十字面片在正交与低透视相机下已经有足够的体积感，不需要逐帧旋转对齐相机；如果将来相机倾角变化更大，再补真正的 billboard 旋转。

避让次序遵循「先生成道路，再撒树」：道路先生成采样点并建立空间索引，撒树时逐个查询最近路距离，小于阈值就跳过。森林格成簇（每格 2~4 株），草地与山地稀疏分布，树木带逐实例颜色扰动。

### 6.4 道路

路面由 CatmullRom 样条采样带构成。控制点取相邻两格中心的中点（即六边形共享边中点）并叠加噪声偏移，首末点落在城市格心，保证道路真正接入城市。道路不居中：控制点在 XZ 平面做确定性随机偏移，避免所有路都压在格心上。

路面的 UV 用**世界等比映射**（沿路方向按累计里程、横向按法向距离），因此同一种材质在整张地图上颗粒大小一致，不会被拉伸成条纹。

**跨水 / 跨河＝桥**：跨水与跨河路段都把路面抬平为桥面，桥面高度取该段两端邻近陆地样本的较高者再加余量（早期版本用整条路的最高点定桥面，会把桥抬到比山还高）；自动生成桥墩（柱高＝桥面高度 − 该点地表高度）与两侧护栏。**跨河判定在 v1.7 改成了「符号翻转」**：道路采样步长约 7.04 单位，与收窄后的河宽（半宽 3.52）同量级，完全可能两个采样点跨在河两侧而没有一个落在河里 —— 只看「采样点是否在河道内」会整段漏判，路面直接扎进 2.20 深的河槽。判据因此写成「该点带符号距离 < 0 **或** 相邻两点符号翻转」；跨河段落在陆地上，`hexes` 标记覆盖不到，还要按采样点补标 `bridgeVia`。

**开阔深水＝栈桥**（v1.3 新增，v1.7 改判据）：离岸 ≥ `road.trestleDeepWater`（默认 3 格）的**开阔**水面，普通桥墩会站在很深的水里，因此改用更大的余量把桥面抬到岸线之上并配**高细密墩**（间距更小、柱更细）。窄桥面加密集柱列，远看就是栈桥。v1.3~v1.6 的触发条件是「跨峡谷」，峡谷移除后改为纯按离岸距离判定；本图实测没有满足条件的开阔水面，因此栈桥 0 格。

**穿山脊＝隧道**（v1.4 重做）：离散高度 ≥ 2 的山脊路段定为隧道。洞内路面不铺正常路面，而是**压暗 + 略微下沉**（`floorShade` / `floorDrop`），读作「路钻进山里」；进出口各放一座洞口，由四部分拼成：卡在路上的**六棱柱岩体**（颜色由山脉配色派生并按 sRGB 线性化，因此与山体是同一种石头，而不是摆在草地上的白板）+ 两根门柱与门楣 + 深色洞口（两层暗面做出纵深）+ 门槛石阶。

三个尺寸关系是这一版的关键，都是被实拍逼出来的：

- **洞口半径跟着路幅走**（`holePad`）。v1.3 的洞口是固定值，比最宽的御道（路幅 17.6 单位）还窄，路会从洞口两侧溢出来；现在取「路半宽 × 1.12」与下限值的较大者。
- **岩体必须整个包住门框**（`rockGrow` / `rockHeight`）。否则门框会从岩体顶上冒出来，看起来是「一堆石头上又叠了几个方块」。
- **岩体六棱柱绕 Y 转 30°**，让一个平面正对道路，洞口就开在这个面上；岩体还向下埋入地表一点（`rockSink`），避免看起来是「摆上去的」。

同样是被实拍否掉的方案：v1.3 后期试过「一圈石环」和「一块更宽更矮的崖壁方板」，前者像悬在坡上的一只碗，后者像立在地上的一块白板——低多边形风格下，用体积（岩体）而不是面片来交代「这里是山的一部分」才成立。代价是它属于「加法」而非布尔切除，岩体不会真的切削地表网格。

### 6.5 蜡笔描边与手绘质感

「涂鸦、卡通」观感的关键不是配色，而是**区域之间的深色描边**。描边层沿地形类别边界、海岸线、道路两侧各铺一圈贴地扁带，颜色取偏暖的黑棕。之所以不用 GL 线段，是因为线宽在多数平台被固定成 1px、无法调粗细，而扁带几何既能控宽，也能做出手绘的粗细抖动。

v1.2 的描边是等宽的，观感接近 CAD 线。v1.3 改成**蜡笔笔触**：

1. **手抖**：每条边按固定长度细分成小段，宽度在小范围内抖动，并叠加横向游走；
2. **下笔轻重**：每段有独立不透明度，再叠一张以 alpha 承载「两侧虚化 + 颗粒 + 孔洞」的笔触贴图。逐段不透明度用**四分量顶点色**实现——three.js 在 color 属性 itemSize 为 4 时启用逐顶点 alpha，因此不必为每一档笔触拆网格；
3. **断笔**（`breakRate`）：每段按概率整段略过、笔画之间留白。

v1.4 把这条规则改对了，因为它踩了一个很显眼的坑：**同一条边被画成了两条不衔接的线段**。原因是 v1.3 让每一段各自独立随机宽度与横向偏移（32% 的搭接量也不足以掩盖），相邻段的中心线能错开将近一个笔宽，于是同一条边看起来是两条错位的短线。修法是把「逐段独立随机」改成**沿边的连续笔触**：

- 把边分成 N 段后取 N+1 个**站点**，宽度、横向游走、不透明度都只在站点上取值，且由一维平滑噪声决定（每段噪声频率随边长归一），相邻段**严格共享站点数值**，因此中心线连续、宽度渐变；
- 每一段用「两端各有宽度／游走／透明度」的梯形拼出来，段与段之间不再有重叠，也就不存在错位；
- 默认把 `breakRate` 置 0（一笔到底），断笔能力保留为可选项。

这条修法留下了两处可验证指标：一是笔触总数必须等于「边数 × 每条边的段数」且断笔数为 0；二是**相邻段在共享站点上必须给出完全相同的两个顶点坐标**——把整条边的顶点按位置分组，重合顶点数应当恰好等于「边数 × 内部站点数 × 2」。后者能精确地把 v1.3 的错位问题钉住（那时重合顶点数为 0）。

其余手绘质感来自三处：顶点色用多尺度噪声做斑驳（大尺度色斑 + 约 3.5 世界单位的平滑颗粒，不能用逐顶点哈希，否则六边形尺度上会出现刻面噪点）；每类地表配一张程序化灰度贴图（草地斑驳、农田条纹、花田斑点、水面波纹、岩壁层理）；所有植被与房屋贴图都先按放大一圈的形状铺一层墨色再铺本色，得到统一的描边轮廓，立体道具则用反转壳几何描边。

岸线另有一条浅色泡沫线，但只在「恰好一侧是水」的边上绘制。若判据写成「任一侧是水」，水与水之间也会被当成岸线，于是每个水格都被泡沫框一圈，湖面又变成六边形拼块——这个坑同样真实踩到过，见 §15。

### 6.6 环境氛围

三层：**贴地云影**、**高空云雾**、**飞鸟**。三层的数量、速度、透明度都在 `config.ambience` 里，HUD 里各有一个独立开关。v1.7 在此基础上补了一套**三轴环境系统**（见本节末）。

v1.3 只有云雾与飞鸟。云雾是若干大尺度半透明软面片，抬到高空缓慢横向漂移并回绕。问题在实拍里很明确：**整片云雾压在地表之上会让画面雾蒙蒙**，沙盘视角（尤其是正射）下尤其明显，地形起伏、描边、道路等级全被糊掉一层。因此 v1.4 引入贴地云影，云雾降级为可选项。**v1.6 又把云影本身重做了一遍**，因为它在贴地视角下成了「粘连细线」的元凶（详见 §15）：

- **云影现在是一张贴合地形的网格**（`conformGeometry`：平面分段后逐顶点抬到 `world.heightAt + lift`，步长 `0.6 × hexSize`，覆盖 `1.12 × viewBox`）。早先它是「比地图大 2.7 倍、悬在 `maxRise + 0.6` 的水平面片」，后果有三：深度上永远在场景前面，于是盖住树 / 屋 / 山；压低到贴地视角时横贯整个画面；贴图被极度拉伸后 texel 排成一排排细线。改为贴地网格之后，云影落在树冠之下，遮挡关系正确，掠射角下也不再是一整片横条。
- **单层 + 512 贴图 + 各向异性过滤**。旧版 3 层面片只差 0.35 ~ 0.7 单位，等于同高度多层半透明叠加（粘在一起的观感来源之一）；贴图 256 在覆盖整图的面片上 1 个 texel 就有 1.5 世界单位，必然走样。现在 1 层、512、`anisotropy = sceneKit.maxAnisotropy()`（上限由设备决定，渲染器不暴露就退回 1）。
- **两个环境层默认都关**。云影只压暗地表、不糊视线，但仍然是一层压在画面上的氛围层，做成默认开启会让策划第一眼看到的不是地形；因此与云雾一样改为按需勾选。
- 漂移仍然是**滚动纹理 offset**（`offset.x = base + unit × t`），网格完全不动，零矩阵更新；纹理纵向重复次数按面片长宽比推导（`repY = repX × 面片高 / 面片宽`），保证云斑在世界里是圆的。

这三层除了观感，也是检验「环境层与地图层是否解耦」的样本：它们只读世界尺寸，不依赖地形与道路，因此可以独立开关、独立调参。

**v1.7 新增：三轴环境系统。** 云雾 / 云影 / 飞鸟解决的是「空气里有东西」，环境系统解决的是「什么时候、什么季节、什么天气」，两者正交。它由两个模块构成，职责刻意分开：

- `src/render/environment-state.js` 是**唯一环境状态源**：时段 `timeOfDay`（0~1 的浮点，配 4 档 HUD 预设）、`season`、`weather`、`autoCycle`（自动轮播）。所有消费者（地表 / 植被 / 水面 / 天空 / 光照 / 云影）都只读它，不各存一份。
- `src/render/environment-palette.js` 是**唯一配色解析入口**：「基础色板（`palette.*`）× 当前环境 → 各层最终配色」。时段用关键帧插值出太阳色 / 强度 / 天空渐变（`dayNight`），季节按预设给出草地 / 树 / 田 / 岩 / 水 / 花的染色（`season.presets`），天气按预设给出天空染色 / 雾色 / 太阳强度 / 环境光补偿 / 云色（`weather.presets`：clear / cloudy / rain / foggy）。

这样拆的原因是**一致性**：如果让每个图层各自「按当前时段调暗一点」，切换季节时就会出现「草地变了、农田没变」「树变了、树影没变」这类不齐。集中解析之后，切一次环境是整图一起变 —— 实测主色从 `#fff4dd` 变到 `#bdb4b9`（黄昏），地表与场景（太阳 / 天空）同时改变。

它同时兑现了 v1.2 留下的两段预留（`dayNight` / `season`），并新增 `weather`，也就是 §5.4 里说的「十四段全部启用」。

### 6.7 山体与河流（v1.9：噪声高度场 + 统一水位与画面深度过渡）

§6.2 的统一平面对这一节既是前提也是约束：**地表不再承载任何「高低」**，所以山与水都必须做成**独立于地表的额外结构**，而不是继续在地表参数上努力。另外也要反过来承认这一点：v1.5 把山体做成独立几何，本意是「地表几何预算不足」的补救；到了 v1.7 地表完全平，**独立模型层就不再是补救而是唯一方案**。

**山体**（`world/mountain-field.js` + `render/mountain-layer.js`）：山脉格上的独立几何。要同时满足两条形态要求 —— **单格读成一座山体，连续格连成一条山脉** —— 而这两条都不是靠调参能调出来的，必须落在几何的**连接方式**上。

v1.7 走的是「共享格边高度 + 逐格解析式脊线」，实拍仍读成「一格一个六棱台、上面扣一个盖，格子之间没连上」（用户反馈）。v1.9 **放弃逐格造型，把形状整体收敛成一个只依赖 (x, z) 的簇级柏林噪声场**（§15.16）；v2 再把场的**体量形态**从「椭球穹丘」换成「蜿蜒窄脊带 + 低岩台」（§15.17）：

```
H(x, z) = 包络 × 轮廓掩码 × ( 岩台 + (1 − 岩台) × 脊带 × 峰高 × 脊网 )
```

- **脊带**：山体是一条沿簇主轴（格心 PCA）延伸、横向**蜿蜒**（`beltWander`）的窄带，半宽 `beltHalfWidth: 1.15` 格。横向剖面 `belt = (1 − nd)^flankExp`，`flankExp 1.45 > 1` ⇒ **上陡下缓 + 宽裙摆**（山的横剖面必须是凹形；旧版的 `1 − ru² − rv²` 是「倒扣碗」，顶平根陡，几何方向就是反的 —— 这是「太平」的第一根因）。半宽沿走向抖动、两端收口。
- **峰高沿走向调制**（`summitScale` / `summitFloor`）：峰—鞍—峰。旧版椭球只有一个极大值、脊状噪声又只能做减法（`shape ≤ dome`）⇒ 每簇最多一个峰。
- **脊网**（`Rng.ridgedPerlin2` = Perlin 的 ridged multifractal）：山脊是 `|n| → 0` 的**等值线**，天然是曲线、没有格点偏好；沿走向做各向异性拉伸（`crestStretch: 2.4`）让脊线顺山脉走向延伸。⚠ **它的实测值域不是满量程**（min/p05/中位/p95 = 0.11 / 0.34 / 0.62 / 0.87）：旧写法 `1 − 0.5×(1 − rg)` 只在 0.67~0.93 之间飘、噪声实际只贡献 ±13% 起伏；v2 用 `crestSharp` 把它拉到有效量程。⚠ 也不要把它**直接当高度**（阈值切出一张脊网），实拍读成「一堆小尖锥 / 碎石堆」。
- **放射脊 / 冲沟**：把「到脊线的横向距离」按噪声调制（`spurAmp`）⇒ 等值线成**星形**，脊与沟沿坡面放射。单格 / 短簇用**角向**取样：在噪声空间里 `perlin(cosθ·k, sinθ·k)` 天然以 2π 为周期，因此不需要另写一个周期噪声函数。
- **低岩台**（`baseLevel`）：整簇的底盘，保证山格本身是一块岩石高地而不是悬空的脊带，同时必须足够低 —— 实测峰:底 = 3.23（旧版椭球把整簇抬到 63% 峰高，这就是「平台感」的来源）。
- **高度包络**按**簇心取一次**（`peakHeight: [1.05, 1.60] × hexSize`，`ampScale` 控波长），与簇内的 `summitScale` 分工明确：前者管「这条山脉整体高、那条整体矮」，后者管「同一条山脉上峰谷交替」。
- **逐簇归一化**：`body = 脊带 × 峰高 × 脊网` 是三个各自 ≤1 的噪声相乘，极大值不落在同一点 ⇒ 裸场峰顶只有包络的 0.6~0.8。v2 编译时量一次实测峰顶把整簇场缩放回去，于是 `peakHeight` 就是「这座山有多高」，与噪声参数解耦（这也替掉了旧文档里那句「实测峰值只到包络的约 0.74」的补偿心态）。
- **轮廓掩码**以「到簇边界折线的**有符号**距离」收脚：内侧 `taperInner: 0.45` 格开始降、外侧 `taperOuter: 0.30` 格归零，再叠一层低频噪声抖动（`outlineWobble: 0.22`）。**外侧 > 0 就是「允许山脚漫出簇边界」（用户决策 ~0.3 格）** —— 接触线因此是一条噪声曲线，而不是格边折线，这是「摆脱六边形轮廓」的关键。实测 260 / 260 条簇边界边外侧仍是山体。
- **山脉分布一起收窄**（`hex-world` 的起伏通道由 `fbm2` 换成 `ridgedPerlin2`，`ridgeShare 0.42 → 0.22`）：原因是结构性的 —— 山格 = 起伏通道的高分位集合，`fbm2` 的极大值是**团块**，所以只调份额永远收不出窄带（实测平均簇宽随份额上升反而从 3.6 涨到 6.1 格）。换噪声后实测山脉占陆地 16.8%、平均簇宽 2.9 格、长宽比 2.76。
- **随簇尺度增长的两条规则**（否则「一大片山脉」读不出来）：`beltWidthGrow 0.85` 让脊带随簇宽增长、`peakHeightGrow 0.32` 让峰值随簇格数增长，两条都只对 ≥ 6 格的簇生效 ⇒ 单格与小簇形态完全不变。
- **山谷**（`valley`）：脊线一侧刻一条同向的沟（单格与连续地块都可能出现，哈希门控、确定性可复现）；单格簇另给谷一个朝向，于是**单格山峰可以不对称**。
- **演示用大片山脉**（`relief.demoMassif`）：手工块，优先级高于比例生成，但**不计入**目标份额、也不进「分布是窄带」这条断言（见 §15.18）。

以下三条是**设计红线**，换实现也要守住：

- **红线①：高度只有一个来源，且只依赖 (x, z)**。同一世界坐标只有一个值 ⇒ 相邻格、跨格、跨簇一律同高，**裂缝在机制上不可能出现**。这一条取代了 v1.7 的「共享点两侧必须算出同一个值」那一族技巧：场是 (x,z) 的函数，两侧读到的本来就是同一个值。实测 3210 个采样点场值恒 ≥ 0、低于地表 0 个；顶点重复位置 0。
- **红线②：山脚不低于地表**（表面高度 = `max(场, world.heightAt)`）。否则丘陵微起伏与河床浅切槽会让地形从山脚里穿出来，落地墙还会变成朝上的反墙。实测各 LOD 级表面超差 0、墙脚超差 0。
- **红线③：壳体只落在轮廓线上**。「场值归零的那条等值线」就是山脚接触线，沿线立竖直墙落到地表。因此**自由边只剩贴地的墙底边，空中没有任何敞开的边** —— 这就是「表面闭合」的全部含义。实测各级翻面 0、索引越界 0、悬空自由边 0。

拓扑与建网格：

- **共享三角格网格器 + 多级 LOD**：整簇按 `step = hexSize / detail` 铺一张网格、逐点取样场，相邻格**复用同一批格点**，所以格子感从结构上消失；按 `lod.details: [12, 8, 5, 3]` 为每个山簇建**四级**网格（块 = 山簇 ⇒ 相邻簇即使级别不同，接缝处两者都在地面高度上，**结构上没有 T 型缝**）。表面三角按 `ny ≥ 0` 定向（高度场不会悬垂，判据只有这一条 —— 沿用旧的「背离格心」判据实测把一半三角形判反：翻面 19501 / 40486）；只有竖直落地墙用「背离格心」。
- **顶点按位置焊接**（1/512 单位量化）：同一个世界坐标只写一次，颜色也只有一份。实测最细一级（detail 12）：**40671 顶点 / 77690 三角形**（表面 74127 + 落地墙 3563），四级合计约 13.5 万三角。
- **孤峰（单格成山体）**：6 邻无山的山格标记 `isLone`，峰高乘 `loneScale: 0.85`（实测孤峰最高 26.87 vs 最大簇 31.38 单位）。⚠ 旧版有一条「孤立山点软化」循环，把单格山脉还原成普通地形 —— 于是**单格山脉在结构上不可能存在**（实测 0 座）。该循环已删除，现在实测 6 片孤峰。
- **顶点色**（`palette.mountain` + `rockBands`，v2 改成暖棕 / 土黄）：岩带按归一化高度 `y / refH` 做两段 smoothstep 混合（带抖动）；**冲沟压暗**（`creviceShade`）用采样网格的**凹凸**判定（某点比 4 邻平均低就是沟）—— 不重算任何噪声，天然跟着形状改动走；再叠**雪带** —— 雪线 = `refH × snowRatio`（0.66），沿主轴拉伸的噪声让雪成为**顺坡的条带（残雪）**而不是一圈整齐的环。最后**山脚往「脚下地块的地表色」过渡**（`footBlend`），于是山与邻格在颜色上也接得上。实测 24 / 63 格在雪线以上、近雪色顶点 1633 个。
  ⚠ `refH` 取**本簇实测最高峰**（归一化之后它恒等于 `amp`），所以每条山脉都有自己的雪顶。
- **不加轮廓线（按需求决定）**：山体是独立网格、不与地表共享顶点，给它描边一定会在山脚的地表上多出**一圈闭合线**。所以剪影只靠 `flatShading` 的块面感 + 分带顶点色。
- 山体**不进地表的共享顶点校验** —— 它是独立几何，不该被地表的不变量绑住。占位由 `MountainLayer.occupancy(world)` 统一对外提供：植被、房屋各问一次，所以没有杉树从岩壁里穿出来；山格只长岩石，判据是 `occ.thickness(x, z) < ridgeScreeClearance`（**「这一点上山的厚度」与山体形状同源**）。⚠ 历史：旧版按「离格心的距离」判、并把内径与山体的中环半径对齐；山体改成「簇边界收脚」之后两者不再同源，碎石会整块埋进坡面里（§15.13 的遗留，本轮修掉）。地面道路横穿的矮山格也让开，正好形成一处路堑。
- **簇级派生数据只留四个字段**（`boundaryEdges / clusterIndex / isLone / foothill`）：形状搬进场之后，v1.5~v1.7 为「逐格解析式脊线」产的 `axis / perp / fwd / back / hasFwd / hasBack / clusterId / clusterSize / clusterIsLone / boundaryEdgeCount / neighborCount` 没有任何消费者，连同挑主轴的 `pickAxis` 一起删除。这属于「重构后必须回扫派生数据」的常规动作 —— 留着的代价不是性能，而是**下一个读代码的人会以为它们还在起作用**。

**河流**（`world/river-builder.js` + `render/river-layer.js`）：河走**六边形的棱**（地块之间的边界），因为「地块在河的哪一侧、哪个聚落临河」是有玩法含义的。v1.7 把它从「tile 路径 + 取中点」重写成**顶点图上的寻路**：

- **顶点图**：把所有地块的 6 个角点按位置去重成顶点表，沿棱把顶点连成图 —— 于是「走一条棱」恰好就是「跨过一条格边」。这个表示法从根上消除了「河斜切进格内」的可能（旧版出现的 3.279 格斜向长直线段，根因是 `Hex.edgeCorners` 的方向映射写错，见 §15.7）。河源取「融雪线以上最高的角点」里彼此相隔足够远的几个，实测 5 条主河全部从山地 / 丘陵出发。
- **势能场**：先算「每个顶点到海面在图上要走几步」（BFS），再叠一层噪声；每步只能走到势能更低的邻点，而**噪声权重 `meander = 0.45 < 1`**，所以每一步势能都严格下降 —— 既不会绕圈，也不会停在内陆（旧版靠有限次「翻坎」逃洼地，是概率性的）。河还会绕开城市格，否则水带会被城市广场模型整片盖住。
- **汇流**：下一步落到别的河已经走过的顶点即为汇流，本河并入、下游共享同一水道。实测 5 条主河去向为入海 ×4 + 汇流 ×1，不需要第二套渲染规则。
- **水面严格水平，且与海面同源**：整张图只有一个水位 `config.water.level = 0`（= 基准平面 = 与陆地齐平），河 / 湖 / 海共用。旧版把水位钉在「这条棱自身的岸高」上，水面会跟着地形爬坡；v1.8 又给河单独取 `格距 × 0.005`（0.110），结果**河口比海面高 0.11 —— 河入海处有一个台阶**。现在两者同源，台阶不存在。
- **统一河宽**：整条河同宽、所有河同宽、支流与干流同宽。`river.width = 0.16`（× 格距）即半宽 3.52 单位，实测全线 3.52 ~ 3.52（**1.000×**）、首尾差 0.000000。参考《文明 6》：河道宽度基本恒定，不做「河源细、河口粗」的锥形收放（旧版由「走向进度」与「汇流通量」叠出 3.1×，再叠上支流与干流的差异，全图到过 **5.1×**）。
- **浅切槽**：`channelOffset(x, z)` 把临河格的顶点按「到河线距离」下切 `channel.depth × (1 − r²)`（`r = d /（半宽 × channel.widen）`），槽在水带之外回落到 0。它是**纯函数**（只依赖世界坐标），叠在 `world.heightAt` 里，因此共享角点天然一致、相邻地块不会裂缝 —— 这比 v1.5 那种「直接写 `tile.cornerY`」的做法少一条顺序约束（见 §6.2 的第三条不变量）。下切处还加了 `ceiling = waterY − 0.02` 的钳制，保证水面永远是最上层可见面。实测 209 个临河角点 + 134 条临河边中段被切到水面之下；横剖面 102/102 在河线处低于水面、98/98 在半宽处仍在水下、39/39 在槽外回到基准平面；临河平原格心最大高度 0.000000。
  ⚠ 生效判据是「**本格临河 或 本格是临河格的邻居**」（`riverNear`）：格边角点由三格共享，只按本格判定会在角点上漏切，河面拐角被顶出一条薄墙。
- ⚠ **为什么不做「岸唇」**：曾把剖面做成「满深 → 回升越过水面 → 岸唇回落」，想让水带的几何边缘被岸埋住。实测只有约 **27%** 的水带边缘能达到水面之上 —— 地表网格在格边附近**只有角点顶点**，一格以外的地形全靠线性插值，抬到水面之上的岸唇**没有顶点去承载**，渲染出来依旧是水带边缘浮在地表上。因此回退成「几何只负责让水下陷，两岸交给颜色」，并把这条约束写进 `channelOffset` 的注释，避免以后重试一遍。
- **岸色带按水带半宽缩放**：`wetScale / bankScale / floodScale` 是「水带半宽的额外倍数」而非绝对半径，实测湿岸 1.58 / 河床 3.87 / 漫滩 7.74 单位（半宽 3.52），三层按「湿岸 ⊂ 河床 ⊂ 漫滩」层层收束。旧版写死绝对半径（6.6 / 10.1 / 17.6），窄段就成了「细线套一圈 11.5 倍半宽的巨大深晕」、宽段几乎没有岸 —— 这是「河宽很丑陋」的另一半成因。植被与房屋的避让距离同理（`propsClearanceScale`）。
- **树状支流**：从内湖 / 内海湖岸出发（候选 39 处，实测 3 条），走同一套势能场，撞进已有水道即并入，且**每生成一条就把它并进网络**，因此水系自然长成树枝状；支流起点彼此拉开（最近 1.73 格），并会重进最近河段索引，所以同样有湿岸、避让与切槽。
- 渲染上复用 `render/ribbon.js` 的扁带：水面 + 中泓深色带 + 岸线暗边。`river.renderSmoothing` 只做表现层的圆润化，不影响逻辑上的格边路径；水纹与海面共用同一张贴图与同一 UV 周期，滚动 `offset.x` 就是顺流向流动。<br>⚠ 水面与中泓**必须各用一个材质**：v1.8 两个 mesh 共用一个 `waterMat`，于是 `setEnvironment` 里「先设水面色、再设中泓色」的第二行改的是同一个对象 —— 第一行的水面色立刻被覆盖，`palette.river.surface / surfaceDeep` 的区分在环境刷新后完全失效。

**水下地表与画面深度过渡（v1.9 新增）**：水面是一个**水平面**，而「水有多深」在 v1.8 之前根本不是数据（水格地表恒为 0，与陆地共面）。这一轮把它补成真实几何量，并让水面据此与地面过渡：

- **水下地表 = 敞水深度场 × 岸坡因子**（`world/hex-world.js`）。
  · **敞水深度场**：由「到陆地的格距」决定（`depthShallow 0.016` → `depthDeep 0.09`，跨 `depthRamp 2.5` 格过渡），并且**铺在格心三角网（六边形格心的 Delaunay 三角剖分）上做线性插值**。为什么必须插值：相邻水格深度不同，各用各的就会在共享格边上留下「一格一格的水深台阶」，水面半透明后读成一圈圈梯田。实测 504 条共享边的最大跨格差 **0.0007**。
  · **岸坡因子**：0 在岸线上、`shoreRamp 0.7` 格内升到 1；只在**临陆的格边**上量距离。角点处是自洽的：正六边形一个顶点恰由三个两两相邻的格共享，只要三格里有一个是陆地，另外两个水格**都**有一条岸线格边以该顶点为端点，两侧同时归零。实测岸线处为 0（唯一例外是 5 处河口，被浅切槽切下去 2.20）。
  · 实测离岸每远一格都更深：`1 格 0.352 → 2 格 1.003 → 3 格 1.654`。
  ⚠ 旧写法是「每格一个碗」：碗底的 0 落在该格**全部六个角点**上，连深海中央也是 0 ⇒ 整片海变成一格一个洼的六边形凹凸纹。角点只有一种情况该是 0：这个角点**真的踩在岸线上**。
- **水面**：一个严格水平面（实测 2067 个顶点全部落在 `y = 0`），高度只由 `config.water.level` 决定，与地形完全解耦；`render/terrain-layer.js` 里水面与水下地表是**两张独立网格**，不再混在一起。
- **画面深度过渡**（`render/water-depth.js`）：水面网格是平面，它凭什么读出「水有多深」？靠一张**半分辨率的深度预通道**（`WebGLRenderTarget` + `DepthTexture`，只画地表 + 山体 —— **水面自己不在里面**，否则「地表深度」恒等于水面深度、差值为 0，过渡白做），水面材质用 `onBeforeCompile` 在片元里比较「本片元深度」与「该像素处地表深度」：

  ```
  dz = (该像素的地表深度 − 本片元深度) / 每单位深度的窗口深度差
  t  = smoothstep(clamp(dz / depthFade, 0, 1))
  颜色压深 = mix(原色, 原色 × depthTint, t)      不透明度 = mix(depthAlphaMin, 1, t)
  ```

  差 ≈ 0（岸边、水线）⇒ 水面几乎透明、透出水下地表，岸线自然收边；差 ≥ `depthFade` ⇒ 不透明并压深，读作深水。**「水」与「地」之间因此不再是硬边，而是一段由真实几何深度驱动的过渡**，河 / 湖 / 海共用同一套。
  · 筛选预通道内容用**相机 layer 掩码**（给地表 + 山体打开第 1 位、预通道期间 `camera.layers.set(1)`），而不是临时改 `visible` —— `visible` 是图层开关的状态，借来当渲染筛选会跟 HUD 勾选打架。
  · `uDepthPerUnit` 每帧按相机算：窗口深度是非线性的（透视尤甚），同一个 `depthFade` 在正交 / 透视下若不折算会给出完全不同的观感；相机有俯角，视线方向量到的深度差还要除以 `|cos|` 折回竖直方向。
  · UV 换算要用**绘制缓冲尺寸**（`gl_FragCoord` 的单位），且尺寸**每帧自检**：本模块比 `sceneKit.resize()` 先创建，只建一次会拿到 canvas 默认的 300×150，建出一张 150×75 的深度图、UV 全错。
  · 深度贴图用 24 位（`UnsignedInt`）：16 位在 `far ≈ 4000` 时每级 ≈ 0.06 单位，而过渡区间只有 2 单位，会看出台阶。
  · 预通道期间关掉 `shadowMap.autoUpdate`，避免白白重算一遍阴影贴图。
  · **实测对拍**（俯视相机、射线竖直 ⇒ 深度图读到的就是该水格的水下地表）：最深水格真实 1.654 / 量到 1.683；浅滩 0.352 / 量到 0.256；深浅在同一套尺度下被区分开。
- **顺带删掉一处重复逻辑**：顶点色里原来还有一条「浅水带」（按 `distToLand / 3.2` 把水面朝 `water.shallow / water.foam` 提亮）。它看上去也在做「近岸浅、远处深」，但**必然是一格一格的** —— 同一个水格上，格心顶点的权重是「本格 + 6 邻」、角点顶点是「压在角上的 3 格」，两套权重算出的 `distToLand` 平均值不同，每个六边形内部都会有一圈色阶，实拍就是水面上的**蜂窝纹**。水深现在由几何唯一给出，这条就删了（同一类问题第二次出现：**同一个量不能有两套来源**）。

**过渡与次生特征**：描边按**结构类**分级（只有陆\|水、陆\|岩、岩\|水、城\|其他 收边），草\|林、草\|田、草\|花 之间的接缝交给「边界过渡装饰簇」（`props-layer.js` 的第二遍）；同一层还有第三遍「格内次生特征」（水洼 / 草丛 / 碎石堆 / 花簇）。两者共用主植被的物种桶、避让索引与实例网格，因此不新开图层。河滩一侧还多了一层地表混色：顶点色在河线附近朝 `palette.river.bedTint` 靠拢，按漫滩（0.42×）/ 河床（0.78×）/ 湿岸（叠 `water.foam` 提亮）三圈分层叠加，最后整体略微压暗。

## 7. 多人联网架构

### 7.1 权威模型

客户端发送意图：移动到目标格、交易、事件选择。服务器校验路径可达性、移动速度与时间是否合法、交易的价格库存与距离、事件条件是否满足，然后广播结果。

### 7.2 移动同步

服务器保存 `path`、`startedAt`、`arrivalTime`，并在广播里带上。客户端按服务器时间插值显示本地玩家与其他玩家。慢节奏跑商不需要帧同步，事件驱动加 1~2 Hz 位置更新足够。

实验页用本地模拟等价实现了这条链：`simulation/travel-sim.js` 持有权威状态（出发时刻、到达时刻、途经城市），`render/player-layer.js` 只接收姿态数据（位置、朝向、进度）做插值表现，两者之间没有反向依赖。将来把姿态来源换成 WebSocket 快照，表现层不需要改动。

### 7.3 AOI 兴趣区域

按 chunk 或六边形半径划分，只同步附近玩家、地块动态与公共事件。进入 AOI 发快照，之后发增量。

### 7.4 事件同步

私人事件由服务器为该玩家独立判定，只发给该玩家；公共事件是世界级状态，广播给 AOI 内玩家并持久化；生态 tick 由服务器低频模拟，客户端只做表现。

### 7.5 断线重连

`sessionId` 恢复，服务器下发全量快照加增量，客户端重建场景与 UI。项目现在的 Token 会话与 `sv` 版本号已经覆盖了身份与防回滚部分，地图侧需要补「快照 + 增量」的表达。

### 7.6 防作弊

服务器时间为准，校验路径、速度、距离，交易与奖励由服务器结算，另加速率限制与可选的消息签名。项目已有的四道防线（会话 Token、单调版本号、结构白名单、差分审计）可以直接沿用，格子事件与移动是新的校验点。

### 7.7 网络方案的可行性论证

原稿把 WebSocket 作为核心决策，项目现行却是 REST/JSON 加 SSE 推流，而且设计文档里明确写过早期规划的 WebSocket 网关「未按原文实现」。重启这个方向需要先回答两个问题：零依赖约束下能不能做，以及值不值得做。

| 维度 | REST + SSE（现状） | WebSocket（目标） |
| --- | --- | --- |
| 零依赖可实现性 | 已实现 | Node 没有内置 WS 服务端，但可在 `node:http` 的 upgrade 之上自研最小 RFC6455 帧层，只用 `node:http` 与 `node:crypto`，仍然不引入 npm 依赖；浏览器端原生 `WebSocket` |
| 延迟与开销 | 每次请求带完整头，轮询有周期盲区 | 长连接、双向、头部开销一次性 |
| 广播模型 | 服务器无法主动推，AOI 增量只能靠轮询模拟 | 与「快照 + 增量 + AOI」天然契合 |
| 断线重连 | 无状态，重连即请求 | 需要会话恢复协议，但能精确知道客户端丢了哪些增量 |
| 扩展上限 | 50~100 人 / 房间的慢节奏推送够用 | 多人同屏、公共事件广播、生态同步的上限明显更高 |

结论：目标方案采用 WebSocket，但限定在零依赖自研最小实现路径上，同时保留 REST/SSE 作为过渡与降级通道。理由是自研帧层的成本可控（握手 + 文本/二进制帧的解析与组帧，几百行量级），而它换来的主动推送能力正是 AOI 与增量同步的前提；反过来，如果继续用 REST/SSE，多人同步会被迫退化成高频轮询，随人数上升先撞到瓶颈。

需要如实标注的是，当前实验页并未接入网络：它用本地权威模拟演示「权威状态 → 客户端插值」这条链，网络层是空的。迁移路径按三步走：先把格子事件与移动的结算搬到服务端，用现有 REST 接口跑通单人权威；再把地图相关的收发改造成 WS 消息（协议见 §8），REST 保留为降级；最后按 AOI 半径接入快照与增量。

### 7.8 道路五档分级

道路按「里数」定档，两端城市梯度较高时上提一档。v1.3 的关键修订是：**等级不能只靠宽度区分**。在默认视角下，最宽的御道与最窄的小径在屏幕上只差两三个像素，等级根本看不出来；真正让人一眼分档的是「路面材质 + 构件」：

| 档位 | 里数门槛 | 路面半宽（× 格距） | 路面材质 | 构件 | 实验页条数 |
| --- | --- | --- | --- | --- | --- |
| 御道（铁轨） | ≥ 45 里 | 0.20 | 道砟 | 枕木 + 双钢轨（钢轨微凸带高光） | 5 |
| 官道 | ≥ 30 里 | 0.18 | 石板 | 两侧路缘石（抬起） | 3 |
| 商道 | ≥ 18 里 | 0.15 | 夯土 | 双条车辙暗线 | 4 |
| 乡道 | ≥ 8 里 | 0.125 | 碎石 | 沿路散石（实例化小石） | 5 |
| 小径 | < 8 里 | 0.095 | 泥土 | 毛边（路幅边缘抖出缺口） | 4 |

档位、宽度、材质、构件、桥与栈桥的余量都在 `config.road` 里。为了让「HUD 里看到的等级」与「地图上的等级」一定是同一件事，五档的视觉配方（材质表、构件清单、顶视预览绘制）单独抽成 `src/render/road-style.js`：3D 层与 HUD 的「道路一览」面板共用同一份配方与同一张路面贴图，只是把尺寸换算成像素。如果两边各写一套，面板里的对比就失去意义。

档位不仅影响观感，也是后续「不同等级道路的通行效率与修缮成本不同」的挂点：每档在 `tile-state` 里各有自己的状况值，路况影响路面明度与饱和度。

### 7.9 地图状态与生态：玩家决策如何改变地图

方案的目标之一是「所有玩家的决策一定程度上会改变这个地图实际的样子」。为此把地图拆成两层：

- **静态地形**：地形类型、高度、道路走向、城市位置。由种子确定性重建，任何客户端与服务端算出来都一样，可以随时丢弃重算。
- **动态状态**（`src/world/tile-state.js`）：每格的湿度、肥力、植被生长度；每条路的状况；每栋房屋的状况。这一层可以整体 `serialize()` / `restore()`，体积与「被改动过的条目数」成正比，默认状态下接近于空。

状态层提供两个入口：`tick(dt)` 做低频推演（磨损、生长），`applyImpact({type, target, amount})` 表达玩家行为对地图的影响（道路磨损与修缮、道具修缮、植被生长）。渲染层只读取状态：路况决定路面明度，房屋状况决定墙体与屋顶向「破败色」靠拢的程度，植被生长度决定尺寸与饱和度。

本期的取舍是把推演的速率全部设为 0，也就是不做磨损与生长的演示，只保留结构与接口（有断言覆盖 `tick` 短路与 `applyImpact` 生效）。这样做的原因是：磨损只有在「玩家长时间反复通行同一条路」的场景下才有意义，而实验页没有真实玩家行为，硬做动画只会得到一个没有信息量的演示。等阶段 2 的格子事件与移动结算落到服务端之后再打开速率，届时不改渲染代码。

## 9. 性能与扩展

**客户端。** 地块与树木走批量绘制；LOD、视锥剔除、纹理图集；对象池复用；移动端降级关闭阴影、减少装饰。实验页在 535 格、708 个植被道具、71 栋房屋的规模下场景三角面数约 20 万、绘制调用 200+ 次，WebGL 2.0 上运行正常。这个规模离性能上限还很远，真正的压力在纹理与美术资产量上来之后。其中山体是单笔最大的固定开销（四级合计约 13.5 万三角；最细一级 77690），但**按缩放分级**：默认视角只渲染 19.5%。要再压可以改小 `lod.details`，代价只是脊线更钝。

**服务端。** 单房间 50~100 玩家起步，分片与多世界实例扩展，低频生态 tick 避免全图高频计算。项目实测 100 并发下约 68 req/s、p95 约 1 ms，慢节奏跑商的服务器负载主要来自广播而非计算。

**带宽。** 六边形坐标 (q, r) 体积小，慢节奏事件驱动，位置更新可降到 1~2 Hz，或只在旅行开始与到达时发送。

### 已验证的事实

逻辑层用 Node 环境对世界生成、地形按比例、统一平面与格内微起伏、**水下地表（岸线归零 / 跨格连续 / 离岸逐格变深）**、浅切槽横剖面、河流骨架与统一河宽、五档道路、桥 / 栈桥 / 隧道、**山体簇级噪声场（场值非负、轮廓外溢、脊线多峰、孤峰、雪线）**、状态层与确定性重建做了断言；渲染与交互层用系统 Chrome 无头运行做了断言，其中几条是「结构不变量」性质的：**共享顶点的颜色与法线必须一致**、**蜡笔笔触必须在站点上严格接续**、**山体顶点必须按位置焊接（重复位置 0）**、**表面与墙脚都不得低于地表**、**没有塌陷面 / 翻面 / 越界**、**自由边必须贴地**、**山脚必须越过簇边界**、**水面必须是一个严格水平面**、**水下地表必须真的被切下去且深浅不一**、**深度预通道读出来的水深必须等于真实水深（俯视对拍）**、**河面必须是垂直射线打到的第一个表面**、**离河线 0.75 格处必须已不是水面**、**扁带左右两列必须落到地形上而桥面不许被摊平**、**云影网格相对地形必须是常数偏移**。

### 未实现部分与刻意取舍

未实现：网络层（无 WebSocket、无快照与增量同步）、格子事件与资源再生、交易与经济逻辑在 3D 地图上的接入、LOD 与视锥剔除、真实美术资产、触屏与移动端适配。环境系统（日夜 / 季节 / 天气 + 自动轮播）已实现。磨损与生长有完整实现与接口，但按需求未启用演示。

刻意取舍几处，写在这里是为了避免后来者把它们当成 bug：

- **顶点色的交融权重只能调格心**：角点被 3 格共享，必须等权，否则相邻格各算一份（历史实测色差 0.07~0.12）。可调项只有 `blendWeights.center`。见 §6.2。
- **河道的「岸」只能用颜色表达，不能靠几何**：地表每格只有 13 个顶点（格心 + 中环 + 6 共享角点），格边附近只有角点顶点，抬到水面之上的「岸唇」没有顶点承载（实测只有约 27% 的水带边缘能达到水面之上）。所以几何只负责把水下陷，两岸交给河床混色与湿岸带；要做出几何意义上的岸，必须提高地表网格在格边附近的细分。见 §6.7。
- **洞口是「加法」而非布尔切除**：洞口用「卡在路上的六棱柱岩体 + 门框 + 两层暗面」拼出来，读作「路从岩体里穿过去」，但岩体不会真的切削地表网格。见 §6.4。
- **岩壁用平面 UV**：山体与岩壁地表按世界 XZ 贴图，陡壁上的层理会顺坡拉伸。严格的等比例需要三平面映射（triplanar），本期先用「少量层理 + 稀疏裂纹」把影响压到可接受的程度。
- **山体是叠加几何，不是地表抬升**：统一平面之后这条更彻底 —— 山体是独立网格，基部读 `heightAt` 保证与地表贴合（也顺带跟着河流浅切槽一起凹下去），但它**不参与地表的共享顶点校验**（那条不变量只约束地表）。代价是山体与地表是两套几何，任何「山脚要不要跟着别的东西变」的问题都必须靠「基部读同一个 `heightAt`」这一条兜住。见 §6.7。
- **河走格边，不穿格心**：这样「地块在河的哪一侧、哪个聚落在河哪一边」才是有意义的，代价是河道只能是六边形棱的折线（低多边形风格下这是特征不是缺陷），而且每格的临河距离要用「点到线段的距离」算，不能用格心距离。见 §6.7。
- **山体格只长岩石，且强制落在山脚之外**：山体格中心被山体几何占住，树从里面穿出来很难看。这条规则同时产出了参考图里的「山脚碎石坡」，但它意味着山体格的道具种类被限制死（只剩岩石）。⚠ 碎石的判据必须**跟着山体形状走**：`MountainLayer.occupancy` 给出的 `thickness(x, z)` 就是「这一点上山的厚度」，用 `thickness < ridgeScreeClearance` 判即可。历史：v1.7 山体有中环，「内径 ≥ `midRadius`」就够；v1.9 改成簇边界收脚之后坡面铺到格边，旧判据（离格心 0.62）会让岩石埋进坡面里 —— 本轮已改为与山体同源的厚度判据（§15.16）。
- **山体不加墨线描边**：山体是独立网格、不与地表共享顶点，给它描边一定会在山脚的地表上多出**一圈闭合线**（像被框住）。所以剪影只靠 `flatShading` 的块面感 + 分带顶点色，这是需求方明确接受的取舍。
- **山体的面数不再是「一次性固定开销」，而是按缩放分级**：整簇铺一张三角格，间距 = `hexSize / lod.details[i]`（`[12, 8, 5, 3]` → 1.83 / 2.75 / 4.40 / 7.33 单位），实测四级 77690 / 36132 / 15158 / 6358 三角（用户已明确「地图片面的数量级限制可以忽略，先力求还原参考图」，旧的「≤ 2.5 万」预算作废）。**判据是屏幕像素密度、不是裸距离**（正交是默认档，它没有距离衰减），默认视角实测只渲染 19.5%。连续性 / 落地 / 闭合这三条红线与级别无关，但**每一级都要单独过一遍**（render-test 逐级断言）。
- **峡谷 / 隘口体系连配置一起清干净了**：`tile.canyon` / `tile.pass` 早已不再被写入，但上一版还留着 `terrain.relief` 的 `pass*` / `canyonShare` / `corridorBoost` / `minClusterSize`、`height.levels.*` / `reliefKeep` / `smoothPasses` / `selfWeight`、`palette.terrain.canyon`、`palette.outlineClass.canyon`、`ecology.cover.canyon`、`resources.canyon`、`props-layer` 的 `canyon|*` 过渡物种、`terrain-layer` 的 `CLASS_OF.canyon`、`mountain-layer` 的 `passDip*`。这一轮**全部删除**：留着只会变成静默失效的残留判据 —— 同一个坑在 v1.3 改地形模型时踩过一次（见 §15）。教训：**换地形模型时要连配置与分支一起清，判据「永远不成立」和判据「没有」在代码里是两种危险**。

## 15. 实现过程中发现并修正的问题

这些都是把方案落到可运行代码时暴露出来的，写在这里是因为它们会影响后续实现，不代表方案本身的判断有误。

**噪声方差不足导致地形退化。** 多倍频 fbm 叠加会向 0.5 收敛，直接用阈值切地形时，535 格里只切出 1 格山地，全图几乎都是草地，隧道功能无法验证。修法是先对噪声做对比度拉伸再切阈值。这个问题在改成按比例生成之后从根上消失了。

**顶面三角形绕序反了。** 角点按角度递增排列时，顶面若按 (中心, 角k, 角k+1) 组三角形，法线朝下。后果是水面因为材质默认单面渲染而整片消失，同时射线打不中水面，点击水域选不中任何地块。改成 (中心, 角k+1, 角k) 后两者同时恢复。已在渲染测试里加了一条「垂直射线必须命中水面顶面」的断言把这个坑锁住。

**标签尺寸失控。** 精灵缩放原本用「画布像素 × 一个含义不明的系数」，结果城市名贴图覆盖了大半个屏幕。改成以 `worldPerPixel`（每个画布像素对应多少世界单位）作为唯一控制量，标签大小直接按世界尺度给定。

**平滑把山削平，玩法的离散高度因此永远到不了「高」。** 五遍拉普拉斯平滑把山地从 19.2 单位压到 7.7 单位，导致没有任何一格的高度分档达到 2，隧道判定全部落空。修法有两处：一是把玩法的离散高度改为取自**未平滑的目标高度**，让玩法分档与视觉平滑彻底解耦；二是加入归一化步骤，把平滑后的陆地最大高度重新拉到 `visualPeak`，于是「山有多高」由单一参数决定，再改平滑遍数也不会顺带改地形。

**桥面高过山。** 早期用「整条路最高点 + 抬高」定桥面高度，把桥抬到了 21 单位，比最高的山（9.7 单位）还高。改为取该桥两端邻近陆地样本的较高者再加少量余量。

**区域碎成一格一格，描边把每个六边形都框出来。** 噪声采样尺度只有 1.5 格左右，每种地形都只剩单格，于是描边沿着每格的六条边画，远看就是一片六边形拼块。修法是把采样尺度放大到 5~9 格，并加两遍邻域多数投票吃掉孤立色块。

**逐顶点哈希把地表变成刻面。** 手绘颗粒原本用逐顶点哈希取值，每个顶点的明度独立抖动，在六边形尺度上形成刻面噪点，远看又是一片格子。改成按约 3.5 世界单位取平滑噪声后才连成笔触状的大块纹理。

**水面被抬出亮边。** 角点平均把邻接陆地的水角点抬高了，于是每个水格边缘都出现一条亮边，湖面看起来仍是一格一格。规则改成「角点上有水就取水面高度」，水面因此绝对平坦。

**岸线泡沫线误判。** 岸线判据原本写成「任一侧是水」，导致水与水之间的边也被当成岸线，每个水格都被泡沫框一圈。改成「恰好一侧是水」后，泡沫线从 190 条降到 76 条，湖面才连成整片。

**一处配置路径写错导致页面启动失败。** 村落层的磨损配色写成了 `palette.props.wornTint`，而实际在 `config.props.wornTint`，控制台只报了一个 `Cannot read properties of undefined`。修法除了改正路径，也依靠启动兜底面板把真实错误显示在页面上，避免以后只看到一句「启动失败」。

v1.3 继续优化时，又暴露出下面几处问题。它们大多属于「几何已经无缝、但观感仍然是一格一格」这一类，成因各不相同，值得记下来：

**共享顶点的颜色不一致，平地沿六边形边界露出色阶。** 高度连续只保证几何无缝；顶点色如果按「当前正在写哪个地块」计算，草与林、陆与水之间就会在同一个角点上得到两种颜色，形成硬色阶。诊断方法是直接量：把同一物理位置的所有顶点副本分组，比对它们的颜色与法线差值（当时实测最大色差 0.542）。修法是把基色、辅助色、沿岸度、离岸度都改成「该顶点的地块集合」的平均值。

**共享顶点的法线不一致，空地出现明暗缝。** 每个地块的顶点是独立副本，`computeVertexNormals` 只在本格内平均，同一角点在相邻地块上拿到不同法线。修法是按物理位置累加面积加权法线，同位置的副本共用一条。这两条修完之后，颜色差与法线差都降到 0，这是「不要分明的六边形」最可验证的指标。

**地表贴图不可平铺，远看是一片一片的补丁。** 贴图在世界里按约 2.2 格周期重复，而噪声不是周期的、笔画在画布边界被切断，平铺后就在随机位置留下网格接缝。修法是给噪声加一个环面版本（整数格点按 period 取模）并把跨边界的笔画/斑点按 ±N 环绕补画。顺带发现农田条纹的周期与作物行距是两处各自维护的常数（17/192 与 0.195），已经改成由贴图模块统一推导，避免下次改贴图时作物「长到条纹外面」。

**一格宽的峡谷被平滑填平，深峡谷做不出来。** 拉普拉斯平滑会把谷底平均到两侧高地的高度（实测谷底被抬到 12 单位，与坎顶几乎齐平）。修法是平滑之后按 `reliefKeep` 把山脉与峡谷回填一部分目标高度：峰顶与谷底保得住，山脚过渡仍由平滑给出。

**起伏与商路完全不相交，隧道与栈桥永远看不到。** 起伏只灌在离城 4 格以外，而商路是 3~12 格的短线，实测 84 个走廊格到最近起伏格的中位距离是 5 格，21 条路一条都不穿过山脉或峡谷。修法是给走廊加可关闭的加成（见 §6.2），并通过一次噪声偏移的搜索，让商路上同时出现山脊与峡谷。

**隧道洞口过大且悬空。** 洞口原本用 0.30 格距的洞面加 0.34 格距的石拱，中心抬到地表上方 0.32 格距，结果是几个「悬在空中的大碗」；又因为穿山段只有一两格，两个洞口挤在一起。修法是把洞口尺寸压到 0.17/0.30 格距、中心抬 0.19 格距、加一圈石砌门圈让它像嵌在岩壁里，并且太短的穿山段不再放洞口。

**重构后残留的失效判据。** 地形模型从「山地」改为「山脉 + 峡谷」之后，隧道判据仍写着 `landform === 'mountain'`（该字段已不存在），统计里的 `targetByTerrain.mountain` 也已失效。这类残留不会报错，只会静默地「永远不成立」，因此每次改地形模型都要连带搜索一遍全部判据与统计。

v1.4 这一轮把「起伏、隧道、描边、氛围」四件事推到能看，暴露的问题几乎都是**同一类：代码逻辑自洽、但实拍观感不成立**。它们只能靠「先量化、再实拍」两步找出来：

**走廊加成是概率思维，凑不出关隘。** v1.3 想让隧道出现，做法是「把商路走廊上的起伏强度放大若干倍」，指望噪声自然交汇。实测直接推翻了这条路：起伏带被城市距离权重推走，而商路几乎全在低权重区，84 个走廊格中只有 4 个有资格起伏；再穷举 289 组噪声偏移，没有一组让任何一条路同时穿过山脊与峡谷。教训是：**「让玩家一定会遇到」这件事不能用概率表达**，只能用显式安排（点名隘口）。这也是本版改动最大的一处。

**山脊隘口不保证出现隧道。** 改成点名隘口之后仍然看不到隧道：隘口的类型由该处噪声符号决定，实测 5 处里 4 处是峡谷（栈桥），而隧道只长在山脊上。修法是给山脊留一个下限 `passRidgeMin`：最长的若干条商路先按山脊安排。

**「山脉远离城市」与「隘口在商路上」在几何上冲突。** 把隘口也按远郊标准（离城 ≥ 3 格）要求后，隘口只剩 1 处且落在峡谷上。查数据才知道原因：全图 21 条商路共 189 个格子，只有 5 格同时满足「在路面上」且「离城 ≥ 3」。结论不是「降低标准」而是「分开标准」：远郊山脉按地理规则、隘口按关卡规则，并在断言里分成两条 —— 否则要么山脉贴城，要么隧道消失。

**顶点色的「两圈交融」把色阶又带回来了。** 想让地形色块过渡更宽，最直觉的写法是「自身权重 1.0 / 相邻角的两格 0.85 / 再外一圈 0.30」。结果是共享顶点的颜色差从 0 涨到 0.072 / 0.091 / 0.124（陆/岩/水三组），平地沿六边形边界出现色阶。根因是「两圈」对三个格并不对称：每个格的邻域都包含另外两格没有的格子，于是同一个物理角点被三份不同的权重各算一次。**共享顶点的颜色只能由「谁在问」无关的信息决定**，落地上就是「压在该角上的 3 格等权」；可调的只剩不共享的格心顶点。

**蜡笔笔触「逐段独立随机」把一条边画成了两条线。** v1.3 每段各自随机宽度与横向偏移，相邻段中心线能错开将近一个笔宽，用户看到的就是「同一条边出现两条不衔接的线段」。修法是改成沿边的连续笔触：段与段**严格共享站点**上的宽度/游走/浓淡。这件事的验收方式很值得记下来 —— 它没法靠肉眼看断言，但可以精确量化：把整条边的顶点按位置分组，重合顶点数应当恰好等于「边数 × 内部站点数 × 2」（当时实测 0，修完 2820 = 期望值）。

**隧道洞口的三次返工。** 洞口一共做了三版：① `圆面 + 石环`，贴在坡面上像悬在空中的一只碗；② `崖壁方板`，像立在地上的一块白板；③ 现在的 `六棱柱岩体 + 门框 + 暗面`，才读得出「路从岩体里穿过去」。另外两个尺寸关系也是实拍才暴露的：洞口半径比最宽的御道路幅还窄（路从洞口两侧溢出来），以及门框比岩体还高（看起来是一堆石头上又叠了方块）。**低多边形风格里，交代「这是山的一部分」要靠体积，不能靠面片。**

**材质颜色的 sRGB 双重转换。** 洞口岩体一开始直接取 `palette.terrain.ridge.color`，实拍却白得发亮，像摆在草地上的道具。原因是地形顶点色经过 `convertSRGBToLinear()`，而材质颜色被当作线性值、再经 sRGB 输出，两者差了一大截。修法是把石块颜色也先线性化。这类问题不会报错，只会「看起来不像同一个世界」。

**「云雾」和「云影」是两种东西。** 高空云雾整片压在地表之上，会让画面雾蒙蒙（正射视角尤其严重），把地形起伏、描边、道路等级全糊掉一层。改用贴地云影后还要注意纹理尺度：一开始 `repeat = 1.6`，整张地图只盖住一层云，既看不到云在动、也几乎不压暗；改成 `repeat = 7` 之后单块云影约三四个六边形大，才读得出「云在飘」。（**v1.6 补充**：这里的 `repeat = 7` 是配「地图 × 1.7 的大面片」算的，面片改成贴地网格后覆盖范围变成 `1.12 × viewBox`，对应的值是 `repeat = 3` —— 结论「单块云影约三四个六边形大」仍然有效，只是数字要跟着面片尺寸换算。这也是一个教训：**把「一次重复覆盖多少世界单位」写进注释，比只写一个裸数字更耐用。**）

**新增图层忘了接线。** 云影在 HUD 里加了开关、在主循环里加了默认可见性，但 `ui:toggle` 的分支表漏了一条 `showCloudShadow`，于是那个勾选框点下去什么也不会发生 —— 而且不会报错。这类「声明与接线分处两地」的遗漏，靠渲染测试里的「点一下、看状态是否翻转」才抓得住，已补上对应断言。

v1.5 这一轮针对「微缩沙盘、文明 6 那类山脉、陆地中的河流、地形之间的过渡、单个地块里的自然性」五件事。核心结论是：**有些观感不是调参问题，而是几何预算问题**，继续在参数上努力是白费的。

**地表网格的分辨率决定了「山」做不出来。** 每格 7 个顶点（格心 + 6 个共享角点）是「地块之间没有台阶」的前提，但它的直接后果是：无论把山抬多高，形状永远是缓丘。实测隘口山格的格心 34.1，它最高的邻格 29.9 —— 只高 4 个单位，看着是台地。所以山体必须另叠一层独立几何。抽出来之后有两条硬约束：**基部环直接取该格的 6 个共享角点**（位置与高度都取自地表网格），山脚才严丝合缝；**山体不进共享顶点校验**（它是独立几何，不该被地表的颜色/法线不变量绑住）。这两条让「山脚无缝」与「不改坏地表」同时成立。验收方式同样是量化的：山体每座 19 个顶点（基环 6 + 中环 6 + 上环 6 + 峰顶 1），逐个顶点核对基部与共享角点的位置和高度。

**一个中环的山是圆台，不是峰。** 第一版山体只有「基部 + 中环 + 峰顶」，实拍是一片六边形晶体/台地：俯视只能看到一块浅色平台。根因是半径 1.00 → 0.55 收得太少、高度只有 0.42。改成 1.00 → 0.46 → 0.20 两圈收窄、高程 0 → 0.30 → 0.62 → 1.00 之后才收出尖顶，而且相邻两座山会在共享边上自然形成鞍部（峰-鞍-峰的节奏）。**低多边形的「峰」靠的是环半径的收敛速度，不是高度。**

**河面必须钉在「这条棱自身的岸高」上。** 第一版水面按「原地面 − 常数」给，实拍有一半被地表盖住、另一半浮在地表之上。原因是判据用错了参照：河线是格边，格边的地面高程是**两端角点的插值**，而当时用来核对的 `world.heightAt` 是「格心 → 中环 → 六角均值」的两段线性模型 —— 边上的点根本不是那个值。修法有两处：水面改为按该棱两端角点插值出岸高再减水深，并且沿流向做单调约束 + 保证高于河床；断言也改成用采样点自带的 `bank`/`bed`（这条棱自身的高程）判，而不是拿整格均值判。**教训：网格分辨率低的时候，「某点的地面高程」有好几个都说得通的算法，选错了不会报错，只在实拍里露出来。**

**岸线暗边画在水面高度上会被岸坡埋掉。** 岸坡一定比水面高，所以按水面高度铺的岸线整条都在地表之下（看不见，但也不报错）。修法是先按世界高度采出一条「贴地岸线」的采样点，再拿它铺带子。

**下凹的水面横截面会劈出明暗两半。** 为了让河有「槽感」，第一版给水面加了负 `crown`（中间下凹）。结果是带子的左右两半各朝一个方向着色，远看像两条并排的色块。修法是水面做平切面，水深改用「中泓深色带」（更窄、更深的一条）表达 —— 这也是参考图的做法。

**描边分级要按结构与用途，不是按地形。** v1.4 的规则是「任一侧地形标记为 outlined 就画」，于是农田、花田的每条边都有墨线，视觉上仍是一格一格。改成「只有跨结构类（陆|水、陆|岩、岩|水、城|其他）才描边」，草|林、草|田、草|花 之间交给**边界过渡装饰簇**去咬合。这里有个副产品：`classNameOf`（用哪种材质画）与描边分级不是一回事 —— 城市与草地共用 land 材质，但城市边界必须收边，所以分级表单独放在 `palette.outlineClass`。

**「过渡」与「次生特征」不是新一层，而是同一层里的两遍。** 一开始想给它们各写一个 layer，但两者都要用植被层已有的物种桶、避让规则（道路/河流/山体）与实例网格，另起一层就得把这些再抄一遍。因此落在 `props-layer.js` 里做成「主植被 → 过渡带 → 次生特征」三遍，共用同一个 `scatter()`。

**「山体占位」必须显式问一次。** 山体是独立几何，`world.heightAt()` 看不到它，于是树会长到山里面去（半截穿出岩壁）。修法是 `MountainLayer.occupancy(world)` 统一对外提供查询，植被与房屋各问一次；山体格只长岩石，并且强制落到「山脚外圈」上 —— 正好得到参考图里的**山脚碎石坡**。这条也顺手解决了一个观感问题：杉树不再从山体里穿出来。（⚠ 这圈的**判据要跟着山体形状走**：见 §15.13 —— 山体从「中环」改成「高度场收脚」之后，碎石的「内径」必须按离脊线的距离判。）

**新增的占位/避让规则都要有量化验收。** 新增的断言里最有价值的几条不是「有没有生成」，而是「有没有越界」：落在山体格内的非岩石道具 = 0；落在河里的道具 = 0；压河/进山的房屋 = 0；河面在河中线上是射线打到的第一个表面（100%）；离河线 0.75 格处已不是水面（98.9%）。这些数字直接对应「看起来对不对」，比参数快照有用得多。

### 15.6 v1.6：贴地视角下的「粘连细线」

**先定位，再动手。** 用户反馈「当前出现很多粘连的线」，现象是贴地视角下多条细长、淡灰、大致平行的半透明带横穿地图，并压在树冠与屋顶之上。定位分了四步，每一步都对应一类可能的根因：

1. **几何坏值？** 遍历全场景（每个 mesh / line / instancedMesh）：无 NaN、无坏实例矩阵；最长三角形边的前几名全是合法大件（底座、网格线、山体），其余 ≤ 2 格。**排除「几何被拉长」。**
2. **实例缩放异常？** 只有 `bridge-piers` 8.38 与 `trestle-piers` 13.46 两个尺度比 > 3，一度被当成嫌疑。查下去发现矩阵里的 `scale.y` 就是柱高（桥面高 − 地面高，单位是世界单位），桥跨水面 8 单位、栈桥跨峡谷 13 单位，完全合理 —— 这是**我自己换算错了**（把它当成「× hexSize 的倍数」）。**排除了一个假线索，也是一个教训：先核对量纲再怀疑数值。**
3. **哪一层画的？** 用同一个贴地视角（仰角 16.7°、距离约 300、星陨城北）逐层开关对照：只关「云影（贴地）」→ 长条全部消失、画面饱和度恢复；只关「道路」→ 长条仍在。**主因锁定云影面片。**
4. **为什么会成这样？** 地形最高 41.8，云影面片挂在 `y = maxRise + 0.6 = 42.4`，共 3 层（相差 0.35）——**等于一张悬在全图正上方、比所有东西都高的薄纸**。再加 2781×2326 的面片（地图的 2.7 倍）配 256 的贴图、`repeat = 7`：1 个 texel ≈ 1.5×1.9 世界单位；贴地视角纵向压缩 `sin(16.7°) ≈ 0.29`，texel 行于是被压成间距 ≈ 2 世界单位的密排细线（用户截图上量到 13px @ 150px/格 = 1.9 单位，对得上）。`depthWrite:false` + `renderOrder 18` 且面片高于一切，所以它盖在树 / 屋 / 山之上。

**修法一：云影改为贴合地形的网格。** 不是调参（把 opacity 调小只是让细线变淡），而是把它的几何关系改对：平面分段后**逐顶点抬到 `world.heightAt + lift`**（步长 `0.6 × hexSize`，覆盖 `1.12 × viewBox`），3 层并成 1 层，贴图提到 512，并把 `sceneKit.maxAnisotropy()` 下发给贴图（掠射角抗走样的关键，取不到就退回 1）。另外两个环境层改为**默认都关**。验收指标是「云影网格相对地形的偏移必须是常数」：实测抽 253 个顶点，`min = max = 1.100` 单位 —— 真正贴地，而不是随地形在几十个单位间跳。

**修法二（顺带发现的同类问题）：扁带只按中心线走高度。** 隔离测试里注意到的现象是：即便关掉云影，道路在某些角度仍会「浮」出一条细边。查 `render/ribbon.js` 的 `pushBand`：它给一条带子推三列顶点（左 / 中 / 右），**三列共用采样点那一个 `y`**，只有中心线跟着地形走。8.8 单位宽的御道横跨陡坡时，一边必然浮起、另一边必然插进地形；再加上御道自身叠了道砟面 / 双钢轨 / 枕木 / 两条边线等 4~6 条不同高度与横向偏移的细带，掠射角下就散成一组悬空细线。修法是给 `pushBand` / `pushCrossBar` 增加 `ground + maxDrop`：左右两列（枕木是四个角）各自取地形高度并钳制在中心线 ±`road.conformDrop` 内；`ground` 返回 `null` 表示该采样点**不贴** —— 桥面 / 栈桥面 / 洞内路面本来就是离地的构件，必须原样保留高度（这是这条改动的关键约束，测试里专门有一条断言守住它）。同一场景两次构建道路层、只差 `conformDrop`，实测左右两列的离地偏差：

| 左右两列离地偏差 | 修复前（三列共高） | 修复后（贴合地形） |
| --- | --- | --- |
| 中位数 | 0.85 单位 | **0.00 单位** |
| 平均 | 1.77 单位 | 1.00 单位 |
| > 1 单位的比例 | 26.4% | **11.0%**（＝桥 / 栈桥 / 洞内段的桥面） |

**修完怎么确认「细线不再由云影产生」？** 逐行统计画面的纵向梯度（水平细线会在少数行产生尖峰）：同一贴地视角下开 / 关云影的曲线中位数为 4.92 vs 4.88，尖峰落在同样的行 —— 两条曲线几乎重合，说明云影这一层已经不再是线条的来源。剩下的横向条带来自道路本身（8.8 单位宽的路面在掠射角下本来就是一条带），属于设计内的观感；若将来还嫌它「像线」，下一步是「远景简化细构件」（按距离把钢轨 / 枕木 / 边线合并掉），本轮未做。

**一条方法论**：这次的三个候选（坏几何 / 实例缩放 / 图层来源）里，前两个用数值遍历就能排除，第三个必须**在同一个相机下逐层开关**才能定死；而真正的原因（面片悬在全图之上 + texel 密度过粗）在数值指标里完全看不出来 —— 只要「量纲」「同相机对照」「像素级测量」三件事按顺序做，就不会停在「看起来像是 X」。

**追加修复：山体峰顶扇面的索引错误（同一轮）。** 云影修完后策划又反馈「出问题的地方是山脉顶部和底部，且各个地方的山脉之间都会连接起来」，现象是每个峰朝四周射出又长又细的白色尖刺、山脉彼此连成一片，边缘还有巨大白片。根因在 `render/mountain-layer.js` 的环缝合：

```js
// 三层缝合：基环→中环、中环→上环、上环→峰顶
const pairs = [[baseStart, ringStarts[1]], [ringStarts[1], ringStarts[2]], [ringStarts[2], apexIdx]];
...
const i0 = inner + k;   // ✗ 第三组的 inner 是「峰顶这一个顶点」，不能 +k
```

前两组是**环对环**（6 个顶点各用各的，`inner + k` 正确），第三组是**环对一点**（6 个扇区共用峰顶）。写成 `inner + k` 之后，k = 1..5 读到的是紧跟在峰顶之后的顶点 —— 而顶点是「每座山 19 个顺序排列」的，峰顶正是第 19 个，所以那 5 个索引落到了**下一座山的基环**上：每个峰因此被缝到邻山的山脚（顶部出问题 + 山脉连起来），最后一排山的 `apexIdx + 1..5` 还会越过顶点缓冲区（底部/边缘的巨大白片）。反馈里「顶部和底部」这个描述本身就是定位线索。修法是一个三元表达式：`const i0 = toApex ? inner : inner + k;`。

**这个 bug 为什么能活到 v1.6？** 因为 v1.5 给山体写的断言全是「顶点级」的：每座 19 个顶点、基部与共享角点误差 ≤ 1e-3、最外环半径 ≤ 0.7 格、雪顶顶点数。这些断言在索引完全错乱的情况下依然全绿 —— 错的只是「哪些顶点连成三角形」。所以补了两条**拓扑级**断言：三角形三个顶点的 `floor(i / 19)` 必须相同（不跨山）、索引必须小于顶点数（不越界）。实测 0 / 1650 与 0 / 1650，且三角形总数正好是每座 30 个（6×2 + 6×2 + 6×1）。

**验证方式值得记一笔**：无法回到旧版渲染时，可以在页面里**把索引缓冲改回错误写法**（只改峰顶扇面那 6 个三角形的第一个索引）再截一张，就得到与修复后**同一相机、同一场景**的前后对照 —— 前一张是干净的锥体山峰，后一张立刻长出满屏白刺。比「凭记忆对比两张不同时间的截图」可靠得多。

### 15.7 v1.7：河流「直来直去」的根因是 `edgeCorners` 取成了镜像边

用户反馈「现在河流变成直来直去的了，河流应该还是沿着六边形网格圆滑生成的」。定位全程用数字，不靠眼睛：

1. **量「采样点有没有深入格内」**：河线应当落在六边形的棱上，所以拿「采样点到所在格心的距离 ÷ 内切圆半径」做指标。结果 river-1 有 **12/31** 个采样点深入格内 > 0.45 格，采样间距最大 **0.546 格**（越过半格），控制点链里出现了 **3.279 格**的一条直线段 —— 而一个六边形的棱长只有 1 格。
2. **量「直线段的两端在哪」**：把控制点链按段长排序，最长的几段都不是「跨过一条格边」，而是**从一条边斜穿到相邻的平行边**，正好横跨整个格心。到这里现象已经收敛成一句可证伪的话：**取到了错误的棱**。
3. **根因**：`Hex.edgeCorners(dir)` 要把「方向 `d` 的邻居与本格共享的那条边」映射成本地块的两个顶点号。原实现写成 `[(d + 5) % 6, d]`，逐个方向验算后发现它**只在 `d = 0`（东）与 `d = 3`（西）正确**，其余四个方向取到的是关于 x 轴镜像的那条边 —— 于是河在四个方向上「借道」了错误的棱，看起来就是直来直去地穿过格心。
4. **修法**：把三个约定摆在一起推导 —— 顶点 k 的角度是 `cornerAngle(k) = 30° + 60k`；顶点对 (k, k+1) 的连线方向是 `60° + 60k`；邻居方向 `DIRS[d]` 的平面角度是 `-60d`（文件头注释里定死的）。令 `60 + 60k ≡ -60d (mod 360)` 得 `k ≡ 5 - d`，所以方向 d 对应的边是顶点对 `(5 - d, 6 - d)`，即 `[(5 - dir + 6) % 6, (6 - dir) % 6]`。修正后的函数注释里把这套推导写在旁边，避免以后又凭直觉改回去。

**这个 bug 为什么能活到现在？** 因为 `edgeCorners` 在全仓库只有一个调用点（`river-builder`），而上一版河流是「tile 路径 + 取中点」，只在少数方向真正用到它，「河大致沿着格子走」这个弱检查一直是通过的。把它逼出来的是 v1.7 把河流改成**顶点图上的寻路** —— 一旦「走一条棱」成为唯一的基本动作，方向映射错一次整条河就走歪。修完之后，「严格沿格边」这条断言（采样点必须落在内切圆与外接圆之间）也从「差不多」变成了精确指标：实测最大越界 **0.0000 格**。

**教训**：这类「只在部分输入下错」的映射错误，光看画面会被归因成「风格问题」（用户描述的是「变直了」，听起来像美术偏好），只有把它变成「深入格内多少格」「最长段多少格」这类数字才能定位。

### 15.8 v1.7：河宽 5.1× 的不一致，与「岸色带写死绝对半径」

用户反馈「河流的宽度有很明显的宽窄，很丑陋，继续优化贴近文明 6 的设计」。同样是先量后改，量出来是两个独立成因叠在一起：

1. **水面宽度本身在收放**：旧版宽度由两项相乘 —— 「走向进度」（河源细、河口粗）与「汇流通量」（汇流后加宽）。实测最宽 / 最窄 **3.1×**，再叠上「支流本来就更细」这条独立规则，全图到过 **5.1×**。
2. **岸色带是绝对半径，不跟水宽缩放**：湿岸 / 河床 / 漫滩三层当时写死 `6.6 / 10.1 / 17.6` 世界单位。河宽是 `3.5 ~ 17` 单位时，窄段就成了「一条细线套一圈 11.5 倍半宽的巨大深色晕」，宽段则几乎没有岸 —— 窄段看起来是「河」，宽段看起来是「一片糊开的水」。**观感的崩坏主要来自这里，而不是水带本身**，这也是「只调水宽不管用」的原因。
3. **修法**：（a）宽度改成**单一常量** `river.width = 0.16`（× 格距）即半宽 3.52 单位，整条河同宽、所有河同宽、支流与干流同宽，删掉「走向进度」「汇流通量」两套参与宽度的逻辑；（b）三层岸色带改成「水带半宽 × 倍数」——`wetScale 0.45 / bankScale 1.10 / floodScale 2.20`，避让距离同理（`propsClearanceScale 1.50`）。水宽变了岸自动跟着变，不可能再出现「细线配巨晕」。
4. **验收方式**：（a）**全线宽度极差**必须 < 1.05×，实测 3.52 ~ 3.52 单位（**1.000×**）、首尾差 0.000000；（b）**没有锥形收放**：河源段半宽与河口段半宽之差必须为 0；（c）**三层岸带严格嵌套**：湿岸 ⊂ 河床 ⊂ 漫滩，实测 1.58 / 3.87 / 7.74 单位，且都等于「半宽 × 各自倍数」。

**顺带修掉的一处副作用**：「共享顶点颜色一致」这项历史遗留失败（最大色差 1.1e-3）在这条改动后自动归零（0.0e+0）。用对照实验（临时把 `channel.depth` 置 0）确认过它与河道切槽无关，成因就是岸色带绝对半径太宽、把「该顶点属于哪一圈」算出了格间差异。

**一句话结论**：把「宽度」从「由位置/流量推导」改成「一个常量」，再把所有依赖宽度的东西都改成**它的倍数**，比反复调参数有效得多 —— 因为前者的错误会以「不同地方不一样」的形式出现，后者不会。

### 15.9 v1.7：浅切槽的三个被否掉的方案

水面要看得见，就必须让河线附近的地表低于水面。这句判断没问题，但「怎么低」试了三版，其中两版被实拍直接否掉：

**方案一（否掉）：把水面按「整格均值 − 常数」给。** 结果是水面一半被地表盖住、另一半浮在地表之上。根因是**参照选错了**：河线是格边，格边处的地面高程是**两端角点的插值**，而当时的 `world.heightAt` 是「格心 → 中环 → 六角均值」的两段线性模型，边上的点根本不是那个值。**教训：网格分辨率低的时候，「某点的地面高程」有好几种都说得通的算法，选错不会报错，只在实拍里露出来。**

**方案二（否掉）：抬高的「岸唇」。** 把剖面做成「满深 → 回升越过水面 → 岸唇回落」，本意是让水带的几何边缘被岸埋住、看起来像一条真正嵌在地里的河。写了个诊断脚本扫全部水带边缘采样点，结果只有约 **27%** 的边缘能达到水面之上 —— 原因不是参数不对，而是**几何预算不够**：地表网格每格只有「格心 + 中环 + 6 个共享角点」，格边附近只有角点顶点，一格以外的地形全靠线性插值，**抬到水面之上的岸唇没有顶点去承载**，插值出来仍然是平的，水带边缘照旧浮在地表上。因此回退成「几何只让水下陷、两岸交给颜色」，并把这条约束写进 `channelOffset` 的注释，避免以后重试一遍。

**方案三（采用）：纯函数下切 + ceiling 钳制。** `channelOffset(x, z) = depth × (1 − r²)`，`r = d /（半宽 × widen）`，槽在水带之外回落到 0；下切处再钳到 `waterY − 0.02`，保证水面永远是最上层可见面。三个连带问题也一并处理：

- **水面会被地形盖住**：水域格、城市格、山体格都不参与切槽，如果水位低于基准平面，水带在这些地方就会消失。所以水位取 `hexSize × 0.005`（略高于基准平面）。
- **山脚与相邻林地之间裂出竖直缝**：山体格不参与切槽而相邻林地切了，两者就差了 `槽深`。修法是山体格不参与丘陵 dome、但**参与河流浅切槽**，并且山体基部环的高度从 `tile.cornerY` 改读 `world.heightAt`。
- **切槽必须是纯函数**：v1.5 的「挖河谷」直接写 `tile.cornerY`，靠「必须在道路与地表网格之前调用」的顺序约束兜住。改成只依赖世界坐标的 `channelOffset` 之后，这条顺序约束不再需要，而且共享角点天然一致（见 §6.2 的第三条不变量）。

**验收指标**：209 个临河角点全部被切到水面之下；横剖面 **102/102** 在河线处低于水面、**98/98** 在半宽处仍在水下、**39/39** 在槽外回到基准平面；临河平原格心最大高度 **0.000000**（切槽不侵入格心）。最后一条尤其重要 —— 它把「河只该切在格边上」这件事变成了数字。

### 15.10 v1.7：跨河桥的漏判 —— 判据的粒度比被判对象还粗

收窄河宽（半宽 3.52 单位）之后出现一个隐蔽问题：道路采样步长约 **7.04 单位**，与河宽**同量级**。于是完全可能出现两个相邻采样点**跨在河的两侧、而没有一个落在河道里** —— 按「采样点是否在河道内」判定就整段判不出桥，路面直接扎进 **2.20 深**的河槽。

修法是补一条**符号翻转**判据：采样点存下带符号的河距 `riverDist`（负 = 在河道里），只要「该点 < 0」或「相邻两点符号相反」就保桥。跨河段落在陆地上，`hexes` 标记覆盖不到，所以还要按采样点补标 `bridgeVia`。

这条的验收方式值得记：断言不去数「生成了几座桥」（那个数会随采样相位抖动），而是锁不变量 ——「凡是被标为跨河桥的陆地采样点，它自己或左右邻点必在河道内」。实测 18 个陆上跨河桥采样点、异常 **0**；再加一条「没有桥面被水淹」（最低桥面 3.41 > 水面 0.11）。

**教训：判据的粒度不能比被判对象粗。** 当「离散化的步长」和「要判别的特征尺寸」接近时，所有「点是否落在 X 里」的判据都会随机漏判，必须改成对**区间**（这里是符号变化）的判定。

### 15.11 v1.7：山体「单格成山体、连续格成山脉」是连接问题，不是参数问题

需求方给了参考图（《文明 6》）：地块是平的，山脉自己是一个有高度的体。要求很具体 —— **单格的山脉要成山体，连续的格子要成山脉**。第一版（v1.5 那套「基环 + 中环 + 上环 + 脊冠环 + 中心」）在参数上怎么调都不对，做了诊断脚本才定位到是**连接方式**错了，一共三处；后续又补了一条簇级约束：**连续山簇只保留簇外边界的落地墙，簇内共享边不再逐格立柱**，否则视觉上仍会退回「六棱柱拼装」。

**问题一：主轴取自「簇级 PCA」。** 旧版对整片山脉簇做 PCA 求主轴，再让每个格沿这个方向拉长。诊断脚本实测 121 格的脊线方向与最近的六边形邻居方向**偏差 6.6°~19.1°** —— 也就是说脊线是**斜穿格心**的。这直接导致相邻两格的主轴不同向，脊线在格边处各走各的。修法：改成**逐格局部取向**，对 6 个方向打分（`Σ max(0, dir_d·dir_k)` + 「邻居正好在该方向」加 1.5），在 3 组反向对里取最优 —— 主轴从此**只可能是六边形方向**，实测 121 格角差全部 **0°**。

**问题二：连续性靠「两侧各算一遍」而不是「共享参照」。** 旧版让每一格各自算自己的脊线长度，结果两格在共享格边上算出的端点**不是同一个点**。诊断脚本实测 **15/15 对相邻山格的脊顶全部断开**（100% 有缺口）。修法是把这个决定**上移成共享量**：`sharedEdgeH(tile, d) = edgeLevel × (两侧峰高的平均)`。平均值是对称的，所以两侧算出**同一个高度**；再把主脊端点定义成 `Hex.edgeMid(tile, dir, size)`（共享格边中点，且 `edgeMid(A, d) ≡ edgeMid(B, d+3)`），于是两侧算出的**是同一个世界坐标**。实测 490 对相邻山格共享格边高差 **0.0e+0**、118 对脊顶端点位置偏差 **3.6e-15**。这和「共享角点」「共享顶点色」是一个套路：**只要两侧都在算同一个东西，就一定会分叉；要它不分叉，就必须让两侧算的是同一个参照。**

**问题三：T 形路口（一格有 ≥3 个山邻居）压根没连。** 旧版只处理「前后」两个方向，第三条腿被当成「侧翼装饰」。就算问题二修好了，直行处连上、岔口处仍然断。修法是把连接**从「两条腿」改成「格边」**：任何一条两侧都有山的格边都取共享高度，支脊只是沿这条边再架一条较低的脊 —— 于是直行处与岔口处用的是同一套规则，不需要为 T 形单开分支。连带地，测试断言也不能再比「A 的前端点 == B 的后端点」（那要求两格互为前后，岔口不满足），改成比**「端点落在共享格边中点上」+「共享格边两侧同高」**这两条更弱但更普遍的不变量。

**问题四：单格山脉在结构上不可能存在。** 这条是用户直接指出的。旧版有一条「孤立山点软化」循环：把所有 6 邻无山的山格还原成普通地形。它的本意是「避免草地上突兀地立着一座孤峰」，但结果是**整张图 0 座单格山脉** —— 与需求正好相反。删除该循环，并给孤峰一条 `isLone` / `loneScale` 规则（单格成山体，但比整条山脉矮一点，实测孤峰最高 22.24 单位）。教训：**清理规则要检查它是否把某个需求类别整体删空**；「孤立点软化」清掉的不是噪声，而是一整类形态。

**问题五（实拍才看出来）：峰高全等，整条脊排成一列等高的锯齿。** 前四个问题修完之后，连续性与取向都对了，但实拍里山脉像一条上下等高的锯子。根因是剖面 `mid = 1 − amp × (1 − bump)` 让每一片里的**所有峰都到满高**，变化只来自横向偏移。修法是给每一个峰乘一个 `crestGain`，并**归一化到最高峰 = 1** —— 这样峰高有高低差，而 `peakHeight` 仍然精确等于「这一片的最高峰」（否则「峰高参数」会同时被峰数摊薄，语义漂移）。同一轮还把脊顶半宽从 0.075 / 0.125 的窄刃放宽到 0.13~0.41 格半径：**旧版实拍读起来是一排薄刀片，不是山体**，这也是「单格成山体」在观感上的最后一环。

**这次的方法论收益有两条：**

1. **「连续性」要当成不变量来测，不能靠眼睛看。** 三条断言把两处致命错误变成了数字：主轴角差 = 0°、共享格边高差 = 0.0e+0、脊顶端点位置偏差 = 3.6e-15。第二条尤其是关键 —— 它是**用实际几何顶点缓冲**验证的（读 `position.array`，不是读规划数据），所以能同时抓住「规划对了但生成错了」。
2. **测试断言要跟着设计一起改，而且要改成更普遍的那一条。** 「A 的前端点 == B 的后端点」在 T 形路口必然失败；换成「端点落在共享格边中点」+「两侧同高」之后，规则覆盖了全部方向组合，也不需要为岔口写特例。

### 15.12 v1.7：山体「悬空」不是高度错，而是壳体底部开口

这次用户反馈的现象不是「山离地一点点」，而是**掠射视角下能从山体下方直接看穿**，整片山脉像浮在空中。诊断脚本把问题钉死了：山体网格的自由边界全部落在**基部外圈**，数量正好是 `121 片 × 12 = 1452`；另有 **1078** 个外圈顶点高于地表，最大离地 **19.5** 单位。再做一组同机位对照：正常材质时底部透空，改成 `DoubleSide` 立刻“填满”，这说明根因不是 `world.heightAt()` 错，也不是山脚整体抬高，而是**壳体底面根本没封住，背面剔除把内部直接暴露出来了**。

修法分两步，而且两步缺一不可。第一步是把跨格鞍部降下来：`edgeLevel` 从 `0.55` 降到 `0.40`，`taperLevel` 从 `0.34` 降到 `0.24`，先把「整簇像台地」的问题打掉；第二步才是几何补面：外圈下面新增一圈**同 XZ、高度 = 地表**的落地裙边，并用**竖直墙**把外圈补到地面。这样每片山体从 **60 顶点 / 106 三角形**变成 **72 顶点 / 130 三角形**，新增预算全部用在“落地”上。

这次还有一个测试层面的教训。最初我直接拿 Float32 顶点坐标反喂 `world.heightAt()` 校验裙边，结果在格边与临河门槛处打出了 **2.2** 单位的假误差；根因是量化误差把点判进了另一格，触发了不同的切槽分支。后来把断言改成两条更稳的结构性约束：**裙边与规划共享点同位**、**自由边只允许落在裙边上**。实测回归后，自由边只剩每片裙边底环那 **12** 条，裙边与地表最大差 **4.8e-08**，正常材质与 `DoubleSide` 的视觉差异也不再表现为“一个漏空一个填满”。

### 15.13 v1.7：山体「格子之间没连上」是**每片各自算高度**的结构后果

用户接着反馈：**外围正常了，但内部还是一格一个山盖、格子之间没连上**。这一轮的诊断比上一轮更有说服力，因为它推翻了两个看起来最合理的猜测：

1. **不是「有洞被背面剔除」**。同机位拍 `FrontSide` / `DoubleSide` 两张图**完全一致** —— 有洞时双面一定会填上（§15.12 就是这么定的案），所以这次不是开口问题。
2. **不是「两侧没对齐」**。实测内部共享边两侧的基部环**高差 0.00e+0、平面偏差 4.4e-15** —— 位置和高度都是逐位相同的。

也就是说，**几何是连上的，形状是错的**。把样例格的 12 段「基部高度 vs 中环高度」打出来后一眼就看到了：

```
j= 0 d=0 内部  base=0.373  mid=0.328  lip=+0.045   ← 基部比中环高 → 唇边
j= 7 d=4 内部  base=0.379  mid=0.334  lip=+0.045
j= 8 d=4 内部  base=0.399  mid=0.351  lip=+0.048
j= 2 d=1 外缘  base=0.000  mid=0.319  lip=-0.319
```

- 跨格那几侧的**基部环比中环还高**（`lip > 0`，883 个内部方向全中）⇒ 坡面从脊顶往下走，先降到中环 0.33，**又抬回格边 0.40**：一道**唇边 + 环状凹槽**。
- 中环在**所有方向高度几乎相同**（0.26~0.35）⇒ 它是一圈**近水平的台肩**。台肩 + 拉长的脊 = 实拍里的「六棱台 + 上面扣一个盖」。

根因是**三套彼此不相干的高度公式**：外圈读 `edgeH / cornerH`（角点还要再取三条边的平均），中环取「裙高 / 基部高 × 0.88」的较大者，脊冠再乘 0.74。它们只在 12 个采样点上恰好对上，中间怎么走完全靠各自的公式 —— **只要两侧都在算同一个东西，两侧就一定会在采样点之间分叉**（和 §15.11 的端点、§6.2 的共享角点是同一个道理，只是这次发生在“同一片内部的两圈之间”）。

修法是把这个量**上移成簇级共享高度场**：

```
field(x, z) = max( 各片的脊坡, 各条簇内共享边的鞍部锥 ) × 簇边界收脚
脊坡   = 最近脊点高度 × (1 − (d / footRadius)²)
鞍部锥 = edgeLevel × 两侧平均峰高 × (同一衰减曲线)
收脚   = smoothstep( min(到簇外边界线段的距离) / 0.5 格 )
```

- **取 max 而不是求和/取大**是关键：同一个点上只有一个值 ⇒ 相邻两片**逐点相同** ⇒ 唇边、凹槽、折面在机制上不可能出现。实测 490 条共享边的鞍部高度误差 **0.0e+0**、横向剖面 `20.3 → 19.3 → … → 0.0` 单调下降到地面。
- **鞍部锥不能省**：T 形路口、以及两条平行脊之间的相邻格，光靠脊坡会在格边上落到接近地面（实测 0.12 单位），山脉会被切断 —— 这正是 v1.7 判断里「连接要按格边、而不是按前后两条腿」的那条经验。
- **脊端内收 `crestEndInset: 0.90`**：脊端原本落在共享格边中点上，而外圈那 12 个点里也有同一个点 ⇒ 外圈 → 脊冠那一小片扇面**自交（折鳍）**。内收之后跨格高度交给鞍部锥，位置不再重合。
- **脊端不能当“唯一高度来源”**，它只负责沿脊的形状。

这一轮踩到并修掉的两个**形状反例**值得单独记下来，它们都是「看起来像参数问题、其实是公式选错了」：

1. **衰减曲线用 smoothstep ⇒ 山体被读成「薄鳍站在平盘上」**。smoothstep 在近端掉得太快（0.41 格处只剩 0.46 倍峰高），坡面从脊顶直落。换成 `1 − (d/R)²` 后 0.41 格处还有 0.72 倍峰高（与旧版屋脊半宽处的 0.74 接近），山体才有体量。
2. **坡面顶出格边 ⇒ 簇外边界立起 15.7 单位的高墙**。山体按「离脊线距离」收脚，而格子的**侧角点离脊只有 0.5 格**：坡面在那里还有 0.6 倍峰高，被格边一切就成了高墙（实测 191 个簇外边界点离地 > 6 单位，最高 15.66）。修法是加一道**簇边界收脚**，半径取 **0.5 格** —— 这个值不是拍出来的：它正好等于「格边中点 → 相邻格边端点」的距离，所以**所有格心与鞍部到簇外边界都 ≥ 0.5 格**，收脚碰不到它们（实测收脚后簇外边界点离地均值 **0.00**、最大 2.20）。

**测试口径也跟着换了**，这轮换了三处：

- 旧的「主脊端点落在共享格边中点」作废（脊端已内收），换成 **「鞍部 = 高度场在共享格边中点的值」** —— 直接盯住“两侧同一个函数”这条不变量。
- 旧的「自由边只落在裙边上」作废（簇内不再立柱），换成 **「共享格边两侧逐点重合」**（用实际顶点缓冲，位置 + 高度）与 **「壳体边界只落在贴地的裙边底边上」**（边界边 400 → **28** 条，且全部离地 0）。
- 新增 **「跨格方向的坡面没有唇边」**：从格边走到脊顶一路只升不降 —— 这条正是唇边/凹槽的直接回归线（**只看“格边 → 第一个脊顶”那一段**：过了脊顶本来就要下降，把它算进来会在 200 条采样线上误报 115 条）。

代价：`midRadius / midRadiusAlong / midHeight / jitter` 与 `cornerH` 派生量全部作废并删除（每片顶点 72 → **60**，全图 10866 三角形）；`ridgeScree` 的内径判据失效，需要改成「离脊线的距离」，本轮先在文档里标为遗留（实测岩石会埋进新坡面里）。
> ⚠ 这一处遗留已在 **v1.9** 一并处理，而且处理方式与当时的判断不同：v1.9 不再用「离脊线的距离」，而是直接用 `occupancy.thickness(x, z) < ridgeScreeClearance`（**与山体形状同源的厚度判据**）；同时 v1.9 整套几何又被噪声场替换，本段描述的 60 顶点壳体已不存在（见 §15.16 与 §6.7）。本节保留原样作为当时的记录。

### 15.14 v1.7：还有细缝 —— 「面片接合」需要**焊接顶点** + **山脚不低于地表**

上一轮把高度收敛成一个场之后，方向对了，但用户仍反馈「少量裂缝或缺口」，并要求「让所有面片可以接合，检查顶点有无连接」。这一轮把「裂缝」拆成两个可量化的原因，各自修掉：

**① 顶点没焊。** 山体是**逐片**写顶点的：相邻两片的外圈共享点、以及贴地的裙边点，都是同一个世界坐标，却各写了一遍 —— 位置重合、索引独立。后果有两层：只要有一丁点量化误差，掠射角下就是一道细缝；更隐蔽的是**顶点色** —— 山体的分带 / 雪线是按「该片自身峰高」算的，缝两侧各算一份，同一个点在两侧可以拿到不同颜色。量化实测：**7260 个顶点里只有 5608 个唯一位置，1212 个位置被重复写（多出 1652 个顶点）**。
修法是把 `pushVertex` 改成**按位置焊接**的顶点池（1/512 单位量化）：同一个世界坐标只写一次，颜色取首个写出者的算法结果。焊接后 **5604 顶点 / 0 个重复位置 / 三角形数不变** —— 顺带省掉 23% 顶点。

**② 山脚会低于地表。** 高度场只描述山体自身（离脊越远越接近 0），但地表还有**丘陵微起伏**（实测山格相邻地块的地表最高 0.52）与**河床浅切槽**（最低 −2.20）。不处理时实测有 **10 处地形从山脚里穿出来**（最大 0.53 单位），而且裙边会变成「朝上」的反墙（地表比外圈还高）。修法是山体表面高度取 `max(高度场, world.heightAt)`：山脚永远骑在地表之上，反墙也不可能出现（实测「低于地表的点 = 0」）。

**测试口径也跟着改了两处**（都是「布局假设」失效引起的）：

- 焊接之后**不再有「每片固定 stride」**，所以断言不能再用 `i * stride + j` 取顶点。改成：用**位置表**（量化位置 → 顶点下标）验证每片的外圈 / 脊冠环 / 中心线点都在，并用山体层新暴露的 `vertRole` / `vertTile` 元数据给三角形分组做绕序检查。位置表的量化必须与焊接**同一分辨率**（1/512），并且查点要在 ±1 邻域里找 —— 用 1e-4 这种更细的粒度，会因为「值正好落在量化边界上」报出 37 个假“缺失”。
- 落地墙的分组也变了：外圈高度取过 `max(…, heightAt)` 之后，贴地处**裙边顶点就是外圈顶点**，「三个顶点都是外圈」的三角形现在也是墙 —— 不把这种算进去，墙会被误判成坡面（实测 944 → 54）。

新增的断言：`顶点已按位置焊接（重复位置 = 0）`、`每片的外圈 / 脊冠环 / 中心线顶点齐全`、`外圈高度 = max(高度场, 地表)（低于地表的点 = 0）`、`跨格鞍部 = 共享格边高度（焊接后两侧就是同一个顶点）`。

删这段时暴露了一个更值得记的问题：**那段截图代码顺手点了「正射（主）」与「重置视角」，而这两个按钮在别处根本没有断言。**

- 「低透视」是有断言的（`mode() === 'perspective'`），但**切回正射没有** —— 覆盖是单边的；

新增 / 改写的断言：`相机可切回正射（主）`、`点「重置视角」后相机回到初始装配（拖拽 / 缩放被撤销）`（自带自检：扰动必须 > 10 单位，否则这条断言是空转）；删除 `交互后截图已生成`、`过程截图 preview.png 已生成（不入库）`。前者的基准不写死 rig 常量，而是在**加载完成、零交互时**抓一次相机位置，避免把 `main.js` 里的初始装配值在测试里再抄一份。

### 15.16 v1.9：山体「格子感」的根因是逐格造型；水深「不是数据」就没有深度过渡

这一轮的起点是两条用户反馈：「山脉要更生动、更拟真」「河流、湖面、海洋要用画面深度做水面与地面的过渡」。两条最后都归结为同一句话：**形状/深度必须只有一个来源，而且必须是世界坐标的函数。**

**（1）山体的格子感来自「每格各自造型」，不是参数没调好。**

v1.7 已经把高度收敛到「全簇共用一个场」，但那个场是 `max(各片的脊坡, 各条簇内共享边的鞍部锥)` —— 脊线的位置、峰数、峰高仍然是**逐格算出来**的。结果就是：相邻格在共享点上是接上了，但每一格内部仍各自鼓起一个「六棱台」，实拍读成「一格一个盖」。

修法是**把造型整体搬出格的概念**：新建 `world/mountain-field.js`，形状 = 高度包络 × 轮廓掩码 × 椭球穹丘 × (1 − 脊深 × (1 − 脊状噪声))，只用柏林噪声与簇级几何，渲染层退化成纯粹的「采样 + 建网格 + 上色」。三个副作用都是好的：

- 「裂缝」从「需要两侧对齐」变成「**机制上不可能**」—— 场只依赖 (x, z)，两侧读到的就是同一个值，v1.3 以来那一串「共享点 / 对称函数 / 求平均」的技巧整族退场；
- 山脚可以**越过簇边界**（`taperOuter > 0` + 轮廓噪声），接触线不再是格边折线（实测 232 / 236 条簇边界边外侧仍是山体）；
- 网格改成「整簇一张共享三角格」，格子感从结构上消失。

中间有两个被否掉的写法，都值得记：

- **把 ridged 噪声直接当高度**（阈值切出一张脊网）：实拍读成「一堆小尖锥 / 碎石堆」。正确用法是让它当**刻刀**：椭球 × (1 − carve × (1 − ridged))，谷底 = 椭球 × (1 − carve)、脊顶 = 椭球。
- **表面三角沿用「背离格心」定向**（那是逐格壳体的判据）：参考点从「脊线」变成了「格心」，判出来的其实是水平方向，于是**一半三角形翻面**（实测 19501 / 40486）。高度场不会悬垂，判据只有一条：`ny ≥ 0`。

顺带修掉两个「同源」问题：`refH` 必须取**本簇实测最高峰**（用配置里的理论峰高实测得到 `snowPeaks: 0` —— 场的实测峰值只到包络上限的约 0.74，雪线吊在够不着的地方）；山脚碎石带的判据必须改用 `occ.thickness(x, z)`（旧版按「离格心的距离」判，而山体按「离簇边界的距离」收脚，两者不同源 ⇒ 岩石整块埋进坡面）。

**（2）「水深」在 v1.8 之前根本不是数据，所以谈不上过渡。**

v1.8 给了统一水位，但水格地表恒为 0（与陆地共面）—— 于是「浅水 / 深水」没有几何差异，任何深度效果都无数据可依。这一轮把水下地表做成真实几何量：

- **敞水深度场 × 岸坡因子**，并且深度场**铺在格心三角网上插值**。为什么必须插值：相邻水格深度不同（离岸越远越深），各用各的就会在共享格边上留下「一格一格的水深台阶」，水面半透明后读成一圈圈梯田 —— 实测连续版本的最大跨格差 0.0007。
- 第一版写成「**每格一个碗**」（角点 0 / 中环 midRing / 格心满深）：碗底的 0 落在该格**全部六个角点**上，连深海中央也是 0，整片海立刻变成一格一个洼的六边形凹凸纹（实拍确认）。根因是把「岸线两侧必须齐平」这条正确的要求**推广到了全部角点**。角点只有一种情况该是 0：它真的踩在岸线上。
- **画面深度过渡**（`render/water-depth.js`）：半分辨率深度预通道（只画地表 + 山体，**水面自己不在里面**）+ 水面材质 `onBeforeCompile` 注入。踩到三个坑，都属于「单位 / 时机」类：
  · **`gl_FragCoord` 的单位是绘制缓冲像素**，不是 CSS 像素；而且本模块比 `sceneKit.resize()` 先创建 —— 只建一次会拿到 canvas 默认的 **300×150**，建出一张 150×75 的深度图、UV 全错。改成「每帧自检尺寸」。
  · **窗口深度是非线性的**：同一个 `depthFade` 在正交 / 透视下若不逐帧折算，观感完全不同；相机有俯角时还要除以 `|cos|` 折回竖直方向。
  · **8 位读不回这个量级**：水深对应的窗口深度差只有 1e-4 量级，用 `Uint8Array` 读回来全是量化噪声（实测把 1.654 的水深读成 9.46）。验证脚本必须用浮点 RT，深度贴图本身也必须用 24 位（16 位在 `far ≈ 4000` 时每级 ≈ 0.06 单位，而过渡区间只有 2 单位）。
- **删掉了一处重复逻辑（蜂窝纹的真凶）**：顶点色里还有一条「浅水带」（按 `distToLand / 3.2` 提亮水面）。它必然一格一格：同一个水格上，格心顶点的权重是「本格 + 6 邻」、角点顶点是「压在角上的 3 格」，两套权重算出的 `distToLand` 平均值不同 ⇒ 每个六边形内部一圈色阶。定位手段是把水面的「贴图 / 顶点色 / 半透明」逐项关掉各拍一张对比。**同一个量不能有两套来源** —— 这是这个项目里第二次栽在同一句话上（第一次是 v1.7 的「每片各自算高度」）。
- **顺手清掉的重构遗留**：山体形状搬进场之后，`MountainCluster` 为逐格造型产的 `axis / perp / fwd / back / hasFwd / hasBack / clusterId / clusterSize / clusterIsLone / boundaryEdgeCount / neighborCount` 全都没有消费者了（连挑主轴的 `pickAxis` 一起删）。留下它们的代价不是性能，而是**下一个人会以为它们还在起作用**。

新增 / 改写的断言：`山体层已生成（簇级噪声场 + 共享三角格网格器）`、`山体面数在预算内（≤ 2.5 万三角）`、`顶点已按位置焊接`、`表面顶点高度 = max(场, 地表)`、`没有塌陷面 / 翻面 / 越界`、`山脚越过簇边界`、`雪带存在于顶点色里`、`水下地表在岸线处为 0`、`水/水共享边上深度场连续`、`离岸每远一格水就更深`、`深度通道读出来的水深 = 真实水深（俯视对拍）`、`深浅在同一套尺度下被区分开`、`山簇派生标记只保留被消费的四个字段`；删除 `主轴必为六边形邻居方向之一`（随逐格取向一起退场）。

同时修掉两条**曾经不稳的断言**，都属于「测试自己写错」：

- `浅切槽落在格边上` 的采样方向**反了**。河沿格边走 ⇒ 河道中心线就是格边，角点本身在河线**上**；而从格心朝角点退 6% 是退到离角点 20.7 单位的地方（早就出槽）。正确写法是从**角点朝格心**退 6%（离格边还有 1.1 单位，槽半宽 4.4）。这条断言在「水位统一」之后才暴露，因为那时它才开始测出真实结果。
- `点「重置视角」后相机回到初始装配` 的收敛判据写成了「相邻两次采样位置没变就收工」。软件渲染偶有一段时间不推进帧，两次采样看起来一样，于是**把「还没收敛」误判成「已到位」**（残留 79.170）。改成「一直轮询到偏差真的回到 1 以内」，实测 0.660。教训与 §15.15 记的那条同源：**阻尼系统的断言既不能用固定等待，也不能用「看起来不动了」当收敛**。

### 15.17 v2：山体「太平」是**体量形态**错了，不是起伏参数没调好；顺带把 LOD 做成「同一场的不同采样」

这一轮的起点是用户反馈「当前的山脉有点太平了没有起伏，参考这三张图（文明 6 风格）优化生成逻辑与噪声」，并明确「地图片面的数量级限制可以忽略，先力求还原参考图」。

**（1）先量化，再动手。** 「平」是个模糊词，先把它变成数字：

| 实测指标 | v1.9（椭球穹丘） | 参考图 |
| --- | --- | --- |
| 体量比 = 峰高 / 半高半径 | **0.14** | ≈ 1.0 |
| 最大山簇尺寸 / 峰高 | 34.8 × 18.2 格 / 1.30 格 | 2~4 格宽窄带 |
| 山体主体平均高度 / 峰高 | **0.63**（一片平台） | 0.3~0.4 |
| 脊状噪声对造型的贡献 | **±13%** | 主要项 |
| 单格孤峰明暗图 | 一圈同心环 | 6~9 条放射脊 |

三条根因，全部落在「形态」而不是「参数」上：

- **椭球的几何方向是反的**。`dome = 1 − ru² − rv²` 是「倒扣碗」：顶平、根陡。真实山的横剖面必须是**凹形**（顶陡、根宽、带裙摆）。这两者不是调参能互换的 —— 换公式：`belt = (1 − nd)^flankExp`，`flankExp > 1`。
- **椭球只有一个极大值**，而脊状噪声只做减法（`shape = dome × (1 − carve×(1−rg)) ≤ dome`）⇒ 每簇最多一个峰，**永远长不出「峰—鞍—峰」**。
- **噪声的实测值域不是满量程**。`ridgedPerlin2` 的 min/p05/中位/p95 = 0.11 / 0.34 / 0.62 / 0.87。旧写法 `1 − 0.5×(1 − rg)` 只在 0.67~0.93 之间飘 ⇒ 噪声实际只贡献 ±13% 起伏。修法是把它**拉到有效量程**（`crestSharp`）而不是换个噪声函数。

**（2）新形态：蜿蜒窄脊带 + 低岩台**（公式见 README「山体」节）。四个零件各自解决一件事：

- **脊带**（半宽 `beltHalfWidth`）：把「山体宽度」从「整簇范围」里独立出来 —— 这是体量比从 0.14 变到 2.5 的那一刀。
- **峰高沿走向调制**（`summitScale` / `summitFloor`）：峰—鞍—峰。
- **放射脊**（`spurAmp` + 角向取样）：单格 / 短簇用 `perlin(cosθ·k, sinθ·k)` 在噪声空间画圆 —— **天然以 2π 为周期**，因此不需要再写一个周期噪声函数（少一个基础件）。
- **低岩台**（`baseLevel`）：山格本身要是一块岩石高地，但又必须足够低。实测峰:底 = 3.23（旧版整簇都在 63% 峰高，这就是「平台感」的来源）。

**顺带解决了「peakHeight 到底代表什么」**：`body` 是三个各自 ≤1 的噪声相乘，极大值不落在同一点 ⇒ 裸场峰顶只有包络的 0.6~0.8。v1.9 的文档里于是写着一句「实测峰值只到包络的约 0.74」（雪线因此吊在够不着的地方）。v2 在编译时**量一次实测峰顶、把整簇场缩放回去**：`peakHeight` 从此就是「这座山有多高」，与任何噪声参数解耦。这比「上调 peakHeight 补偿」正确 —— 补偿系数会随任何噪声参数改动而失效。

**（3）山脉的分布也一起收窄 —— 但只调 `ridgeShare` 做不到。** 实测（`relief.scale` × `ridgeShare` 全扫）：

| ridgeShare | 山格 / 占陆地 | 平均簇宽 | 最大簇长宽比 |
| --- | --- | --- | --- |
| 0.10 | 28 / 7.4% | 3.6 格 | 1.29 |
| 0.22 | 52 / 13.8% | 5.1 格 | 2.02 |
| 0.42 | 121 / 32.2% | 6.1 格 | 1.92 |

**平均簇宽反而随份额上升而变大，长宽比一直在 1.3~2.0 —— 永远收不出窄带。** 原因是结构性的：山格 = 「起伏通道的高分位集合」，它的形状由这条通道的**极大值**长什么样决定，而 `fbm2`（值噪声叠加）的极大值是**团块**。把通道换成 `ridgedPerlin2`（`|n| → 0` 的等值线是**曲线**）之后，同一个 top 22% 得到的就是蜿蜒窄脊带 —— 实测平均簇宽 2.9 格、最长 14.7 格、长宽比 2.76、占陆地 16.8%。**「换噪声」与「调份额」的区别在这里是定性的，不是定量的。**

**（4）LOD：因为场是 (x,z) 的纯函数，这件事几乎是白送的。** 「同一片山体用不同间距采样」得到的必然是同一个地形的不同精度版本。三个设计点：

- **块 = 山簇 ⇒ 结构上没有 T 型缝**。簇边界处场值恰好归零、落地墙把边界压到地面，所以相邻簇即使级别不同，接缝处两者都在地面高度上。这条是「不需要缝合带 / 裙边」的全部依据。
- **判据必须是屏幕像素密度，不能是裸距离**。本项目有正交 / 透视两种相机，而**正交是默认档**：它没有距离衰减，裸距离判据在它上面会给出完全错误的精度。同一条像素式子对两种相机都成立。
- **滞回阈值必须取相邻两级的几何平均**（对数中点 `√(dc×dn)`）。第一版拿「当前级自己的 detail × (1+h)」当阈值，它落在自然切换点的**错误一侧** —— 实测两个方向都会跳，等于滞回完全没生效（测试改成「从细一侧来 / 从粗一侧来各自保持原级」之后才把这个错抓出来）。

**诚实的成本结论**：四级全部预建（实测 525ms，占启动约 12%），内存约 8MB；默认视角实际渲染 **19.5%** 的三角形。它省的是 GPU 顶点处理，**不减少建造耗时**（预建是各级之和，几何级数，粗级几乎不要钱）。当前地图规模下 GPU 不是瓶颈，所以这一条的意义在「编辑器产出大地图之后」（几千个山格 → 总面数上 50 万、阴影通道也变重）。因此做成「架构就位、默认开、一键关」，并把已知边界写下来：块粒度是「一个山簇」，超长单簇内部无法混级 —— 若编辑器产出那种地图，再按 ~6 格分段 + 一圈裙边处理。

**（5）两个顺手修掉的老问题。**

- **`compile` 被调 4 次**：`plan()`、`occupancy()`（植被 / 村落各一次）各自编译一遍场，每次 16ms 建场 + 每格 7 点采样 3ms ≈ 76ms 白花。改成按 world 用 WeakMap 记忆化（**就地改配置数值时必须显式 `clearCache()`** —— 这是记忆化的代价，写在注释里）。
- **岸线两侧不齐平（陆侧丘陵）**：水格有 `shoreEdges`（邻格非水）并在岸线归零，但**陆侧的丘陵 dome 没有**。dome 的半径（0.76 格）比内切半径（0.866 格）小，所以它会一直铺到格边 —— 实测 3 处岸线：水侧 0、陆侧 0.13~0.35，岸线上多出一道小坎。修法是给陆格也算一份**镜像掩码** `waterEdges`，两侧共用同一个 `edgeFade`；断言也改成「非 0 的必须**确实在河道内**」（旧写法「非 0 且 ≤ 切槽深」会让 shoreFade 一旦坏掉正好躲进同量级里，覆盖失效）。

新增 / 改写的断言：`逐簇归一化：实测峰高 === 该簇 amp`、`峰高落在配置区间内`、`山体是窄脊带（体量比 ≥ 1）`、`脊线剖面多峰且峰谷交替`、`孤峰有放射脊 / 冲沟`、`脊带之外是低岩台`、`山脉分布是窄带`、`LOD 级别表是「细 → 粗」且与配置一致`、`关掉 LOD 时锁在最细一级`、`LOD 判据：正交与距离无关、透视与距离成正比`、`LOD：拉近变细、拉远变粗（单调）`、`LOD 滞回：切换带内两个方向各自保持原级`、`LOD 逐级闭合（每级都要单独过几何红线）`、`LOD 默认视角下真的省了面`；删除 `山体面数在预算内（≤ 2.5 万三角）`（该预算随用户决定作废，改成「逐级面数递减 + 默认视角省面比例」）。

### 15.18 v2.1：演示大片山脉是「手工数据」，山谷的验收必须用 A/B 对拍

这一轮的起点是两条需求：「在左下角生成一大片 4×5 的连续山脉给策划参考」+「单格山脉地块上也要能出现与山脊相对的山谷，更模拟现实多样的生态」。

**（1）手工块与比例生成的关系，必须先说清楚。** `ridgeShare` 是**按排名切分**的，它不保证任何具体位置 —— 所以「左下角要有一大片」在原理上不可能靠调参得到。做法是显式加一块手工数据 `relief.demoMassif`（偏移坐标 4×5），并明确三条约定：

- **手工优先于比例生成**（放在排名切分之后），但**不计入**目标份额；
- 只跳过**地图边界水格**（`border`，海岛轮廓外圈）—— 那是岛屿的边界，改成山会把轮廓切碎；块内的普通水格照改（做成「山体探进海里」），这样块内永远是一整片、**连成 1 簇**（实测 20 格全成山 / 1 簇 / 18 格是新改建的 / 含 1 格沿海水格）；
- 「山脉分布是窄带」这条断言必须**剔除演示块** —— 否则它会退化成「演示块有多大」的间接度量（实测：含演示块时占陆地 21.5%，剔除后 17.1%）。
- ⚠ **必须放在水下地表预计算（`distToLand` / `bedDepth`）之前**，否则新山格会带着「海底深度」进渲染；`landform` 也要一起从 water 改成 plain，否则「山格却是水地貌」会自相矛盾。

**（2）手工块立刻暴露了两条形状规则的必要性 —— 又是「先量化」。** 20 格连成一片之后，实测：

| 现象 | 数字 | 结论 |
| --- | --- | --- |
| 大块的脊带只有 2.3 格宽，而簇有 10 格宽 | 体量比 / 观感「一条薄脊 + 一大片岩台」 | 脊带宽度必须随簇宽增长（`beltWidthGrow`） |
| 改完脊带宽度后 | **体量比 0.79**（簇 10 格宽、峰 1.3 格高 = 缓丘） | 峰高必须随簇增大（`peakHeightGrow`） |
| 两条都加上 | 簇 22 格 / 峰高 1.66 格 / 脊带半宽 4.21 格 / 体量比 1.04 | ✓ |

两条规则都刻意**只对 ≥ 6 格的簇生效**（`beltWidthGrow` 靠「单格 extV ≈ 1 格，增长项打不过下界」自然实现；`peakHeightGrow` 用 `clamp((size − 5)/12)`）⇒ **单格孤峰与小簇的形态与峰高完全不变**（实测孤峰仍是 1.10~1.22 格）。

**（3）山谷：机制简单，验收很难 —— 单点采样在这里是错的。** 机制本身是在脊带局部坐标里沿一条与脊线平行的中心线挖高斯槽；单格簇的脊线退化成一个点（`endCore = 0`），所以另给谷一个朝向（由哈希给出）⇒ 单格山峰可以不对称。

踩到的坑是**验证方法**：第一版在「谷心线 ±偏移」两侧各取一个点比大小，结果读数一片混乱（有的 96%、有的 169%），而且**无谷的对照簇两侧就能差 2.04 倍** —— 原因是脊线本身在蜿蜒、且谷在两端会收口，单点对比根本分不出「谷」与「蜿蜒」。改成 **A/B 对拍**（把 `rate` 关掉、`clearCache()` 再编译一次，在**同一坐标**上比同一个量）之后，读数立刻干净：带谷簇的谷心线被压低 **30%+（最强 51%）**，镜像侧只差 6%（全部来自逐簇归一化系数的微差）。

顺带定下两条工程约定：`clearCache()` 是「就地改配置」的必要配套（记忆化的代价，已在注释里写明）；A/B 的还原必须放 `try/finally`，否则一次异常就会让后面的断言全部跑在「关掉山谷」的配置上。

另外一处修正：山谷最初只刻 `body`（脊带 × 峰高 × 脊网），实拍在坡脚几乎看不见 —— 改成刻**合成后的高度**，谷才读得出「沟」（谷底 = 当地高度 × (1 − 谷深)）。

新增断言：`演示大片山脉：一块 4×5 全部成山、且连成 1 簇`、`演示块读成「大片山脉」：最大簇 + 峰更高 + 脊带更宽`、`脊带宽度随簇宽增长`、`峰高增长只作用于 ≥ 6 格的簇`、`山谷开关是确定性可复现的`、`山谷在单格与连续地块上都能出现`、`山谷确实把谷心线压低三成以上（同坐标「有谷 vs 无谷」对比）`、`山谷只作用在谷那一侧`、`单格山峰可以不对称`；并把 `山脉分布是窄带` 改成**剔除演示块**的口径。

## 16. 结论与落地判断

方案在纯网页、零后端依赖的前提下可以落地，实验页已经用 535 格、13 城、21 条道路、含桥与隧道的真实规模验证了阶段 0 与阶段 1 的视觉与数据管线：表现层能在正交与低透视之间切换、地形是连续无缝的低多边形曲面、道路分五档并会避让树林与架桥穿山、区域边界由墨线描边、确定性重建逐格一致、两名玩家的移动按「服务器权威 + 客户端插值」的链路跑通且不需要表现层反向依赖。

v1.2 补齐的两块结构，价值不在观感而在后续可维护性。一是**参数集中**：地形份额、高度、配色、生态密度、五档道路、氛围与光照全部收进一个配置文件，并且地形改成按份额比例生成，实测各类地形与目标的偏差都在 3 个百分点以内，策划调比例不再需要理解噪声分布。二是**状态与地形分离**：动态状态可以整体序列化，`applyImpact` 已经能把玩家行为写回地图，渲染层只读状态，因此磨损、修缮、生长这些机制将来打开时不需要改表现代码。

v1.3 解决了三件更细的事，都是**表现层的可信度**问题：一是把「不要分明的六边形」从几何层面推到视觉层面（共享顶点的颜色与法线一致、贴图可平铺），这类问题不会报错，只会让人一直觉得「哪里是一格一格的」；二是让地形真的有起伏，并把隧道与栈桥做成可被看到的结构；三是把道路等级的表达从「宽度」换成「材质 + 构件」，并把这份配方抽成 3D 与 HUD 预览共用的单一来源。三条都留下了可复跑的断言，其中「共享顶点颜色/法线差为 0」是后续任何一次地形层改动都必须守住的回归线。

v1.4 的四项改动都瞄准同一个问题：**「结构存在」不等于「玩家看得见」**。视觉峰值从 20 提到 42 单位、噪声尺度放大到 11 格并清掉小于 3 格的孤立簇，起伏因此从「一堆小土包」变成「能连成脉的山系」；走廊加成被证伪之后换成显式点名隘口，隧道第一次成为地图上稳定的、能走到的结构（4 处隧道、8 个洞口、4 段洞内暗色路面）；蜡笔笔触从「逐段独立随机」改成「沿边共享站点的连续笔触」，消掉了同一格上两条错位短线；云雾让位给贴地云影，画面不再发雾。

这一轮最有价值的产出不是观感本身，而是两类**可量化的验收指标**，它们把原本只能靠眼睛争论的问题变成了断言：

1. **共享顶点不变量**：同一物理位置的所有顶点副本，颜色与法线最大差必须为 0；角点色只能取「压在该角上的 3 格等权」——任何「自身加权」「两圈加权」都会把它打破（实测 0.07~0.12）。这条约束顺带决定了「地形交融」只能在格心做文章。
2. **几何接续不变量**：蜡笔笔触在共享站点上的重合顶点数必须等于「边数 × 内部站点数 × 2」。它把「一条边是不是一条线」变成了一个精确数字。

同时也要承认三条限制，都写进了 §14 的刻意取舍：河道的「岸」在几何上做不出来（地表网格在格边附近只有角点顶点），只能用颜色表达；山体是独立几何而非地表抬升，因此与地表的一致性完全依赖「基部读同一个 `heightAt`」这一条；洞口是以「加法几何」拼出来的而非布尔切除（低多边形风格下的取舍）。

v1.5 把方向从「起伏够不够大」转到**微缩沙盘**：山体不再是地表的抬升，而是每格立起来的一座独立山体（基部取共享角点、两圈收窄成尖顶、雪线分带），河流不再是地表的一条色带，而是**沿格边**流的一条河（顶点图上最陡下降、汇流处加宽、把河谷真的挖下去），地形之间的接缝不再靠墨线硬切，而由**边界过渡装饰簇**去咬合，单个地块里则多了**次生特征**（水洼/草丛/碎石堆/花簇）与格内微高差。这一轮补上的第三个量化不变量是**「可见性」**：河面必须是垂直射线在河中线上打到的第一个表面、离河线 0.75 格处必须已经不是水面、被山体与河流挡住的植被必须为 0 —— 这些断言的意义在于，它们量的是「玩家看到什么」，而不是「代码算了什么」。

v1.6 是一次**定位驱动的修复**，没有一个新功能，全部产出都在「把不该有的东西去掉」：贴地视角下的「粘连细线」查明是云影面片（悬在全图之上 + texel 过粗），改为贴合地形的网格并默认关闭；顺带查明道路扁带只按中心线走高度，给 `Ribbon` 补上 `ground + maxDrop` 让左右两列落到地形上（桥面语义用 `null` 保住）。这一轮补上的第四个量化不变量是**「贴地性」**：云影网格相对地形的偏移必须是常数、扁带左右两列的离地偏差必须落在 `conformDrop` 内、而桥 / 栈桥 / 洞内段必须**不**被贴平 —— 这类断言的特点是「既能抓住漏改，也能抓住改过头」，因为「贴合」与「不该贴合」是同一段代码里的两个分支。

v1.7 是一次**减法**：把「连续高度场」整套删掉，换成全部地块共享一个基准平面。这个决定让两件事同时成立 ——（1）「相邻地块之间不能有台阶」这条从 v1.3 追到 v1.6 的约束**从算法上消失**，不再需要平滑、回填、角点平均、归一化这一串互相牵制的步骤；（2）山脉与河流第一次可以「按自己的需要」生成，不必再迁就地表那 13 个顶点的几何预算。代价是**地表本身不再有高低**，所以「山」与「河」都必须是独立结构，它们的可信度完全落在几条共享参照上：河流靠「顶点图沿格边 + 势能场保证入海 + 水平水面 + 统一河宽 + 浅切槽」，山脉靠「独立模型层 + 基部 12 个共享点 + 主轴锁定六边形方向 + 主脊端点与共享格边高度」，见 §6.7 与 §15.11。

这一轮的产出里，最可复用的三条经验都与地形无关：

1. **判据的粒度不能比被判对象粗**。跨河桥漏判（§15.10）与河流「直来直去」（§15.7）其实是同一类错误的两个面：一个是离散化步长（7.04 单位）与特征尺寸（河宽 3.52）同量级，一个是方向映射只在 6 个方向里的 2 个正确。两者的共同修法都是**把「点是否落在 X 里」升级成结构化判据** —— 跨河改成符号翻转，河线改成顶点图上的棱。
2. **把所有依赖某个量的东西改成「它的倍数」**。河宽 5.1× 的不一致里，真正毁掉观感的不是水带而是**写死绝对半径的岸色带**（§15.8）。把宽度定成一个常量、岸带全部写成「半宽 × 倍数」之后，这类错误在结构上就不可能再发生。
3. **「连续性」必须靠共享参照，不能靠两侧各算一遍**。山体连续格之间的缺口（§15.11）和地表共享角点（§6.2）、河流沿边站点（§15.7）是同一件事的三个尺度：只要两格各自算一次「我这一侧的端点」，就一定会分叉；把端点定义成**共享格边中点**、把该处高度定义成**两侧峰高的平均**（对称函数）之后，两侧算出来的是同一个世界坐标与同一个数值，缺口恒为 0。这条同时解释了为什么「实测 0.0e+0」这类断言值得写 —— 它是**恒等式**，不是容差。

**上一版的遗留这一轮都清掉了**：雪线量纲（改成按每片自身峰高取，121 片全部有雪顶）、山脉目标占比与实际占比的分母不一致（改成同分母，27.2% → 27.1%）、以及「生成逻辑已删、配置与分支还在」的死参数（峡谷 / 隘口体系已连配置一起删除）。三条的根因与修法都写在 §14，避免后来者把它们当成新 bug 重新调查一遍。

代价集中在三处：前端多了一个 Three.js 依赖（本地 vendor，不影响服务端零依赖约束）；地块的逐顶点共享角点插值与 InstancedMesh 不能同时满足，需要按 §6.2 的取舍方案处理；河道的「岸」在几何上做不出来（地表网格在格边附近没有可承载的顶点），只能用颜色表达，见 §14。

v1.9 是一次**把「形状」从格子里拿出来**的重构，落点是两条用户都能直接看见的要求：山脉要更生动、更拟真（`world/mountain-field.js`：簇级柏林噪声场，山脊是 `|n| → 0` 的等值线），以及河 / 湖 / 海要用**画面深度**做水面与地面的过渡（`render/water-depth.js`：半分辨率深度预通道 + 水面材质注入）。两条的收益其实是同一条：**形状与深度都变成世界坐标的函数**之后，「相邻格各算一份」这一整类问题（裂缝、台阶、蜂窝纹）从机制上消失，而不是被调参压住。代价是水深必须真的被挖出来（水格地表从「恒为 0」变成「有真实几何深度的碗状海底」），因此 `heightAt` 多了一条与陆地表不相干的分支，属性上也就多了 `bedDepth / shoreEdges` 两个派生量 —— 它们与 `boundaryEdges / clusterIndex / isLone / foothill` 一样，都必须在重构后回扫一遍消费者，否则就会变成「下一个人以为它还在起作用」的死数据（本轮删掉了 `MountainCluster` 的 11 个同类字段）。

下一步的判断依据是网络层。阶段 2 应该先把格子事件与移动结算搬到服务端，用现有 REST 接口跑通单人权威，再进入阶段 3 的 WebSocket 改造。在这样的顺序下，本方案里唯一尚未被代码验证的部分（AOI 快照与增量、断线重连、多人广播）就都落在可独立测试的服务端范围内，风险不会外溢到地图表现层。等多人跑起来之后，再把 `config` 里的磨损与生长速率打开，让真实的玩家行为去改变这张地图。
