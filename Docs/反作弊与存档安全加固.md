# 反作弊与存档安全加固（v9.14.1）

> 适用范围：Node 服务端 `server/` + 网页客户端 `Online-Client/`
> 代码标记：服务端与客户端注释以 `v9.14` / `v9.14.1` 标注本里程碑；客户端发布版本常量 `APP_VERSION='v9.14.1'`
> 关联文档：`CODE_WIKI.md`（API 路由与并发保护）、`跑商网页游戏设计文档.md`（修订记录 v9.14.1）、`部署上线指南.txt`、`开服说明.md`

## 一、背景与威胁模型

在线存档链路原本是"客户端整包上传、服务端全量替换"：玩家把整份 `gs`（金币、货物、材料、任务、成就、声望等）POST 到 `/api/save`，服务端不做身份校验、不做结构校验，直接 `rec.gs = incoming` 覆盖。实际可利用的攻击面包括：

| 攻击方式 | 后果 |
|---|---|
| 仅凭用户名冒充任意玩家调用 `/api/save` | 覆盖 / 清零 / 篡改他人存档（删档、嫁祸、改排行榜） |
| 不带凭证调用 `GET /api/player/{user}` | 读取任意玩家完整存档（隐私泄露、抄作业） |
| 截包后直接改写 `gs` 数值再回传 | 金币 / 货物 / 材料任意修改，无任何校验 |
| 保留旧存档快照反复上传 | 卖货后回滚旧档→货物复现→再次出售，无限刷资源（复制漏洞） |
| 结构注入（畸形类型、负数、超大值、未知字段、原型污染键） | 存档结构污染、后续读档/结算异常 |
| 冒充他人发聊天 / 操作他人邮箱 / 提交他人物资 | 身份冒用与资源盗用 |

## 二、防线设计（四道防线）

### 2.1 身份防线：会话 Token

- 登录与注册成功即签发随机 Token（`server/sessions.mjs`，`randomBytes(24).hex`），响应回传 `token`；客户端存 `localStorage['_auth_token']`。
- Token 会话为**内存态**：有效期 7 天滑动续期；单账号并发会话上限 8，超出吊销最旧；服务器重启后全员重新登录（登录一次即可恢复）。
- 玩家级接口要求 `Authorization: Bearer <token>`（GET）或请求体 `token` 字段（POST / sendBeacon 兼容），且 **Token 所属用户必须等于目标 user**，否则返回 `need login` / `unauthorized`。
- 改密码成功后吊销该账号全部会话并签发新 Token；登出吊销当前会话。

### 2.2 版本防线：服务端单调版本号（防回滚）

- 每个玩家记录一个服务端单调版本号 `sv`（`server/players.mjs` `getSv/bumpSv`，持久化在玩家 json 顶层 `sv` 字段，旧档缺省 0）。
- 以下事件都会 `sv+1`：客户端保存被接受、服务端权威结算（交易 / 星陨城提交 / 邮箱领取 / GM 发放）。
- 客户端保存请求携带 `baseSv`；服务端仅在 `baseSv === 当前 sv` 时接受，否则返回 `{conflict:true, reason:'stale', sv}`。
- 旧档 / 并发旧版本的重放一律被拒绝，客户端收到冲突后**强制以服务器权威档为准**（`fullSync(true)`），从机制上堵死"旧档覆盖→重复变现"的复制漏洞。
- 替代并增强了旧的时间戳启发式（`clientSaveTime` / `__savedAt` 比较，攻击者可伪造大时间戳绕过）。

### 2.3 结构防线：白名单清洗（防注入）

`server/gs-validate.mjs` `sanitizeGs()`，纯函数：

- **顶层键白名单**：只保留存档 schema 已知字段，未知字段一律丢弃；
- 危险键（`__proto__` / `constructor` / `prototype` / `__define*` 等）在任意层级剔除；
- 数值**严格类型**（非 number 回退默认值）、有限性约束、绝对值域封顶；字符串 / 数组 / 对象深度与体积上限；
- 关键结构归整：`materials`（5 键固定）、`stats`（9 个计数器固定）、`cargo` / `cityStocks` 逐项取整非负封顶、`tasks` / `intel` / `titles` / `taskBadLog` / `visitedCities` 形状兜底；
- 容器内部键（物资 id、城市 id）按"键名安全 + 值类型清洗"保留，属于玩法字典可扩展；
- 邮箱 `mailbox` 为服务端权威字段，不随客户端上传；保存时以服务端副本为准。

数值域（`CAPS`，`gs-validate.mjs` 顶部常量区，运营可调）：

| 字段 | 约束 |
|---|---|
| gold | 允许负债，下限 -1e7、上限 1e13 |
| 单类材料 | 上限 1e9 |
| 单个货物 / 单城库存 | 上限 1e7 |
| 其它数值（时间戳等） | 通用上下界 ±1e13 |
| 字符串 / 数组 / 对象 | 单值 ≤200、容器条目 ≤2000、数组 ≤5000、深度 ≤12 |

### 2.4 快照防线：差分审计（防异常注入）

`auditDiff(prev, next, {stockMode})`：以上一次接受的服务端权威副本为快照，对上传档做差分：

- **cargo 严格相等**（perPlayer 模式）：货物只能由服务端权威操作变更，客户端上传不得多不得少，任何差异判 `cargo_mismatch`；
- **gold 有界增减**：单次增幅 > 2e8 判 `gold_spike`、减幅 > 2e8 判 `gold_drop`（覆盖 18M 级成就奖励并留 10 倍余量）；
- **materials 逐类有界增减**：±1e6 / 单次 / 单类；
- **进度类只增不减**：`stats` 计数器、成就 / 见闻 / 称号 / 拜访城市 / 声望等级等集合或数值回退判 `progress_regress`；
- 触发异常 → 返回 `{conflict:true, anomaly:{code, field, detail}}`，客户端强制拉取服务器权威档覆盖，服务器副本永不被异常写入污染。

配套规则：新账号**首次存档**（服务器无历史快照）只做结构清洗 + 绝对值封顶，不做差分（否则新玩家会被无限拒绝）；`stockMode='shared'` 预留模式下跳过 cargo 严格相等（经济字段仍为客户端权威，仅保留清洗与封顶）。

| 访问类型 | 端点 |

| 位置 | 内容 |
|---|---|
| `index.html` | `_auth_token` 存取；`NET` 自动附带凭证（GET 用 Bearer 头、POST 注入 body.token）；`GS.__lastSv` 生命周期；四处重复上传（`autoSave/saveNow/pagehide/syncPlayer`）收敛为统一 `makeSavePayload()/pushSaveOnline()`；sv 冲突强制 `fullSync(true)`；401 弹回登录 |

| 发版强制重登 | `APP_VERSION` 常量 + `_ver_seen` 记录：登录 / 注册成功写入；启动检测到版本变化 → 清除本地会话并提示"游戏已更新，请重新登录（仅需一次）"。每次发版递增 `APP_VERSION` 即可保证旧页面 / 旧会话在下一轮刷新必然回到登录框 |

## 五、运维要点

1. **server 与 Online-Client 必须配套部署**：新版接口要求客户端携带 Token，旧页面会被 `need login` 拒绝。两份目录缺一不可。
2. **更新流程**：停服 →（停机时）按需清理 `players/` 残留账号 → 整包替换 server + Online-Client → 启动 → 玩家刷新一次并重新登录。
3. **删除账号的正确姿势**：服务端没有在线删号指令。`players.mjs` 常驻内存缓存，且 30 分钟补货会遍历缓存对全量玩家落盘——**在线删除 json 会被缓存写回复活**。删除账号必须停服后删文件，或等后续提供 `deluser` 指令。
4. **昵称存储位置**：账号顶层 `rec.nickname` 是排行榜 / 聊天读写的权威字段；`gs.nickname` 只是随档副本。手工改档清理昵称时需同时处理（实际应直接删除该账号 json）。
5. **发版版本号**：客户端 `APP_VERSION` 每次发版递增，触发"一次强制重登"，避免新旧页面混跑造成歧义。

## 六、已知边界与残余风险

- 任务完成、成就解锁、事件与旅行奖励目前仍在**客户端结算**（在线会随下次保存上报）。因此"小幅数值伪造"（把金币从 1 万改到 2 亿以内等低于差分阈值的行为）无法被本方案完全杜绝；彻底方案是"经济字段服务端权威化"（玩法结算逐项迁移到服务端，另行立项）。
- 差分阈值与绝对值上限是"明显异常拦截 + 强制回拉权威档"的粗防线，阈值集中在 `gs-validate.mjs` 的 `CAPS`，运营可按经济模型放宽 / 收紧。
- Token 存浏览器 localStorage，受 XSS 影响面与传统 Web 一致（本项目聊天等富文本均按文本渲染）。
- 服务器重启会清空全部会话与 `sv` 无关（`sv` 已随档持久化），玩家重新登录后 `baseSv` 由 `/api/player` 返回值校准，无需迁移存档。
