## 1. 设计目标

星陨城是唯一一座"只进不出"的特殊城市：它不做常规的物资买卖与任务接取，而是作为待建设的边境城市，周期性遭遇野兽与敌人侵袭，需要玩家自费从其他城市购入物资并送来"提交"，以推进城市建设。

该玩法的三个定位：

- **金币消耗口**：提交物资没有任何金币回报，是当前版本少有的纯消耗玩法，用于回收玩家手中富余金币。
- **竞争出口**：跨玩家贡献排行榜制造"本期谁贡献最多"的竞争，消耗的规模由排名奖励驱动。
- **素材出口**：奖励中的特殊车辆升级素材，作为高排名玩家的专属收益，与常规金币倒货形成差异化回报。

***

## 2. 玩法循环

```text
其他城市：按本期所需物资买入（特产 + 普通物资）
  → 星陨城（活动期间进入）
  → 面板整体切换为"建设面板"
  → 右侧提交物资（消耗自身货物，无金币获得）
  → 个人贡献累计 → 本期排行榜
  → 活动结束：服务端按排名梯度生成奖励邮件（金币 + 星陨合金附件）
  → 玩家在邮箱领取奖励
  → 间隙期进入：查看下一轮倒计时、上期回顾（历史第一）
```

核心约束：玩家不能在星陨城买入，提交的物资必须从其他城市自费运来，形成"买入 → 运输 → 消耗"的单向消耗链。

## 3. 城市定位与解锁

- **解锁**：`startTravel` 中"星陨城暂未开放，无法前往"的限制**已解除**（v9.9），开放通往星陨城的路径（沿用既有路网与经济距离）。
- **无买入**：`starfall.goods` 保持为空，市场不提供任何可购物资；`getBuyableGoods('starfall')` 返回空。
- **无任务板、无情报所**：星陨城不生成任务，也不提供情报所入口——当前设计版本中这两类 UI 从该城市移出（城市页不渲染任务栏与情报所入口）。
- **城市属性**：`tier:'special'` 沿用，城市背景设定见 `Docs/城市背景设定.md` 星陨城条目（边境要塞、受袭背景、建设目标叙事，已落地）。

## 4. 活动周期与阶段

### 4.1 周期

以**现实自然日**为周期单位，每轮活动包含两个阶段：

| 阶段    | 状态             | 持续时长                          |
| ----- | -------------- | ----------------------------- |
| 活动进行期 | `running` | 24 小时（自然日 **08:00** → 次日 08:00） |
| 间隙期   | `intermission` | 48 小时（次日 08:00 → 第 4 天 08:00） |

一轮完整周期 72 小时（3 个自然日）：活动 1 天，间隙 2 天，**所有阶段切换对齐自然日 08:00**（每 3 天 08:00 开启新一轮）。轮转由服务端世界时间驱动，全服玩家共享同一活动时间轴（与事件系统同源，不与玩家存档 day 绑定）。

**周期参数化（v9.10.2）**：建设期/间隙期小时数由 `world.json` 的 `starfallConfig{runHours,interHours}` 配置（1~168 小时，缺省 24/48，缺省时兜底读取 `default-world.json`）。服务端启动经 `Refresh-SfConfig` 装载，GM 指令热改后通过活动快照 `sfConfig{runMs,interMs}` 下发给客户端，客户端 `applyCycle()` 使两端周期对齐；热改影响**下一阶段切换**。GM 指令：`/gm <密码> starfall cycle <建设期h> <间隙期h>`。

**账号切换清理（v9.10.5）**：客户端 `Starfall.reset()` 在登录/登出/注册切换账号时清模块态——在线活动缓存 `_net`、提交面板已选物资 `_sel`、以及周期参数 `RUN_MS/INTER_MS`（恢复默认 24h/48h）。防止上一账号的 GM 周期设置、活动缓存、提交草稿泄漏给下一账号（单机新档经 `sfActivity.sfConfig` 恢复本档周期）。

**内测控制台指令**：内测阶段提供手动阶段切换指令，供测试跳过等待时间——如客户端控制台 `/gm <密码> starfall start|end|next|status`（start=立即进入活动进行期并抽选物资；end=立即结算当前进行期进入间隙期；next=立即进入下一轮；status=查看活动状态快照）。正式运营时可视需要保留或移除。

### 4.2 每期所需物资

每轮活动开始时随机抽选：

- **1 种特产**（从 51 种物资的特产中抽取）
- **若干种普通物资**（已采纳 3 种，从基础物资中抽取）

同一期内的所需物资固定不变，直到下一轮重新抽选。抽选采用确定性种子（服务端世界种子派生），保证全服一致。

## 6. 物资提交规则

- **条件**：玩家持有该物资（星陨城不售出，物资须从其他城市买入后运来）；提交后货物从 `GS.cargo` 扣除。
- **提交范围（v9.9.3）**：不限于当期抽选物资——**物资全集内任意物资均可提交**；当期物资享受高贡献（特产 100、普通 20），**非当期物资每件仅 1 贡献**（用于消化积压货物，但明显低效）。
- **无金币回报**：提交不获得任何金币、声望；不触发 `ITEM_SOLD` 相关经济事件（或仅触发内部"提交"事件用于统计）。
- **提交量**：无上限，受自身持有量与载具容量约束（一次可提交的量按当前持有计算）。
- **在线权威**：在线模式下提交走服务端接口（见第 13 章），服务端校验持有量并记账个人贡献与总进度，返回权威值；单机模式走本地记账（见第 12 章）。
- **进度条已满仍可提交**：进度条显示封顶（不超过目标值），但提交继续生效，个人贡献与排行榜照常累计。
- **面板布局**：提交面板参照普通城市"售出"面板（物资栏 + 提交面板 + 提交按钮），但无金币/税费栏——仅显示各物资贡献率与合计贡献。

## 7. 贡献与进度

### 7.1 单位贡献值

特产与普通物资的单位贡献值不同，作为经济杠杆区分稀有投入：

| 物资类型 | 单位贡献值（已采纳，可调） |
| ---- | ---------- |
| 特产   | 100 / 件    |
| 普通物资 | 20 / 件     |

目标："特产单件贡献高但单件价格也高，普通物资量大有薄利"。参数集中管理（服务端配置或 world 数据字段），首期活动后可按真实回收数据回调。

### 7.2 总进度

- 本期总进度 = Σ(提交量 × 单位贡献值)，服务端累计。
- **显示用具体数值而非百分比**：如 `建设度 78,432 / 200,000`。
- **进度上限（目标值）**：**200,000**。进度达到上限后，显示封顶（不再上涨），但个人贡献与排行榜继续按实际累计。目标值按"24h 提交窗口内全服活跃玩家（约 20~50 人）的总投入"量级估算，依据见 7.3。

### 7.3 经济数值估算（量级参考）

目标值 200,000 依据如下估算（基于当前物价与产出量级推测，非精确模型，用于校准量级）：

**单位贡献的金币成本**（玩家投入金币 → 贡献的换算）：

| 物资类型 | 单位贡献 | 单件价格（估） | 每 1 贡献约消耗 |
|----------|---------|---------------|----------------|
| 普通物资 | 20 | 100~300 金 | 5~15 金 |
| 特产 | 100 | 500~3,000 金 | 5~30 金 |
| 加权平均 | — | — | **约 8~15 金 / 贡献** |

**单名玩家 24h 提交窗口内的投入分档**：

| 玩家档位 | 提交量（估） | 贡献（估） | 回收金币（估） |
|---------|-------------|-----------|---------------|
| 休闲（1~2 趟） | 普通 50~150 件 + 特产 0~5 件 | 1,000~4,000 | 1~3 万 |
| 中度（3~5 趟） | 普通 200~600 件 + 特产 5~20 件 | 5,000~14,000 | 4~10 万 |
| 深度（多轮往返） | 普通 800~2,000 件 + 特产 20~80 件 | 18,000~48,000 | 15~40 万 |

**全服汇总**（假设构成：深度 20% / 中度 40% / 休闲 40%，且玩家通常投入产出的一部分而非全部）：

| 服务器规模 | 总贡献（估） | 回收金币（估） |
|-----------|-------------|---------------|
| 20 活跃玩家 | 约 10~15 万 | 约 80~220 万 |
| 50 活跃玩家 | 约 25~40 万 | 约 200~600 万 |

**结论**：

- 目标值 **200,000** 下：20 人服人均约 1 万贡献（中度偏上）即可填满；50 人服人均约 4,000 贡献（休闲偏上）即可填满——多数服务器进度能达到 60%~100%，既有推进感又不至于永远满格。
- 每轮满进度约回收 **160~300 万金币**；进度满后仍可提交，实际回收略高于此。按 72h 一轮计，相当于每周从玩家侧抽走数百万金币，形成稳定的经济回收口。
- 以上为量级估算，单位贡献值与目标值可在首期活动后按真实数据回调。

## 8. 排行榜

- **排名依据**：本期个人累计贡献值，降序。
- **展示**：前 10 名玩家的名称与贡献值 + 玩家自身排名（含自身贡献值）。
- **数据来源**：服务端（在线全服统一）；单机模式见第 12 章。
- **同分处理（已确认）**：贡献值相同按先达到者优先（记录首次达标时间戳）。
- **刷新**：活动期间实时/周期刷新（进入城市拉取，提交后回传刷新）。

- **消耗场景预留**：星陨合金将用于后续的车辆升级改动（作为指定档位车厢/载具核心升级材料）。本期仅新增素材与发放，**消耗配方与升级接口留待后续车辆升级重构时定义，本文不写死**；玩家获得后先作为库存素材持有（`materials` 新增字段 `staralloy`）。

### 9.4 奖励发放（邮件领取）

- 活动结束瞬间由服务端结算，按最终排名生成**奖励邮件**，投递到玩家邮箱（附件 = 金币 + 星陨合金），玩家在邮箱中**主动领取**（见第 10 章邮箱系统）。
- **进度未满折算**：活动结束时若全服进度未满，各档奖励按 `实际进度 / 目标值` 的**百分比折算**发放（向下取整）。例如进度 60% 时，第 1 名金币 100,000 × 60% = 60,000、星陨合金 10 × 60% = 6；进度满（或超过）时按 100% 发放。金币与素材分别取整。
- **未上线玩家**：邮件持久化在服务端，玩家任意时刻登录/进入邮箱均可看到并领取，无需补发逻辑。
- **后台发放**：GM/后台向玩家发放金币或素材也统一走邮箱（系统邮件），不直接改玩家资产。

## 10. 邮箱系统

通用邮件系统，承担**活动奖励分发**与**后台发放奖励**两类投递，也是未来系统通知/补偿的渠道。

### 10.1 入口与布局

- **入口按钮**：位于顶栏右侧，用户名、登出按钮的**左侧**，与它们一起**向右靠齐**。
- **未读红点**：存在未读邮件时，邮箱按钮右上角显示红点提示（已读后消失）。
- **面板形式**：独立面板，打开后**居中显示**在网页中央；左半为**滚动邮件列表**，右半为**邮件详情**。

### 10.2 邮件结构

```jsonc
{
  "id": "m_20260828_001",      // 唯一 id（服务端生成）
  "title": "星陨城第 12 期建设奖励", // 抬头
  "from": "边境城建指挥部",        // 发送者
  "body": "本期建设圆满结束，感谢你对星陨城的贡献。", // 内容
  "attachments": { "gold": 60000, "mats": { "staralloy": 6 } }, // 附件（可空）
  "read": false,               // 已读 / 未读
  "claimed": false,            // 附件是否已领取
  "ts": 1786500000000          // 投递时间
}
```

附件支持金币（`gold`）与素材（`mats`），可为空（纯通知邮件）。

### 10.3 容量与状态

- **容量上限 50**：邮箱展示 `0/50` 计数；邮件满 50 时新邮件投递策略见 10.5（草案）。
- **状态**：每封邮件有 已读/未读 与 附件 已领取/未领取 两个维度。

### 10.4 操作

| 操作 | 规则 |
|------|------|
| 查看详情 | 点击列表邮件，右侧显示抬头/发送者/内容；未读邮件查看后标记已读 |
| 一键已读 | 顶部按钮，将全部邮件标记已读（红点消失） |
| 删除已读 | 批量删除**已读且附件已领取（或无附件）**的邮件；有未领附件的邮件不参与 |
| 详情删除 | 单封删除，同样要求附件已领取（或无附件）；**有素材/金币未领取时禁止删除** |
| 领取附件 | 详情页点击"领取"，金币入账（`GS.gold`）、素材入 `materials`；领取后附件清空、`claimed=true`，之后可删除 |

### 10.5 投递与满仓（草案）

- 在线模式：邮件存储于服务端（玩家存档 `mailbox`），投递即时；单机模式存本地存档。
- 满 50 时：新邮件**投递失败并提示**（如"邮箱已满，请先清理"），由 GM 或活动结算方知晓；或自动丢弃最旧已读邮件（策略待确认，见第 14 章）。

## 12. 单机模式处理

**已确认采用方案 A**：单机不启用跨玩家竞争——活动照常抽选物资与推进，提交与进度照常，排名即"玩家自身"，奖励按第 1 档发放（或按本地唯一排名结算），体验完整但无竞争。

- 数据与逻辑复用在线实现（本地模式由客户端承担结算，无需服务端）。
- 历史回顾（第 11 章）在单机模式下仅记录本地玩家自身为"冠军"。
- 邮箱在单机模式同样可用（本地存档存储，活动奖励邮件照常投递与领取）。

## 13. 数据与实现（草案）

### 13.1 服务端（server.ps1）

- **活动状态存储**：新增活动状态（可放 `world.json` 或独立文件 `starfall_activity.json`），字段草案：

```jsonc
{
  "period": 12,                    // 当前活动期次
  "phase": "running",              // running | intermission
  "phaseEndsAt": 1786500000000,    // 当前阶段结束时间戳（ms）
  "phaseStartedAt": 1786480000000,
  "target": 200000,                // 本期建设目标（总进度上限，显示封顶）
  "required": { "special": "jade", "normal": ["grain", "iron", "fish"] },
  "contribution": { "special": 100, "normal": 20 },
  "totalProgress": 0,              // 本期累计贡献（显示封顶于 target）
  "scores": { "userA": 3200, "userB": 1500 },   // 本期个人贡献
  "firstOrder": { "userA": 1786481000000 },     // 同分优先的时间戳
  "settled": false,                // 本期是否已结算
  "history": [                     // 最近 7 期冠军（period 降序）
    { "period": 11, "first": "userB" },
    { "period": 10, "first": "userA" }
  ]
}
```

- **接口草案**：
  - `GET /api/starfall/activity`：返回活动状态（阶段、所需物资、进度、排行榜前 N + 玩家自身、历史冠军、下一轮倒计时）。
  - `POST /api/starfall/contribute`：提交物资，body `{user, items:[{item, qty}...]}`；服务端校验持有量、计入个人贡献与总进度（封顶显示）、返回权威 `{cargo, totalProgress, myScore, rank}`。
  - **结算**：阶段轮转检查（沿用 `MaybeRefill` 的周期触发或在请求时惰性检查）：`running` 到期 → 按最终排名与进度百分比生成**奖励邮件**投递到玩家邮箱、归档冠军、进入 `intermission`；`intermission` 到期 → 重新抽选物资、进入下一 `running`。
  - 抽选逻辑：确定性种子从世界种子派生，避免活动期间变化。
  - **内测指令**：`/api/admin` 扩展 `starfall` 子指令（start / end / next / status），手动切换阶段或查看活动状态快照（对齐 4.1 节控制台指令）；`/api/admin mail` 支持自定义 `title`/`body` 补发奖励邮件（v9.10）。
  - **邮箱存储与接口**：玩家存档新增 `mailbox` 数组（50 上限）；接口 `GET /api/mail`（拉取邮箱 + 未读数）、`POST /api/mail/read`（标记已读/一键已读）、`POST /api/mail/claim`（领取附件）、`POST /api/mail/delete`（删除，服务端校验无未领附件）。

### 13.2 客户端（Online-Client/src/gameplay/starfall.js）

- **面板切换**：进入星陨城时 `renderCity` 顶部分支由 `Starfall.renderPanel()` 接管（`station-panel` 外层结构与其他城市板块一致），按活动阶段渲染"建设面板"或"间隙面板"。
- **动态图景**：`citySceneHtml(pct, rest)` 生成轻量 SVG（夜空/远山/屋舍/城墙/城门/吊车），随建设度逐段成型，CSS 动画常驻（星星/窗户/吊车摆动/炊烟/火星），置于整个面板下方通栏；间隙期渲染"已建成"休整夜景。
- **提交交互**：右侧 `sf-submit-layout`（物资栏 + 提交面板），独立模块状态 `_sel`（`toggleItem`/`clearDraft`/`updateSum` 维护），**不复用** `TradeDraft`；在线走 `POST /api/starfall/contribute` 权威扣货，单机本地记账；提交后清空 `_sel` 并重渲染。
- **历史冠军**：`historyWidget(a)` 随时可查看（下拉 + 左右箭头，`histSelect`/`histShift` 同步 `_histIdx`）。
- **UI 状态**：倒计时与采访气泡由 `tick()` 每秒局部刷新（8 秒轮换文案、30 秒在线轮询同步活动）。
- **邮箱**：独立模块 `src/gameplay/mailbox.js`：顶栏按钮（未读红点）+ 居中弹窗（左列表右详情），一键已读/删除已读/详情删除/附件领取，服务端操作。
- **跑马灯公告**：`showBroadcast`（`src/core/ui-primitives.js`）双组无缝滚动横幅，在线轮询 `world.lastBroadcast` 展示。
- **控制台指令**：`/gm` 指令新增 `starfall`（start/end/next/status）、`mail`、`broadcast`；单机免密（`LOCAL_GM`），在线经 `/api/admin` 转发。

### 13.3 存档

- 在线模式：邮箱（`mailbox`）存于服务端玩家存档；单机模式存于本地存档（`GS.mailbox`）。
- 玩家存档新增 `materials.staralloy`（星陨合金）；邮箱结构见 10.2。
- 现有 `__saveSchema` 机制沿用：本次新增存档字段需递增版本并登记迁移（如 `SAVE_SCHEMA=973`）。
