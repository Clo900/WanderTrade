# 交易系统与物价引擎实现索引

> 版本：v9.8（代码现状）　|　更新：2026-08-28  
> 范围：客户端交易链路 + 物价引擎 + 事件注入 + 在线服务端经济权威结算（/api/stocks、/api/trade、/api/tradeBatch）  
> 目标：在不改动任何代码结构的前提下，把“交易与物价变化”模块的关键入口、规则与定位点固定下来，便于下一步优化与重构时快速定位。

## 总览

交易系统与物价变化由 4 个区域共同组成：

- 客户端交易与库存显示：`Online-Client/index.html`
- 价格引擎（买入/卖出定价）：`Online-Client/src/economy/price-engine.js`
- 公共事件（对价格与价差的叠乘注入）：`Online-Client/src/economy/events.js`
- 在线库存权威（补货 + 库存台账）：`server.ps1`

它们在“计算职责”上的分工非常明确：

- **价格计算完全在客户端**（价格引擎 + 事件叠乘 + 声望卖价加成）。
- **服务端负责经济权威结算（v9.7.3/C1）**：`/api/tradeBatch` 对“资金/持仓/库存”全量校验并一次性记账，返回权威 `{gold, cargo, stocks, serverAt}` 供客户端覆盖；客户端提交 `total`（buy 应付含税）/`net`（sell 税后到手），服务端校验金额>0 且与基准价期望和的比率 ∈ [0.3,3]，防极端改价。`/api/trade` 保留为纯库存台账兼容接口。

## 数据流（从 UI 到金币变化）

```text
UI(市场卡片/滑条)
  ↓（加入中转面板）
index.html: draftFromSlider('buy'|'sell', gid) → TradeDraft.add(mode,gid,qty)
  ↓（一次确认多物品成交）
index.html: confirmDraft('buy'|'sell')
  ├─ buy:  execBuyDraft(list, total)
  │     ├─ 在线：POST /api/tradeBatch {user, city, dir:'buy', items:[{item,qty}...], total} → 服务端全量结算，返回 {gold,cargo,stocks,serverAt} 覆盖本地
  │     └─ 本地：循环 buyItem(gid,qty,{skipAdvance:true})（扣金=总价+税；批次 addLots）
  └─ sell: execSellDraft(list, net)
        ├─ 售出仅车厢物资（不含仓库）
        ├─ 优先弹“同城同次倒卖惩罚”汇总确认（60%/80% 结算提示）
        ├─ 在线：POST /api/tradeBatch {dir:'sell', net} → 服务端全量结算，返回 {gold,cargo,stocks,serverAt} 覆盖本地
        └─ 本地：循环 sellItem(gid,qty,{skipAdvance:true})（入账=收入-税；批次 consumeLots）

v9.7.3(C1)：在线路径 buyItem/sellItem 以 serverLedger 轻记账——不再自行改 gold/cargo/stocks，
  仅本地记 lots/成本/声望/事件（sell 复用调用方在提交前真实计算的 lotsResult，含同城同次惩罚）。

定价链路（每次买/卖都会调用）
  buyPrice  = getDayPrice(city, item, day)  → priceFor(..., multiplier=getItemMult(...,'buy'))
  sellPrice = getSellPrice(city, item, day) → priceFor(..., center=base*(1-spread), multiplier=getItemMult(...,'sell')) * getRepSellBonus(...)

税务链路（v9.1 已实现）
  taxRate = Tax.getRate(repLevel)  // 15% - 0.5%*Lv，最低 3%
  buyPay  = total + Tax.calc(total, taxRate)
  sellNet = revenue - Tax.calc(revenue, taxRate)
```

#### 距离口径：经济 vs 表现解耦（v9.1 已落地）

- **经济距离（权威）**：用于定价/税务/例外规则等经济计算，来源为服务端世界数据 `world.json`（通过 `/api/world` 下发）。  
  - 目的：策划可在不改前端静态资源的情况下调整“设定距离”，并且不受地图视觉表现影响。
- **表现距离（非权威）**：用于地图路径绘制、旅行进度条、旅行耗时等表现层计算，继续使用客户端 `Online-Client/src/core/data.js` 的 `ROADS`。  
  - 目的：后续可独立升级地图/路网表现，而不必同步更改经济距离。

> v9.1 已落地 `world.tradeRoads`（格式同 `ROADS`），客户端通过 `TradeGraph.setRoads(world.tradeRoads)` 接入。不要复用表现层 `ROADS`，避免耦合回归。

#### 远途收益来源：主要来自买入端差异化（已确定）

为避免“目的地城市附近存在另一个可购城市 → 综合距离被拉低 → 远途运货反而不赚”的矛盾，本版本选择：

- **卖出价只与售卖城市相关**（统一价），不区分货源城市，不要求玩家选择来源批次。
- **长途跑商收益主要由“产地/优势供给地的更低买入价”提供**，而不是通过“卖出价随来源距离增加”提供。

实现层含义：

- `GS.lots[].city` 保留用于“同城同次倒卖惩罚”，不用于按来源定价。
- 对每个物资可配置 1~N 个“优势供给地/产地”，其买入基础价更低；非产地买入更贵（可视为“转运/二道贩子”溢价）。

#### 税务规则（v9.1 已实现，税曲线 B）

- 买入与卖出均征税：默认 15%。  
- 税以“最终成交额”为基数计算：  
  - 买入：以实际买入成交总价为基数  
  - 卖出：以 `consumeLots` 计算后的最终 `revenue` 为基数（含同城同次惩罚后的真实收入）
- 以本城声望等级减税：**平滑下降**，最低可降到 3%，到达某等级后不再继续降低。
  - 参考曲线（已确定 B）：`每级 -0.5%`，`Lv24 达到 3%`，`Lv24+ 固定 3%`

#### 例外规则：卖出价封顶/封底（待实现，已确定）

- 允许对单个城市+单个物品进行点对点配置，覆盖卖出价的最终输出：  
  - `sellCap`：封顶（不高于某值）  
  - `sellFloor`：封底（不低于某值）  
  - 典型用途：宗教/禁忌城市里某些物资“卖不动”，即使很远也不会卖很高。

#### UI 交互：中转面板（v9.1 已实现，已确定）

- 买入/卖出通过顶部最高优先级按钮切换面板（现有交互保留），**买与卖分别维护各自的中转面板内容（互不混合）**。
- 中转面板的定位是“购物车/交易单（draft）”：玩家可一次性选定多个物品与数量，在中转面板内统一确认成交。
- 中转面板进入/确认前必须做预校验：
  - 买入：本城库存、玩家金币、车厢容量
  - 卖出：仅允许售出车厢内持有物资（不包含仓库）；同时需检查同城同次倒卖惩罚提示
- 若中转面板非空且发生价格锚点变化，必须弹窗提示并清空中转面板内容：
  - 游戏日刷新（`GS.day` 变化）
  - 或中枢点刷新（`floor(GS.day/CENTRAL_PERIOD)` 变化）
- 在线模式批量成交要求“原子提交（全成功/全失败）”：v9.1 已通过服务端 `/api/tradeBatch` 落地（客户端以返回 stocks 强制覆盖本地库存口径）。

##### 中转面板详规（P4）

> 本小节把 P4 细化为可直接落地的“UI/数据结构/校验/弹窗优先级/在线原子性”规格。术语：`draft`=中转面板里的交易单。

**1) 数据结构（前端）**

- `TradeDraftState`（建议挂在 `State` 下，便于 UI 响应式渲染）：
  - `tradeDraft.buy = { cityId, day, hub, items: { [gid]: qty } }`
  - `tradeDraft.sell = { cityId, day, hub, items: { [gid]: qty } }`
  - 说明：
    - `cityId` 记录交易发生城市（税率取该城声望；切城后 draft 必须清空）
    - `day/hub` 为创建时的价格锚点，用于“价格变化→清空”
    - `items` 用 map 结构避免重复条目（同一物品多次添加即累加/覆盖数量）

**2) UI 分区（买/卖一致，内容不同）**

- 左侧：物资列表（仅展示可操作的物资，支持搜索/排序为后续优化项）
  - 行为：`+`/`加入` 将该物资加入 draft；数量调整可在列表或中转面板中完成（最终以 draft 为准）
- 右侧（中转面板）：交易单汇总 + 确认按钮
  - 汇总区仅显示总额：
    - 税率（由 `getTaxRate(cityId, repLevel)` 决定）
    - 税额（总额）
    - 税后总价（买入）/税后收入（卖出）
  - 确认按钮：
    - 买入：`确认购入（合计 …）`
    - 卖出：`确认售出（合计 …）`

**3) 物资可见性规则**

- 买入面板：列表与图表选择都只显示 `getBuyableGoods(cityId)`（不可购买的不显示）
- 卖出面板：仅显示玩家车厢 `GS.cargo` 中数量 > 0 的物资（不包含仓库）

**4) 进入中转面板的校验（“先校验后进入”）**

> 你要求“在中转站这一层就确认参数后才进入中转面板”。实现上等价为：当 draft 从空变为非空，或点击“打开中转面板/确认页”时，必须立即校验；不通过则不允许保留非法条目。

- 买入预校验（以当前城、当前价格为准）：
  - 库存：对 draft 每个 `gid`，要求 `qty <= getCurStock(cityId,gid)`
  - 金币：`sum(price(gid)*qty) + tax <= GS.gold`
  - 容量：`sum(qty) <= getCargoFree()`（以“单位=占用格数”口径）
  - 不通过策略：优先给出弹窗/提示，并阻止进入；必要时把超限项自动裁剪到最大可买（裁剪策略需二选一，建议默认“阻止并提示”，避免玩家误买）
- 卖出预校验：
  - 持有：对 draft 每个 `gid`，要求 `qty <= GS.cargo[gid]`
  - 不通过策略：同买入

**5) 同城同次倒卖惩罚提示（最高优先级）**

- 触发时机：卖出“确认前”（进入最终确认页之前）
- 判定：对 draft 每个 `gid/qty` 调用 `getSameVisitArbitrage(gid,qty)`（现有逻辑）
- 展示：弹窗内列出所有触发项（物资名、sameQty、按 60%/80% 结算的解释），并要求二次确认
- 优先级：该弹窗优先于“总交易确认”

**6) 价格变化导致清空（强规则）**

- 若 draft 非空，且检测到任一情况：
  - `GS.day` 变化（游戏日刷新）
  - 或 `hub = floor(GS.day/CENTRAL_PERIOD)` 变化（中枢点刷新）
  - 或 `GS.location` 变化（切城）
- 则必须：
  1. 弹窗提示“物价已更新/已切换城市，为避免按旧价成交已清空中转面板”
  2. 清空当前 `tradeDraft.buy` 与 `tradeDraft.sell`（或至少清空当前 tab 对应 draft；为避免跨 tab 误解，建议两者都清空）

**7) 最终确认与在线原子性**

- 最终确认按钮点击时必须再次全量校验（防止 UI 期间库存/金币变化）
- 在线模式：
  - 必须使用服务端批量接口保证原子性（全成功/全失败）
  - 建议接口：`POST /api/tradeBatch { user, city, dir, items:[{item,qty}] }`
  - 服务端处理顺序：
    1. 读取玩家库存台账（perPlayer）或 world.stocks（shared）
    2. 全量校验 buy 的每个 item 是否库存足够（sell 回补一般不失败）
    3. 一次性写回（单次保存），返回 ok
  - 客户端收到 ok 后再更新本地 `cityStocks` 并清空 draft（与“税/金币/货舱”结算同步）

### 设计目标（玩家体验）

- **核心循环**：到城 → 看行情/事件/库存 → 决定买入 → 跑到另一城 → 决定卖出 → 赚金币 → 养声望/开情报/扩容 → 进入更高价值跑商。
- **变化来源**：价格不是静态表，而是“基础价带 + 中枢周期剧本 + 日内抖动 + 事件乘数 + 价差 + 声望卖价加成”的组合。
- **风险与约束**：
  - 库存有限且会刷新，避免无限刷金。
  - “同城同次倒卖”被强力抑制（惩罚结算），防止玩家站桩套利破坏跑商动机。
  - “顺价可套利”时库存上限会临时收紧，进一步抑制站桩套利与刷声望。

### 名词与口径（玩家可见/策划使用）

- **买入价**：玩家在城市购买物资时看到的单价。实现：`getDayPrice(city,item,day)`（`price-engine.js`）。
- **卖出价**：玩家在城市卖出物资时看到的“当前售价”。实现：`getSellPrice(city,item,day)`（`price-engine.js`）。
- **价差（spread）**：买入价与卖出价之间的折扣差，玩家通常表现为“卖出价低于买入价”。实现：`getSpreadRate(city,day)`（`events.js`，基础 5% + 事件叠加）。
- **事件乘数（mult）**：事件对价格的叠乘修正（可能只影响 buy 或 sell）。实现：`getItemMult(city,item,day,'buy'|'sell')`（`events.js`）。
- **声望卖价加成**：同城声望等级带来的卖出增益（+1%/级）。实现：`getRepSellBonus(city)`（`index.html`）。
- **同城同次**：玩家在“同一次停留（visitStamp 不变）”期间买入的货物批次。实现：`GS.lots` + `GS.visitStamp`（`index.html`）。
- **同城同次倒卖惩罚结算**：卖出时如果命中同城同次批次，会有 60%/80% 的惩罚结算。实现：`consumeLots`（`index.html`）。
- **中枢周期**：价格引擎的“慢变化节拍”（设计为 2 小时 = 12 游戏日）。实现：`CENTRAL_PERIOD=12`（`price-engine.js`）。

### 买入/卖出价格构成（策划公式口径）

> 下列为“口径公式”，不等同于代码的逐行实现，但与现状一致，便于策划讨论和后续调参。

- 买入价（口径）：  
  `Buy = BaseEnginePrice(city,item,day, salt=0) × EventMult_buy(city,item)`
  - 映射：`getDayPrice` → `priceFor(..., multiplier=getItemMult(...,'buy'))`

- 卖出价（口径）：  
  `Sell = BaseEnginePrice(city,item,day, salt=100, center≈base×(1-spread)) × EventMult_sell(city,item) × RepSellBonus(city)`
  - 映射：`getSellPrice` → `priceFor(..., center=base×(1-spread), multiplier=getItemMult(...,'sell')) * getRepSellBonus(city)`

- 交易收入（口径）：  
  卖出不一定是 `Sell × qty`，因为**批次惩罚结算优先**：同城同次部分按惩罚价结算，其余按 `Sell` 结算。  
  - 映射：`sellItem` → `consumeLots` 返回 `revenue`

### 交易规则（玩家口径，含实现映射）

- **买入成功条件**（玩家会感知为"为什么按钮灰了/为什么提示不足"）：
  - 钱够（`gold >= Buy×qty`；**v9.8 欠债系统**：金币为负（负债）时无法买入——`buyItem`/`trade-validate`/服务端 `tradeBatch` 三重校验全部拒绝，买入永远不会把金币扣成负数；负债时市场卡片显示"欠债中，无法购入"，卖出/任务奖励自动还债）
  - 库存够（`qty <= getCurStock`，注意这是"显示口径库存"，会被 `getMaxStock` 收紧）
  - 货舱够（`getCargoFree >= qty`）
  - 物资可购买（声望解锁规则：`getBuyableGoods`）
  - 映射：`buyItem`（`index.html`）

- **卖出收入由批次决定**（这是策划最容易被误解的一点）：
  - 同城同次批次会被优先扣除并按惩罚价结算（见下方例子）。
  - 映射：`sellItem` → `consumeLots`（`index.html`）

- **“顺价套利”抑制**（双重限制）：
  1. UI 弹窗提示：同城同次 + 买入价 < 卖出价 时会弹出“60%结算”警告。映射：`doAction('sell')` → `getSameVisitArbitrage`（`index.html`）
  2. 库存上限收紧：买入价 < 卖出价 时，`getMaxStock` 将库存上限乘 0.5 或 0.3。映射：`getMaxStock`（`index.html`）

### 可调参数（数值平衡建议，不改代码）

> 这里给出“调参抓手”，你后续优化可以选择把它们抽成配置或集中到单一模块管理（本章只做说明）。

- **基础价差**：`getSpreadRate` 的基础值当前为 `0.05`。  
  - 调小（如 3%）：更“好卖”，跑商更爽，但更容易出现站桩套利，需要更强抑制。  
  - 调大（如 8%）：更“难卖”，玩家需要更依赖事件/情报，但早期挫败感会变强。

- **事件对价格的影响强度**：事件表字段 `mult`（如 1.25/0.85）与 `target`（buy/sell/both）。  
  - 建议：对“只影响 buy 或 sell”的事件，倍率可以更激进一点，因为它不会同时抬高两端，套利窗口更清晰。

- **vNext：经济距离与产地价差（新增设定）**：
  - 经济距离权威来自服务端世界数据（`/api/world`），与地图/旅行表现层距离解耦。
  - 长途收益主要由“产地更低买入价”提供，因此关键旋钮会从“卖出端距离溢价”转为“买入端产地/非产地倍率”。
  - 建议先从特产开始试行（更符合直觉，也更好控通胀），基础物资保持差异较小。

- **vNext：税务（新增设定）**：
  - 买入/卖出默认税率 15%，随本城声望等级平滑下降，最低 3%（参考：每级 -0.5%，Lv24 达到 3%）。
  - 税以最终成交额结算：卖出税基为 `consumeLots` 后的真实收入（含同城同次惩罚影响）。

- **同城同次惩罚系数**：
  - `顺价套利`：当前为 `buy×0.6`（60%）  
  - `普通同城同次`：当前为 `batch.cost×0.8`（80%）  
  - 调低会更强制跑商；调高会允许更多“本城短炒”。这是影响经济上限与玩法导向的关键旋钮。

- **库存上限收紧系数**：`getMaxStock` 在 `buy<sell` 时 `×0.5/×0.3`。  
  - 作用：让“顺价套利”即便被发现也难以放大规模。  
  - 风险：若收紧过强，玩家可能觉得“库存莫名其妙变少”，需要 UI/文案解释（本章例子会覆盖）。

- **声望对经济的影响强度**：  
  - 卖出加成：`+1%/级`（`getRepSellBonus`）  
  - 库存上限：`+15%/级`（`getMaxStock`）  
  - 这两个一起会让高声望玩家同时拥有“更大规模 + 更高卖价”，属于后期经济加速器。若后续你要控通胀，优先从这里入手。

## 假设例子（用于策划讨论与测试用例）

> 说明：以下数值为**假设**，用于演示规则叠加后的结果与玩家感知。城市/物资仅作为示例，不代表线上某一城真实数值。

### 统一假设参数（便于复用）

| 名称 | 假设值 | 含义 |
|---|---:|---|
| `baseBuy` | 2000 | 假设某特产在该城的“引擎基础买入价”（未乘事件） |
| `spread` | 5% | 默认基础价差（`getSpreadRate` 基础值） |
| `repLevel` | 10 | 本城声望等级 |
| `repBonus` | 1.10 | 卖价加成（`1+repLevel×1%`） |
| `eventMult_buy` | 1.00 | 买入侧事件乘数 |
| `eventMult_sell` | 1.00 | 卖出侧事件乘数 |

#### 例子里使用的口径计算

- 假设卖出引擎中心价大致为：`baseSellCenter ≈ baseBuy × (1 - spread)`  
  在 `spread=5%` 时：`baseSellCenter ≈ 2000×0.95 = 1900`

> 注意：真实代码会再叠加“中枢/趋势/调控/日内抖动”，这里为了策划可读性只演示关键乘数与价差方向。

### 例 1：基础跑商（无事件、无惩罚）

场景：

- 玩家在 A 城买入 50 件某特产（Buy=2000）。
- 跑到 B 城卖出时，B 城该物资卖出价为 2600（假设 B 城行情更高）。
- 玩家没有“同城同次倒卖”（因为跨城）。

计算：

- 成本：`2000×50 = 100,000`
- 收入：`2600×50 = 130,000`
- 毛利润：`30,000`

策划解读：

- 这是玩家最直观的“买低卖高”体验。
- 如果你希望玩家更依赖情报所/事件，则可以通过提高基础 spread 或降低跨城价差的出现概率来收紧这条收益线。

### 例 2：同城同次倒卖（触发 60% 惩罚）

场景（同城站桩套利）：

- 玩家在同一座城 C，先买入 10 件（买入价 `Buy=2000`），然后立刻想卖出。
- 此时该城显示卖出价 `Sell=2200`（出现“买入价 < 卖出价”的顺价套利窗口）。
- 这 10 件都是本城本次停留买入（同城同次批次）。

结算规则（映射：`consumeLots`）：

- 因为顺价套利成立，惩罚价为：`buy×0.6 = 2000×0.6 = 1200`
- 这 10 件会按 1200/件结算，而不是 2200/件

计算：

- 买入成本：`2000×10 = 20,000`
- 卖出收入（惩罚）：`1200×10 = 12,000`
- 结果：亏损 `8,000`

玩家感知与文案口径：

- 玩家会看到弹窗警告“同城倒卖按 60% 结算”，确认后实际确实亏钱，从而被强制导向跨城跑商。

### 例 3：库存上限收紧（为什么库存突然变小）

场景：

- 城市 D 的该物资在数据里有库存 200（`GS.cityStocks`）。
- 但玩家打开市场面板看到“库存只剩 60”。
- 原因是假设该城当前出现顺价套利：`buy < sell`，触发 `getMaxStock` 的临时收紧。

假设：

- 声望等级 `repLevel=10`，库存基础上限 `baseLimit=150`
- 声望加成后上限：`150×(1+0.15×10)=150×2.5=375`
- 但因为 `buy < sell` 且价差 `gap>0.1`（假设），触发 `×0.3`：`375×0.3=112.5≈113`

结果：

- `getCurStock = min(实际库存200, 上限113) = 113`
- UI 展示库存会被“截断”到 113（或更低，取决于当时 `cap`）

策划解读：

- 这是“顺价套利抑制”的第二道闸，作用是让套利规模难以放大。
- 若玩家反馈“库存莫名其妙变少”，建议在 UI 增加解释（例如：行情异常时市场收紧配额），但这属于后续优化范畴，本章只记录现状。

### 例 4：事件只影响卖出价（target='sell'）带来的“出货窗口”

场景：

- 玩家在 E 城囤货后，打听到事件“本城收购价上涨（仅卖出价）”，准备回到 E 城出货。
- 事件配置口径：`eventMult_sell = 1.25`，且 `eventMult_buy = 1.00`

假设（只演示乘数）：

- 平时卖出中心价：`baseSellCenter ≈ 1900`
- 事件期间卖出价（口径）：`Sell ≈ 1900 × 1.25 × repBonus`
- 若 `repBonus=1.10`：`Sell ≈ 1900×1.25×1.10 = 2612.5 ≈ 2613`

策划解读：

- `target='sell'` 的事件会制造很清晰的“出货窗口”，且不会把买入价一并抬高，体验上更容易让玩家理解“消息值钱”。
- 这类事件更适合和情报所绑定，成为玩家主动追逐的跑商机会。

### 例 5：在线模式一致性（客户端价格 vs 服务端经济权威结算）

目的：明确“改哪里不会影响另一边”，避免误改。

场景：

- 玩家在线模式买入 20 件。
- 客户端做两件事：
  1. 用客户端引擎计算应付金额（`total = 成交价 + 税`），随交易单提交服务端
  2. 服务端 `/api/tradeBatch` 全量校验并记账（扣 gold、加 cargo、扣 stocks），返回权威 `{gold, cargo, stocks, serverAt}`
  3. 客户端用返回值覆盖本地 `gold/cargo/stocks`；`buyItem(...,{serverLedger:true})` 只做本地轻记账（lots/成本/声望/事件）

假设：

- 客户端算得应付 `total = 40,000`（2000×20 含税）
- 服务端校验：金额>0、比率 `40000/Σ(basePrices×20) ∈ [0.3,3]`、`gold≥40000`、库存≥20 均通过 → 一次性记账并返回权威快照

关键结论（v9.7.3 现状）：

- **服务端已对“资金/持仓/库存”做权威校验与记账**，客户端无法通过改本地存档透支或凭空卖出；价格比率校验防止极端改价（如 1 金买入）。
- 价格本身仍由客户端引擎计算（服务端只做比率粗校验），后续如需更严格的价格签名可在此基础上扩展。
- 单笔在线交易同样走 `/api/tradeBatch`（单物品）；`/api/trade` 保留为纯库存台账兼容接口（不校验资金/持仓）。

## 交易系统（客户端）详解

### 买入：`buyItem(itemId, qty)`（L1237）

关键规则（按代码顺序）：

- 时间推进：调用 `advanceDay()`；若 `GS.traveling` 则禁止交易。
- 可购物资校验：`getBuyableGoods(city)` 决定能否购买（声望不足会被拒绝）。
- 定价：`price = getDayPrice(city,itemId,GS.day)`。
- 资金/库存/容量校验：
  - 金币：`GS.gold >= (price*qty + tax)`（税见 `Tax.getRate`）
  - 库存：`qty <= getCurStock(city,itemId)`（注意 `getCurStock` 受 `getMaxStock` 影响）
  - 容量：`getCargoFree() >= qty`
- 成本记录：
  - `GS.buyPrice[itemId]` 记录为“加权平均成本”（不是本次价格）
  - 批次记录：`addLots(itemId, city, qty, price)`（用于倒卖限制）
- 状态变更：
  - `State.batch` 内：写 `cargo`、`buyPrice`、扣减 `cityStocks`
  - batch 外：`State.set('gold', GS.gold-pay)`（pay=total+tax）
- 经济外溢：
  - 事件：`EventBus.emit(ITEM_BOUGHT, ...)`
  - 声望：`addRep(city, qty)`（买入按数量）

### 卖出：`sellItem(itemId, qty)`（L1269）

关键规则：

- 时间推进：同买入（`advanceDay()`；旅行中禁止）。
- 定价：先计算 `sPrice = getSellPrice(location,itemId,GS.day)`，但最终收入由 `consumeLots` 计算。
- 批次扣减与惩罚：`consumeLots(itemId, qty)` 返回 `{revenue, sameQty, arbitrage}`
  - 若卖出的部分来自“同城同次批次”，会按惩罚结算（见下一节）。
- 状态变更：
  - `State.batch` 内：扣减/清理 `cargo`、清理 `buyPrice[itemId]`（卖空则删除）
  - batch 外：`State.set('gold', GS.gold+net)`（net=revenue-tax）
- 经济外溢：
  - 事件：`EventBus.emit(ITEM_SOLD, ...)`
  - 声望：`addRep(city, floor(revenue/1000))`（卖出按收入折算）

## 同城同次倒卖限制（lots/visitStamp）

### 数据结构

- `GS.lots[gid] = [ {city, qty, cost, stamp}, ... ]`
- `GS.visitStamp[city]`：每次离开城市再返回会递增（同一次停留 stamp 不变）

### 触发条件（UI 弹窗）

UI 入口 `doAction('sell', gid)`（L2802）在卖出前会检查：

- `buy < sPrice`：本城当前买入价低于卖出价（顺价可套利）
- 且本次卖出数量中存在 `sameQty`：来自“本城本次停留（stamp 相同）买入”的批次

满足则弹窗提示：这部分 `sameQty` 将按“当前买入价的 60%”结算。

### 实际结算规则（`consumeLots`，L1210）

卖出会按批次扣减（先扣同城同次批次，再扣其他批次）：

- 同城同次批次：
  - 若 `arbitrage = true`（顺价套利）：`rate = round(buy * 0.6)`
  - 否则（非顺价套利）：`rate = round(batch.cost * 0.8)`
- 其他批次：按当前卖出价 `sPrice` 全额结算

返回值用于提示信息拼接：

- `sameQty>0` 时在 toast 中追加说明“其中 X 件同城同次买入按 60%/80% 结算”。

## 库存系统：上限、刷新与显示口径

### 显示口径：`getCurStock = min(实际库存, 库存上限)`

`getCurStock(cityId,itemId)`（L1110）把 `GS.cityStocks[city][item]` 与 `getMaxStock` 取最小值，这意味着：

- UI 展示的库存可能小于 `GS.cityStocks` 存储的原值。
- 想排查“为什么库存突然变小”，需要优先看 `getMaxStock` 是否触发了顺价套利收紧。

### 库存上限：声望加成 + 顺价套利收紧

`getMaxStock(cityId,itemId)`（L1427）规则：

- 基础上限：`base = PURCHASE_LIMITS[cityId][itemId]`（由 `buildLimits()` 生成）
- 声望加成：`cap = round(base * (1 + 0.15 * repLevel))`
- 顺价套利抑制：当 `buy < sell` 时按价差收紧：
  - `gap > 0.1`：`cap *= 0.3`
  - 否则：`cap *= 0.5`

### 补货机制（在线与离线）

- 客户端离线/兜底：`refillStocks()`（L1014）按 30 分钟补货，更新 `GS.cityStocks`
- 服务端在线权威：`MaybeRefill()`（server.ps1 L183）每 30 分钟补货一次
  - perPlayer：`RefillAllPlayers()`（L159）逐个玩家存档把 `gs.cityStocks` 重置为 `world.purchaseLimits`
  - shared：预留模式，更新 `world.stocks`

## 物价引擎（price-engine.js）详解

### 基础价与初始库存梯度

- `BASE_PRICES`（L23）：由 `buildBasePrices()`（L4）生成
  - 基础物资：固定常量 + 城市 tier 与特例调节 + 少量随机
  - 特产：`buildSpecialPrice(iid,cid)`（L17）按产地/非产地定价表
- `PURCHASE_LIMITS`（L46）：由 `buildLimits()`（L32）生成
  - 设计意图：城市等级越高，基础物资上限更高；高档特产上限更低（稀缺）

### 核心定价：`priceFor(...)`（L124）

基础概念：

- **游戏日**：由 `GS.day` 表示
- **中枢周期**：`CENTRAL_PERIOD = 12`（L58），即 12 游戏日一个“中枢”（设计为 2 小时）
- **独立剧本**：每个 `(cityId, itemId)` 都有独立的确定性种子序列（盐值 salt 区分 buy/sell）

价格生成流程（高度概括）：

- 计算 `hub = floor(day / CENTRAL_PERIOD)`（L127）
- 计算有效物价带 `band = getEffectiveBand(...)`：
  - 正常段 band 基于 base 的区间（基础窄、特产宽）
  - 若历史突破事件已结束且带有 shift，会把漂移累积进后续 band（L92-L103）
- 查找当前中枢是否被未结束的突破事件覆盖：`findActiveEvent(...)`（L111）
  - 若无突破：`normalHubPrice(...)` 在 band 内确定性取值（L106）
  - 若有突破：按 “突破 → 趋势段 → 王国调控段” 生成 hubBase（L135-L143）
- 日内抖动：`jitter` ±2.5%（L145）
- 注入事件乘数：`* multiplier`（L146），该乘数来自事件系统 `getItemMult`

### 买入价与卖出价的差异

- 买入价：`getDayPrice`（L148）
  - `salt = 0`
  - `multiplier = getItemMult(city,item,day,'buy')`
- 卖出价：`getSellPrice`（L149）
  - `salt = 100`（与 buy 分离种子序列）
  - `center = base * (1 - getSpreadRate(city,day))`（在“基准价×(1-价差)”附近跑同一套引擎）
  - `multiplier = getItemMult(city,item,day,'sell')`
  - 最后再乘：`getRepSellBonus(city)`（声望卖价加成）

## 公共事件对物价的注入（events.js）

### 事件时间轴：与世界时间绑定（避免玩家天数分叉）

事件的“当前中枢编号”使用：

- `getEventHubNow()`（L66）：`floor((Date.now - GS.gameStartTime) / getHubMs())`
- `getHubMs()`（L83）：`HUB_MS / (GS.timeScale || 1)`，其中 `HUB_MS = 2小时`

这意味着事件不依赖 `GS.day`，并且会随 GM `timescale` 同步加速。

### 价格乘数：`getItemMult(city,item,day,mode)`（L118）

规则：

- `mode` 只能是 `'buy'` 或 `'sell'`
- event 的 `target` 控制作用面：
  - 缺省或 `both`：同时影响 buy/sell
  - `buy`：只影响买入价
  - `sell`：只影响卖出价
- 叠乘来源：
  - `scope='global'` + `items` 命中
  - `scope='city'` + 城市命中（可带 item）
  - `scope='item'` + 城市与 item 同时命中

### 价差：`getSpreadRate(city,day)`（L130）

- 基础价差率：5%
- 叠加：所有 active events 中满足城市范围的 `spread` 累加

### 玩家可见性：全局事件 vs 已知事件

- `getPlayerEvents()`（L156）：
  - 全局/费用事件永远可见
  - 城市/单品事件：需要被 `knownEvents` 标记后才可见（到达城市或情报所获得）
  - 预告事件：只有已知的才可见（未从情报所获得则不可见）

## 在线库存 API（server.ps1）

### GET `/api/stocks?user=...`（L289）

行为与 stockMode 有关：

- `stockMode='perPlayer'`（当前默认）：
  - 无 user：返回 `stocks=null`（客户端可据此判断未登录等情况）
  - 有 user：读取 `players/<user>.json`，返回 `rec.gs.cityStocks`
- `stockMode='shared'`（预留）：
  - 返回 `world.stocks`

在处理 stocks 前会调用 `MaybeRefill`（L293）确保按 30 分钟补货。

### POST `/api/trade`（L310，单笔库存台账）

入参（JSON）：

- `user`：用户名（perPlayer 模式必填）
- `city` / `item`：库存键
- `qty`：数量
- `dir`：`buy` 或 `sell`

行为：

- perPlayer：更新 `players/<user>.json` 内的 `gs.cityStocks[city][item]`
- shared：更新 `world.stocks[city][item]`
- buy：库存不足则 `err='stock shortage'`
- sell：直接回补库存（不做上限限制）

重要说明：

- 该接口只维护“库存台账”，**不会验证客户端提交的金币变化、货物持有量、价格是否合法**。
- **v9.7.3(C1) 起**：客户端在线交易（含单笔）已统一改走 `/api/tradeBatch` 全量结算；`/api/trade` 仅作为纯库存台账兼容接口保留（如旧客户端/调试/手动扣库存）。

### POST `/api/tradeBatch`（v9.1 批量原子接口 → v9.7.3(C1) 全量结算）

用途：

- 在线交易的**经济权威结算**：一次请求完成“资金 + 持仓 + 库存”的全量校验与记账（全成功/全失败），杜绝客户端改档透支、凭空卖出与极端改价。

入参（JSON，perPlayer 模式）：

- `user`：用户名
- `city`：城市 id
- `dir`：`buy` 或 `sell`
- `items`：`[{ item, qty }, ... ]`
- `total`：buy 方向客户端应付金额（含税），`[double]`，必传
- `net`：sell 方向客户端税后到手金额，`[double]`，必传

行为（perPlayer，v9.7.3/C1）：

1. 金额校验：`amount = dir='buy' ? total : net`，须 `amount > 0`
2. 价格范围校验：`ratio = amount / Σ(basePrices[city][item] × qty)`，须 ∈ **[0.3, 3]**（防“1 金买入”式极端改价；basePrices 缺省按 100）
3. 资源校验：
   - `dir='buy'`：`gold ≥ total` 且每个 item 库存充足（任一不足整体失败，返回 `gold insufficient` / `stock shortage`）
   - `dir='sell'`：每个 item 持仓 `cargo ≥ qty`（否则返回 `cargo shortage`）
4. 一次性记账并写盘：
   - buy：`gold -= total`、`cargo += qty`、`stocks -= qty`
   - sell：`gold += net`、`cargo -= qty`、`stocks += qty`
5. 返回权威快照（客户端**必须**用其覆盖本地）：

```jsonc
{ "ok": true, "gold": 46000, "cargo": { "grain": 20 }, "stocks": { "grain": 50, ... }, "serverAt": 1786500000000 }
```

- `serverAt`：服务器存档版本戳（客户端更新 `GS.__lastServerAt`，避免后续自动保存覆盖本次变更）

客户端联动（C1）：

- `execBuyDraft(list, total)` / `execSellDraft(list, net)`：在线先 POST 本接口，成功后用 `r.gold/r.cargo/r.stocks` 覆盖本地，再以 `serverLedger` 轻记账完成 lots/成本/声望/事件。
- `doAction('buy')` / `doSell()`：单笔在线交易同样 POST 本接口（单物品）。
- `buyItem/sellItem(..., {serverLedger:true})`：跳过资金/库存/容量校验与 gold/cargo/stocks 变更；sell 以 `opts.lotsResult` 复用调用方在提交前真实计算的批次结算（含同城同次惩罚）。
- `stockMode='shared'`：仍为纯库存台账（buy 校验库存、sell 回补），不校验资金/持仓。

## 方案与优先级（vNext 改造）

> 下列是“按风险最小→收益最大”的推荐推进顺序；每步尽量保持可回滚与数据兼容。

### P0：数据层解耦（经济距离下发，v9.1 已完成）

- 目标：实现“经济距离（world）与表现距离（client）解耦”。
- v9.1 已落地：
  - `world.tradeRoads`：经济距离路网（仅用于经济计算）
  - 客户端 `TradeGraph`：接入并缓存经济距离

### P1：买入端差异化（产地/非产地）

- 目标：长途收益主要来自“产地更便宜的买入价”，卖出价仍是售卖城市统一价。
- 建议落点：
  - 在 `BASE_PRICES` 或 `getDayPrice` 侧引入“sourceCities/倍率”配置（详见 `Docs/物资设定与例外规则.md`）
  - 先对特产启用，基础物资启用轻量差异

### P2：税务（15%→3% 随声望，v9.1 已完成）

- 目标：把税纳入买/卖最终结算，并在 UI 中显式展示税额与税后价格。
- v9.1 已落地：
  - `Tax.getRate(repLevel)`：15% - 0.5%*Lv，最低 3%
  - `buyItem`：扣金 = 成交总价 + 买入税
  - `sellItem`：入账 = 成交收入 - 卖出税（税基为 `consumeLots` 后的 revenue）

### P3：例外规则（城市×物品卖出封顶/封底）

- 目标：支持沉浸设定（如禁酒城），并可与城市背景呼应。
- 建议落点：
  - 在 `getSellPrice` 的最终输出处套一层 `applySellCaps(city,item,price)`
  - 例外规则先以“世界数据/配置表”形式实现，避免硬编码到逻辑里

### P4：UI 中转面板 + 图表口径调整（v9.1 已完成）

- 目标：中转面板作为“购物车/交易单”，支持一次性多物品确认成交；并让折线图切换逻辑符合 vNext。
- UI（交易单）：
  - 买/卖分离：`buyDraft[]` 与 `sellDraft[]` 两套中转内容，随 `marketTab` 切换显示。
  - 在“进入中转面板/确认成交”前做预校验（买：库存/金币/容量；卖：仅车厢持有量）。
  - 若 `GS.day` 或中枢点变化且 draft 非空：弹窗提示并清空 draft（避免玩家按旧价成交）。
  - 同城同次倒卖惩罚提示优先级最高：批量确认前需先汇总提示并二次确认。
- 在线模式（原子性）：
  - v9.1 已新增 `POST /api/tradeBatch`，先校验再一次性写入库存台账，保证“全成或全不成”。
  - v9.7.3(C1) 升级为**全量结算**（资金/持仓/库存权威，见下节）。
- 图表：
  - 列表跟随 `marketTab`：买入仅本城可购；卖出仅车厢持有（不含仓库）。
  - 折线只画卖出价；提示改为“预计买入/卖出变化”，不展示分位百分比。

### C1：服务端经济一致性（v9.7.3 已完成）

- 目标：在线交易资金/持仓/库存由服务端权威结算，防止改档作弊。
- 已落地：
  - `/api/tradeBatch` 全量结算：金额>0、价格比率 `[0.3,3]`（相对 `world.basePrices` 期望和）、buy 资金+库存 / sell 持仓校验，一次性记账（gold/cargo/stocks），返回 `{gold, cargo, stocks, serverAt}` 供客户端覆盖。
  - 客户端 `serverLedger` 轻记账：`buyItem/sellItem(...,{serverLedger:true})` 只记 lots/成本/声望/事件（sell 复用真实 `lotsResult`）；单笔与批量在线交易统一走 `/api/tradeBatch`。
  - 浏览器回归套件：`scripts/e2e/regress.js`（puppeteer-core + 系统 Chrome，`E2E_URL` 参数化端口），覆盖在线市场面板（51 物/新增物资价格/售出需求标签）与单机旧档迁移（`itemsAfterMigrate=51`、`saveSchema=972`）。
